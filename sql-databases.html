INNER, LEFT, FULL, semi- and anti-joins — what does each return, and why can NOT IN return no rows at all?

SQL
-- Anti-join: customers without orders (safe with NULLs, planner turns it into a Hash Anti Join)
SELECT c.id, c.name
FROM customer c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- Trap 1: NOT IN + one NULL in the subquery = zero rows
SELECT id FROM customer
WHERE id NOT IN (SELECT customer_id FROM orders);   -- customer_id NULL anywhere -> empty result

-- Trap 2: filtering the right table in WHERE turns a LEFT JOIN into an INNER JOIN
SELECT c.name, o.id
FROM customer c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'PAID';   -- keep the filter in ON
-- WHERE o.status = 'PAID'   would drop every customer without a paid order

Why NOT IN fails: x NOT IN (1, NULL) means x <> 1 AND x <> NULL. The second comparison is UNKNOWN, so the whole predicate is never true. NOT EXISTS has no such problem, which is why it is the default for anti-joins.

Physically, PostgreSQL executes any logical join as a Nested Loop (small outer side plus an index on the inner side), a Hash Join (large unsorted inputs, equality only) or a Merge Join (both inputs already sorted). You choose the logical join; the planner chooses the algorithm from statistics.

2
In what order is a SELECT logically evaluated, and what is the difference between WHERE and HAVING?
Medium▼

Logical order (the planner may reorder physically, but the result must be as if it ran in this order):

  1. FROM / JOIN — build the row set
  2. WHERE — filter rows (no aggregates allowed, can use indexes)
  3. GROUP BY — collapse rows into groups
  4. HAVING — filter groups (aggregates allowed)
  5. SELECT — compute expressions, then window functions
  6. DISTINCT → ORDER BY → LIMIT / OFFSET
SQL
SELECT customer_id,
       count(*)                                     AS orders,
       count(*) FILTER (WHERE status = 'REFUNDED')  AS refunds,
       sum(total)                                   AS revenue
FROM orders
WHERE created_at >= now() - INTERVAL '30 days'   -- row filter, before grouping
GROUP BY customer_id
HAVING sum(total) > 1000                          -- group filter, after aggregation
ORDER BY revenue DESC;                            -- the alias is visible here
  • Put every condition that does not need an aggregate in WHERE: fewer rows reach the grouping step and an index can help.
  • This order explains the classic errors: a SELECT alias is not visible in WHERE, and a window function cannot be filtered in WHERE (wrap it in a subquery or CTE).
  • count(*) counts rows, count(col) counts non-NULL values, count(DISTINCT col) counts distinct non-NULL values.
  • PostgreSQL lets you select other columns of a table when you GROUP BY its primary key (functional dependency); other engines may demand every column in the GROUP BY.

What are window functions? Show top-N per group and a running total, and explain the default frame trap.
Hard▼

A window function computes a value over a set of rows related to the current row without collapsing them (unlike GROUP BY). PARTITION BY splits the rows into groups, ORDER BY orders rows inside each partition, and the frame says which rows around the current one take part.

SQL
-- Top 3 orders per customer
SELECT *
FROM (
  SELECT o.*,
         row_number() OVER (PARTITION BY customer_id ORDER BY total DESC) AS rn
  FROM orders o
) t
WHERE rn <= 3;      -- filter outside: window functions run after WHERE

-- Running total and change against the previous day
SELECT day, revenue,
       sum(revenue) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running,
       revenue - lag(revenue) OVER (ORDER BY day)                                        AS delta
FROM daily_revenue;

100111

90322
80443
Default frame trap: With an ORDER BY and no explicit frame, the frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE includes all peers (rows with the same sort value), so two orders on the same day get the same "running" total. Write ROWS BETWEEN … when you mean row by row. The same default is why last_value() seems to return the current row.
Senior detail: For "top N per group" on a big table with an index on (customer_id, total DESC), a LATERAL join with LIMIT 3 per customer reads only 3 index entries per group, while row_number() numbers every row first.

OFFSET vs keyset (seek) pagination — why does OFFSET get slow on deep pages, and how do you implement keyset pagination?
Medium▼

LIMIT 20 OFFSET 100000 makes the database produce 100,020 rows and throw 100,000 away, so every page is slower than the one before. Rows inserted or deleted between two requests also shift the window, and the user sees duplicates or misses rows.

Keyset pagination remembers the sort key of the last row shown and asks for rows "after" it. With an index on the sort columns each page costs the same, no matter how deep.

SQL
CREATE INDEX orders_created_id_idx ON orders (created_at DESC, id DESC);

-- first page
SELECT id, created_at, total FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- next page: pass the last row's (created_at, id) back as the cursor
SELECT id, created_at, total FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)   -- row-value comparison, uses the index
ORDER BY created_at DESC, id DESC
LIMIT 20;
Java — Spring Data JPA (3.1+) scrolling API
interface OrderRepository extends JpaRepository<Order, Long> {
    Window<Order> findFirst20ByOrderByCreatedAtDescIdDesc(ScrollPosition position);
}

Window<Order> page = repo.findFirst20ByOrderByCreatedAtDescIdDesc(ScrollPosition.keyset());
if (page.hasNext()) {
    Window<Order> next = repo.findFirst20ByOrderByCreatedAtDescIdDesc(page.positionAt(page.size() - 1));
}

  • The sort key must be unique — add the primary key as a tie-breaker (created_at, id), otherwise rows with equal timestamps are skipped.
  • The row-value comparison (a, b) < (x, y) only works when all sort columns go in the same direction; mixed directions need the expanded form a < x OR (a = x AND b > y).
  • A total page count still needs count(*), which is a full scan on large PostgreSQL tables — many APIs drop it and return only "has next".

Indexes & Performance

B-trees, composite and partial indexes, reading query plans

5
How does a B-tree index find a row, and how do you choose the column order of a composite index?
Medium▼

A B-tree is a balanced tree of fixed-size pages (8 kB in PostgreSQL). Each inner page holds hundreds of keys, so even hundreds of millions of rows need only 3–4 levels. Leaf pages hold the sorted keys plus a pointer to the row (in PostgreSQL the ctid, a physical address in the table heap), and leaves are linked to their neighbours, which makes range scans and ORDER BY cheap.

Composite index (a, b, c) is sorted by a, then b inside equal a, then c. It can be used like a phone book sorted by last name, then first name:

  • Efficient: a = ?; a = ? AND b = ?; a = ? AND b > ?; a = ? ORDER BY b.
  • Not efficient: b = ? alone — there is no sorted entry point. (PostgreSQL 18 added B-tree skip scan, which helps when a has few distinct values; on 16/17 plan for the leading column.)
  • A range condition on a column stops later columns from narrowing the search: in a = ? AND b > ? AND c = ? the c condition is checked inside the scanned range, not used to seek.

Rule of thumb: equality columns first, then the column you sort by or filter with a range. Among the equality columns, prefer the order that lets other queries reuse the prefix — one index (tenant_id, status, created_at) can serve several queries.

SQL
-- serves: WHERE customer_id = ? ORDER BY created_at DESC LIMIT 20
CREATE INDEX CONCURRENTLY orders_customer_created_idx ON orders (customer_id, created_at);
PostgreSQL vs MySQL InnoDB: A PostgreSQL table is a heap and every index points into it. InnoDB stores the table inside the primary-key B-tree (clustered index) and secondary indexes store the primary key, so a secondary lookup is two tree walks and a long random primary key (UUIDv4) bloats every index and splits pages. Either way every extra index slows inserts and updates — index for the queries you actually run.

Index-only scan needs two things: every column the query uses is in the index, and the table page is marked all-visible in the visibility map. Because of MVCC the index does not know whether a row version is visible to your snapshot; only pages that VACUUM has marked all-visible can skip the heap. A table with lots of recent updates and lagging autovacuum shows a high Heap Fetches count and loses the benefit.

How do you read EXPLAIN (ANALYZE, BUFFERS) output? What do you look at first?
Hard▼
Text — EXPLAIN (ANALYZE, BUFFERS) output

  • Read inside-out: the most indented node runs first and feeds its parent.
  • cost= is the planner's estimate in arbitrary units (startup..total); actual time= is milliseconds per loop. Multiply time and rows by loops — a cheap inner node with loops=50000 is the real problem.
  • Estimated vs actual rows is the first thing to compare. Off by 10× or more → stale or missing statistics (ANALYZE), or correlated columns the planner treats as independent (CREATE STATISTICS). Bad estimates cause bad join choices.
  • Rows Removed by Filter large compared to rows returned → the filter is applied after reading; an index on that column may help.
  • Sort Method: external merge Disk → the sort spilled to disk; raise work_mem for that query or avoid the sort with an index.
  • Buffers: shared hit came from cache, read from disk/OS cache. A query that is fast only when the cache is warm shows many reads on the first run.
  • Node names: Seq Scan, Index Scan, Index Only Scan, Bitmap Heap Scan (many matching rows, read in physical order); Nested Loop, Hash Join, Merge Join.
ANALYZE runs the statement: EXPLAIN ANALYZE really executes the query. For UPDATE/DELETE, wrap it: BEGIN; EXPLAIN ANALYZE UPDATE …; ROLLBACK;
Finding the query in production: Enable pg_stat_statements to rank queries by total time, and auto_explain (with log_min_duration) to log plans of slow statements as they actually ran with production data and parameters.

Transactions & Locking

Isolation levels, MVCC, optimistic and pessimistic locking, deadlocks

9
What does each isolation level guarantee, and which anomalies does each one allow (PostgreSQL vs MySQL)?
Hard▼

ACID's I is a dial, not a switch: weaker levels allow more anomalies and give more concurrency. The anomalies:

  • Dirty read — you read another transaction's uncommitted change.
  • Non-repeatable read — you read the same row twice and get different values because someone committed in between.
  • Phantom — the same WHERE returns a different set of rows the second time.
  • Lost update — two transactions read a value, both write back a value computed from it, one write disappears.
  • Write skew — two transactions read an overlapping set, each updates a different row, together they break a rule (two doctors both go off call because each saw the other on call).
Level (PostgreSQL)Dirty readNon-repeatable readPhantomLost updateWrite skew
Read Uncommitted — behaves as Read Committed in PGPreventedPossiblePossiblePossiblePossible
Read Committed — PG default; new snapshot per statementPreventedPossiblePossiblePossible (read-modify-write in app code)Possible
Repeatable Read — snapshot isolation; one snapshot per transactionPreventedPreventedPrevented in PG (the SQL standard allows it)Prevented — the second writer gets error 40001Possible
Serializable — Serializable Snapshot Isolation (SSI)PreventedPreventedPreventedPreventedPrevented — one transaction gets error 40001

Defaults differ per engine: PostgreSQL, Oracle and SQL Server use Read Committed; MySQL InnoDB uses Repeatable Read. Same Java code, different behaviour.

  • MySQL InnoDB Repeatable Read: plain SELECTs read a snapshot, but UPDATE, DELETE and SELECT … FOR UPDATE read the latest committed row and take next-key (gap) locks, which block inserts into the scanned range. InnoDB does not raise an error for a lost update in a read-modify-write — it silently uses the latest value. Gap locks also make InnoDB deadlocks more common.
  • Oracle has no Repeatable Read; its Serializable is snapshot isolation (write skew still possible).
  • In PostgreSQL Read Committed, a single statement UPDATE account SET balance = balance - 100 WHERE id = 1 is safe: the update re-checks the newest row version. The lost update happens when Java reads the balance, computes, and writes it back — fix with a single atomic UPDATE, @Version, or SELECT … FOR UPDATE.
Serializable means retries: At Repeatable Read and Serializable PostgreSQL aborts instead of blocking: ERROR: could not serialize access (SQLSTATE 40001). The application must retry the whole transaction, so these levels only work with a retry loop around the transactional method.

How does MVCC work in PostgreSQL? What are xmin and xmax, dead tuples, and why does VACUUM matter?
Hard▼

PostgreSQL never overwrites a row in place. Every row version (tuple) carries xmin (the transaction that created it) and xmax (the transaction that deleted or replaced it, 0 if none). An UPDATE writes a new version and sets xmax on the old one; a DELETE only sets xmax. Each statement (Read Committed) or transaction (Repeatable Read and above) works with a snapshot that says which transaction IDs count as committed, and sees only the versions visible to that snapshot.

  • Readers never block writers and writers never block readers. Two writers on the same row still block each other: the second waits for the first to commit or roll back.
  • Dead tuples are versions no snapshot can see any more. VACUUM (normally autovacuum) marks their space reusable and updates the visibility map; it does not shrink the file. VACUUM FULL rewrites the table under an exclusive lock — avoid it on a live system (use pg_repack).
  • HOT updates: if no indexed column changes and the page has free space, the new version stays on the same page and no index entry is written. Another reason not to index every column.
  • Long transactions are the enemy: an idle in transaction session holds back the cleanup horizon for the whole database. Set idle_in_transaction_session_timeout and keep transactions short.
  • Transaction ID wraparound: transaction IDs are 32-bit, so old rows must be frozen by vacuum; autovacuum forces an anti-wraparound vacuum on tables that get close.
SQL
SELECT xmin, xmax, ctid, * FROM accounts WHERE id = 1;

-- tables with the most dead tuples
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- sessions that block cleanup
SELECT pid, state, xact_start, left(query, 60)
FROM pg_stat_activity WHERE state = 'idle in transaction' ORDER BY xact_start;
MySQL InnoDB: InnoDB updates the row in place and keeps the old versions in the undo log; a purge thread removes them. Same idea (snapshots, long transactions cause growth), different storage — there is no VACUUM, but a long transaction grows the undo log instead.

@Entity
class Product {
    @Id Long id;
    int stock;

    @Lock(LockModeType.PESSIMISTIC_WRITE)            // Hibernate on PostgreSQL: SELECT ... FOR UPDATE

  • The retry must wrap the whole transaction: after the exception the persistence context and transaction are unusable. A @Retryable and a @Transactional on the same method only work if the retry advice runs first — putting the transaction on a separate bean makes the order obvious.
  • For a web form, send the version to the client and back. Then the check also covers the minutes the user spent editing, which no database lock can do.
  • Pessimistic: always set a lock timeout (NOWAIT, or SET lock_timeout in PostgreSQL) so a stuck transaction does not drain the connection pool.
  • Often the best option is neither: one atomic statement UPDATE product SET stock = stock - :q WHERE id = :id AND stock >= :q and check the update count.

How does a deadlock happen in a relational database, how does PostgreSQL resolve it, and how do you prevent it?
Medium▼
SQL
-- Transaction A
BEGIN;
UPDATE account SET balance = balance - 10 WHERE id = 1;   -- step 1: A locks row 1
-- Transaction B
BEGIN;
UPDATE account SET balance = balance - 20 WHERE id = 2;   -- step 2: B locks row 2
-- Transaction A
UPDATE account SET balance = balance + 10 WHERE id = 2;   -- step 3: A waits for B
-- Transaction B
UPDATE account SET balance = balance + 20 WHERE id = 1;   -- step 4: B waits for A: a cycle
-- After deadlock_timeout (default 1s) PostgreSQL checks for a cycle and aborts one:
-- ERROR: deadlock detected (SQLSTATE 40P01)
  • PostgreSQL waits deadlock_timeout (default 1 s) before running the deadlock check, then aborts one of the transactions; the other continues. The server log shows both statements.
  • MySQL InnoDB detects deadlocks immediately by default and rolls back the "smaller" transaction (fewest rows changed).
  • Spring translates deadlocks and serialization failures into subclasses of PessimisticLockingFailureException (a TransientDataAccessException) — these are safe to retry.

Prevention

  1. Lock in a consistent order — e.g. always by ascending id: SELECT … WHERE id IN (1, 2) ORDER BY id FOR UPDATE before updating.
  2. Keep transactions short — no HTTP calls, no user input, no message sending inside a transaction.
  3. Index foreign keys and the columns you update by — without an index the database scans and locks more than needed (especially InnoDB, which locks every scanned row).
  4. Fail fast — lock_timeout turns an endless wait into an error you can retry.
  5. Retry — a deadlock is not a bug you can always remove; a bounded retry with jitter is part of the design.

Running a Database from Java

Connection pools, migrations, schema design, replicas

13
How do you size a HikariCP connection pool, and why is a bigger pool often slower?
Hard▼

A database can only execute as many queries truly in parallel as it has CPU cores and I/O capacity. More connections beyond that add context switching, lock contention and memory (each PostgreSQL connection is a separate OS process), so throughput drops while latency rises. A small pool with a short queue in front of it is usually faster than a big one.

  • Starting point (HikariCP's "About Pool Sizing" page): connections = (core_count × 2) + effective_spindle_count for the database server — then measure.
  • Little's law for the application side: connections needed ≈ requests per second × seconds each request holds a connection. 500 req/s × 0.02 s = 10.
  • Count the whole fleet: pods × pool size must stay below PostgreSQL max_connections (default 100) minus admin and replication slots. 20 pods × 10 = 200 already does not fit — use PgBouncer or smaller pools.
YAML — application.yml (HikariCP defaults in comments)
spring:
  datasource:
    hikari:
      maximum-pool-size: 10        # default 10
      minimum-idle: 10             # default = maximum-pool-size (fixed-size pool, recommended)
      connection-timeout: 3000     # default 30000 ms; fail fast instead of piling up threads
      max-lifetime: 1800000        # default 30 min; keep it below any DB/firewall idle cut-off
      leak-detection-threshold: 20000   # log a stack trace if a connection is held > 20 s
  jpa:
    open-in-view: false            # default true: holds a connection for the whole web request

What makes a pool too small in practice is usually not traffic but connections held for too long:

  • Open Session in View (spring.jpa.open-in-view, on by default; Spring Boot logs a warning) keeps the connection through view rendering and JSON serialization.
  • Remote calls (HTTP, Kafka send with acks) inside a @Transactional method hold the connection while waiting on the network.
  • Slow queries — fix the query, not the pool.
Virtual threads: With virtual threads (Java 21, spring.threads.virtual.enabled=true) you can have thousands of concurrent requests, but still only 10 connections. The pool becomes the natural throttle: watch hikaricp.connections.pending and hikaricp.connections.acquire in Micrometer, and keep connection-timeout short so overload fails fast.

How do you run Flyway migrations on PostgreSQL without downtime?
Hard▼

During a rolling deployment the old and the new application version run at the same time against the same schema. So every migration must work with both versions — the expand → migrate → contract pattern, spread over several releases.

ReleaseSchema changeApplication
1 — expandAdd email_address (nullable)Writes both columns, reads the old one
2 — migrateBackfill in batchesReads the new column, still writes both
3 — contractDrop emailUses only the new column

Locks are the real danger. Most ALTER TABLE forms take an ACCESS EXCLUSIVE lock. Even a change that takes 1 ms must first wait behind every running query on the table — and while it waits, every new query queues behind it. One slow report can turn a "fast" migration into an outage. Always set a lock_timeout and retry.

  • Flyway basics: V<version>__name.sql runs once, R__name.sql re-runs when its checksum changes, history lives in flyway_schema_history. Never edit an applied migration — validation fails on the checksum; write a new one.
  • Spring Boot runs Flyway on startup before JPA initializes. Use spring.jpa.hibernate.ddl-auto=validate (never update) in production so Hibernate checks the schema instead of changing it.
  • Several pods starting together are safe: Flyway takes a lock so only one applies migrations.
  • Flyway 10+ needs the extra module org.flywaydb:flyway-database-postgresql on the classpath.
  • Large backfills do not belong in a startup migration: they hold the deployment and a long transaction. Run them as a batched job.
CREATE INDEX CONCURRENTLY: It cannot run inside a transaction block. Flyway detects it on PostgreSQL and runs it outside a transaction, but keep it alone in its own file — mixing it with transactional statements fails. If the build fails it leaves an INVALID index behind: drop it and retry.
15
Normalization vs denormalization — what are the normal forms for, and when is denormalizing the right call?
Medium▼

Normalization stores each fact exactly once, so an update cannot leave two copies disagreeing (update, insert and delete anomalies).

  • 1NF — atomic values, no repeating groups (no phone1, phone2, phone3 columns, no comma lists).
  • 2NF — no column depends on only part of a composite key.
  • 3NF — no column depends on another non-key column (zip → city belongs in its own table). "Every column depends on the key, the whole key, and nothing but the key."
  • BCNF — a stricter 3NF: every determinant is a candidate key.

For OLTP, start at 3NF. Denormalize only for a measured read problem, and decide who keeps the copy correct:

Not every copy is denormalization: An order line's unit_price looks like a copy of product.price, but it is a different fact: the price at the time of the order. It must be stored — joining to today's price would be a bug.

How do read replicas work in PostgreSQL, what is replication lag, and how do you route reads from Spring without breaking read-your-writes?
Hard▼

Streaming replication ships the primary's write-ahead log (WAL) to standbys, which replay it and can serve read-only queries (hot standby). It is asynchronous by default: a commit returns before the standby has the change, so a read on the replica right after a write may not see it — that delay is replication lag.

  • synchronous_standby_names + synchronous_commit = on waits until the standby has flushed the WAL (no data loss on failover); remote_apply waits until it is replayed (read-your-writes on that standby). Each step adds commit latency, and if the synchronous standby is down, commits wait.
  • Measure lag on the primary with pg_stat_replication (write_lag, flush_lag, replay_lag); on a standby, now() - pg_last_xact_replay_timestamp() (misleading when the primary is idle).
  • Long queries on a standby can be cancelled when replay needs to remove rows they still read (max_standby_streaming_delay); hot_standby_feedback = on avoids that at the cost of bloat on the primary.
  • With asynchronous replication, failing over to a replica can lose the last committed transactions.
Java — route @Transactional(readOnly = true) to the replica
class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "replica" : "primary";
    }
}

@Bean @Primary
DataSource dataSource(@Qualifier("primaryDs") DataSource primary, @Qualifier("replicaDs") DataSource replica) {
    var routing = new ReadWriteRoutingDataSource();
    routing.setTargetDataSources(Map.of("primary", primary, "replica", replica));
    routing.setDefaultTargetDataSource(primary);
    routing.afterPropertiesSet();
    // Lazy proxy: the physical connection is fetched on the first statement,
    // after the transaction has set its read-only flag.
    return new LazyConnectionDataSourceProxy(routing);
}

Read-your-writes options, from simple to precise:

  1. Read from the primary in any flow that just wrote (same transaction, or the request right after).
  2. Sticky to primary for a few seconds after a user's write (flag in the session or a cookie).
  3. Remember the primary's WAL position after the write (pg_current_wal_lsn()) and use a replica only once its pg_last_wal_replay_lsn() has passed it.
