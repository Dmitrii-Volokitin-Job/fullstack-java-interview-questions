Explain @Input() and @Output() with EventEmitter. How does two-way binding work with [(ngModel)]?
Easy▼
TypeScript
// Child component
@Component({ selector: 'app-counter', template: `
  <button (click)="increment()">Count: {{ count }}</button>
`})
export class CounterComponent {
  @Input()  count = 0;                  // receives from parent
  @Output() countChange = new EventEmitter<number>(); // emits to parent

  increment() { this.countChange.emit(this.count + 1); }
}

// Parent template
// [(count)] = banana-in-a-box = [count]="val" (countChange)="val=$event"
<app-counter [(count)]="myCount"></app-counter>

// ngModel two-way binding — requires FormsModule
// [ngModel] sets value, (ngModelChange) reads changes
<input [(ngModel)]="username">
// equivalent to:
<input [ngModel]="username" (ngModelChange)="username=$event">

Signal-based alternatives (stable since v19): count = input(0), countChange = output<number>(), and count = model(0), which creates the input and the countChange output in one declaration, so [(count)] works with a writable signal.

5
Explain the difference between map, switchMap, mergeMap, concatMap, and exhaustMap.
Hard▼

map transforms values; the four *Map operators map each value to an inner Observable and flatten it, but they differ in how they handle concurrent inner Observables:

OperatorConcurrencyUse case
mapn/a (synchronous transform)Transform each value — no inner Observable
switchMapCancels previous inner obs on new emissionTypeahead search — only care about latest request
mergeMapAll inner obs run concurrentlyUpload multiple files in parallel
concatMapQueues — waits for previous to completeSequential actions where order matters (shopping cart steps)
exhaustMapIgnores new emissions while inner obs is activeLogin button — ignore re-clicks while request is in flight
TypeScript
// Typeahead — switchMap cancels stale requests
this.searchControl.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(term => this.api.search(term))  // cancels previous HTTP call
).subscribe(results => this.results = results);

// Login button — exhaustMap ignores double-click
this.loginClick$.pipe(
  exhaustMap(() => this.authService.login(this.form.value))
).subscribe(...);

7
How do you handle errors in RxJS? What is the difference between catchError, retry, and retryWhen?
Medium▼
TypeScript
// catchError — recover and return fallback or rethrow
this.http.get<User[]>('/api/users').pipe(
  catchError(err => {
    if (err.status === 404) return of([]);          // return empty array
    return throwError(() => new Error(err.message)); // rethrow
  })
);

// retry(n) — resubscribes up to n times on error (no delay)
this.api.get().pipe(retry(3)).subscribe(...);

// Exponential backoff with retry's config object (RxJS 7) — replaces retryWhen
this.api.get().pipe(
  retry({
    count: 3,
    delay: (err, retryCount) => {
      if (err.status && err.status < 500) return throwError(() => err); // don't retry 4xx
      return timer(2 ** (retryCount - 1) * 1000);            // 1s, 2s, 4s
    }
  }),
  catchError(() => of(fallback))   // after the last retry fails
);
retryWhen is deprecated: in RxJS 7 retryWhen is marked "will be removed in v9 or v10, use retry's delay option instead". retry({ count, delay, resetOnSuccess }) covers backoff, giving up, and filtering which errors to retry. Order matters: catchError after retry handles the final failure; before it, it would swallow the error and nothing is retried.

How do you prevent memory leaks from subscriptions? Compare takeUntil, async pipe, and takeUntilDestroyed.
Hard▼
TypeScript
// Option 1: async pipe — cleanest, auto-unsubscribes, triggers CD
// template: {{ users$ | async }}
users$ = this.userService.getAll(); // no subscribe needed

// Option 2: takeUntilDestroyed (Angular 16+) — inject in constructor
private destroyRef = inject(DestroyRef);

ngOnInit() {
  this.data$.pipe(
    takeUntilDestroyed(this.destroyRef)
  ).subscribe(data => this.data = data);
}

// Option 3: takeUntil pattern (pre Angular 16)
private destroy$ = new Subject<void>();

ngOnInit() {
  interval(1000).pipe(takeUntil(this.destroy$)).subscribe(...);
}
ngOnDestroy() { this.destroy$.next(); this.destroy$.complete(); }
💡

In Angular 16+ with standalone components, prefer takeUntilDestroyed() — it's the cleanest pattern. async pipe is best for templates. Avoid manual Subscription arrays.

Change Detection

Zone.js, OnPush, Signals

9
How does Angular's change detection work? What is Zone.js's role?
Hard▼

Angular uses Zone.js which monkey-patches async APIs (setTimeout, Promise, XHR, DOM events). When any async task completes, Zone.js notifies Angular, which then runs change detection from the root component down the tree — comparing current and previous template expressions. Any change triggers DOM updates.

Default strategy — checks every component, every time. Simple but can be slow with large trees.

OnPush strategy — component is checked only when:

  • An @Input() reference changes (not mutation)
  • An event originates from the component or its children
  • An Observable used with async pipe emits
  • A signal read in its template changes
  • You manually call markForCheck() or detectChanges()
Zone.js is no longer the default: since v21, new Angular apps are zoneless — change detection runs when signals, markForCheck() or template events notify Angular, not after every async task. Zone.js still runs most existing apps, so you need to know both models (see the zoneless question in Performance).
TypeScript
@Component({
  selector: 'app-list',
  changeDetection: ChangeDetectionStrategy.OnPush, // opt-in to OnPush
  template: `<li *ngFor="let item of items">{{ item.name }}</li>`
})
export class ListComponent {
  @Input() items: Item[] = [];
  // Must pass new array reference to trigger re-check:
  // ✅ this.items = [...this.items, newItem]
  // 🚫 this.items.push(newItem)  ← doesn't trigger OnPush
}
10
What are Angular Signals (Angular 16+) and how do they differ from traditional change detection?
Hard▼

Signals are reactive values that know who reads them. When a signal changes, Angular marks exactly the views (components) that read it as dirty, so with OnPush or zoneless only those components are refreshed — not the whole tree, and not their ancestors. The unit of update is still a component view, not a single DOM node. Signals work with and without Zone.js. Status: introduced in v16 (developer preview), signal/computed stable in v17, effect, linkedSignal and toSignal stable in v20.

TypeScript
@Component({
  template: `
    <p>Count: {{ count() }}</p>          <!-- signal read = function call -->
    <p>Double: {{ doubled() }}</p>
    <button (click)="increment()">+</button>
  `
})
export class CounterComponent {
  count   = signal(0);                          // writable signal
  doubled = computed(() => this.count() * 2); // derived, auto-updates

  increment() { this.count.update(v => v + 1); }

  // effect() — side effects when signals change
  constructor() {
    effect(() => console.log('Count changed:', this.count()));
  }
}

// Convert Observable to Signal
users = toSignal(this.userService.getAll(), { initialValue: [] });
ℹ️
Direction of Angular
Signals are what makes zoneless change detection possible: experimental in v18 (provideExperimentalZonelessChangeDetection()), developer preview in v20.0 (renamed provideZonelessChangeDetection()), stable in v20.2, and the default for new apps since v21. Use effect() for side effects (logging, syncing to storage), not to copy one signal into another — that is what computed() and linkedSignal() are for.

11
How does lazy loading work in Angular? What is a Route Guard?
Medium▼
TypeScript
// Lazy loading — loadComponent/loadChildren defer the bundle
const routes: Routes = [
  {
    path: 'admin',
    canActivate: [authGuard],     // guard runs before loading
    loadChildren: () => import('./admin/admin.routes')
                        .then(m => m.ADMIN_ROUTES)
  },
  {
    path: 'profile',
    loadComponent: () => import('./profile/profile.component')
                         .then(m => m.ProfileComponent),
    resolve: { user: userResolver }  // pre-fetch data before activation
  }
];

// Functional guard (Angular 15+ — preferred over class guards)
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);
  return auth.isLoggedIn()
    ? true
    : router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
};

// Functional resolver — pre-fetches data before component activates
export const userResolver: ResolveFn<User> = (route) => {
  return inject(UserService).findById(+route.paramMap.get('id')!);
};

What is the difference between ActivatedRoute params, queryParams, and data? How do you read route parameters?
Easy▼
TypeScript
// Route: /products/:id?filter=active
@Component({...})
export class ProductComponent {
  private route = inject(ActivatedRoute);

  constructor() {
    // params — path variables (:id) — Observable for dynamic changes
    this.route.params.subscribe(p => this.productId = +p['id']);

    // queryParams — ?filter=active
    this.route.queryParamMap.subscribe(q => this.filter = q.get('filter'));

    // data — static data from route config or resolver result
    this.route.data.subscribe(d => this.user = d['user']); // from resolver

    // Snapshot — use only if you know param won't change during component lifetime
    const id = this.route.snapshot.paramMap.get('id');
  }
}

How do you implement a custom async validator (e.g. check if email is unique)?
Medium▼
TypeScript
// Functional async validator factory
export function uniqueEmailValidator(userService: UserService): AsyncValidatorFn {
  return (control: AbstractControl): Observable<ValidationErrors | null> =>
    // Debounce with timer: Angular unsubscribes the previous pending validator on every
    // new value, so the timer is cancelled and the HTTP call fires only after 300 ms of quiet.
    timer(300).pipe(
      switchMap(() => userService.checkEmail(control.value)),
      map(isTaken => (isTaken ? { emailTaken: true } : null)),
      catchError(() => of(null))   // a failing check should not block the form
    );
}
// Wrong: checkEmail(value).pipe(debounceTime(300)) sends the request immediately on every
// keystroke and only delays the answer. Alternative: { updateOn: 'blur' } on the control.

// Usage in FormBuilder — 3rd param is async validators array
email: ['',
  [Validators.required, Validators.email],
  [uniqueEmailValidator(this.userService)]
]

<!-- Template: show error during/after async check -->
<mat-error *ngIf="form.get('email')?.errors?.['emailTaken']">
  Email is already registered
</mat-error>
<mat-spinner *ngIf="form.get('email')?.pending" diameter="16"></mat-spinner>

Performance & Best Practices

Bundle size, lazy loading, trackBy, SSR

15
How do you optimise Angular application performance? List at least 5 techniques.
Hard▼
  1. OnPush change detection — reduces the number of component checks; combine with immutable data
  2. Lazy load routes — split code by route so initial bundle is small
  3. Stable list identity — track in @for (mandatory) or trackBy in *ngFor lets Angular reuse DOM elements instead of destroying and re-creating them on list update
  4. Signals (Angular 16+) — fine-grained reactivity without Zone.js overhead
  5. Defer blocks (Angular 17) — @defer lazily loads component when it enters the viewport
  6. async pipe — auto-unsubscribes, triggers CD precisely when needed
  7. Pure pipes — cached; only re-runs when input reference changes
  8. Bundle optimisation — Angular's esbuild builder (default in v17), tree-shaking, removing unused imports
HTML
<!-- built-in control flow (v17+): track is required -->
@for (user of users; track user.id) {
  <li>{{ user.name }}</li>
} @empty {
  <li>No users</li>
}

<!-- legacy *ngFor: trackBy prevents full list re-render -->
<li *ngFor="let user of users; trackBy: trackByUserId">
  {{ user.name }}
</li>

<!-- @defer (Angular 17) — loads when in viewport -->
@defer (on viewport) {
  <app-heavy-chart [data]="chartData" />
} @placeholder {
  <div class="skeleton"></div>
}

16
What is Angular Universal (SSR)? What problems does it solve?
Medium▼

Server-side rendering renders the app on a Node.js server and sends fully-formed HTML to the client. "Angular Universal" is the old name: since v17 SSR lives in the Angular CLI as @angular/ssr (ng new --ssr or ng add @angular/ssr). Solves:

  • SEO — search crawlers see complete HTML instead of an empty shell
  • First Contentful Paint (FCP) — user sees content before JavaScript executes
  • Social sharing — Open Graph / Twitter Card meta tags are in the initial response

Hydration (provideClientHydration(), stable since v17) — the client reuses the server-rendered DOM and attaches event listeners instead of destroying and re-rendering it, which removes the flicker. Incremental hydration (stable in v20) goes further: @defer blocks with hydrate on … triggers stay server-rendered and inert until needed.

⚠️
SSR gotchas
No window, document, or localStorage on the server. Run browser-only code in afterNextRender() or behind isPlatformBrowser(). With provideClientHydration(), HttpClient GET/HEAD responses made during SSR are put into the page (HTTP transfer cache, on by default) so the client does not re-fetch them; tune it with withHttpTransferCacheOptions() or turn it off with withNoHttpTransferCache().

What is the difference between a structural directive (*ngIf, *ngFor) and an attribute directive?
Easy▼

Structural directives — change the DOM structure by adding/removing elements. Prefixed with * (syntactic sugar for <ng-template>). Examples: *ngIf, *ngFor, *ngSwitch. Angular 17+ offers built-in control flow: @if, @for, @switch — part of the template syntax, so no import is needed and it type-narrows better (stable since v18). NgIf, NgFor and NgSwitch are deprecated since v20 (migration: ng generate @angular/core:control-flow); custom structural directives are not deprecated.

Attribute directives — modify the appearance or behaviour of an existing element without changing DOM structure. Examples: NgClass, NgStyle, custom tooltip directive.

TypeScript
// Custom attribute directive — highlight on hover
@Directive({ selector: '[appHighlight]', standalone: true })
export class HighlightDirective {
  @Input('appHighlight') color = 'yellow';

  constructor(private el: ElementRef) {}

  @HostListener('mouseenter') onEnter() {
    this.el.nativeElement.style.backgroundColor = this.color;
  }
  @HostListener('mouseleave') onLeave() {
    this.el.nativeElement.style.backgroundColor = '';
  }
}

20
How do you implement HTTP interceptors in Angular? What common use cases do they solve?
Medium▼
TypeScript
// Functional interceptor (Angular 15+ — preferred)
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);   // inject() only works synchronously, in the injection context
  const token = auth.getToken();
  if (!token) return next(req);

  const authReq = req.clone({
    headers: req.headers.set('Authorization', `Bearer ${token}`)
  });
  return next(authReq).pipe(
    catchError(err => {
      if (err.status === 401) auth.logout();  // not inject() here: this callback runs later, outside the context
      return throwError(() => err);
    })
  );
};

// Register in bootstrapApplication
provideHttpClient(withInterceptors([authInterceptor, loggingInterceptor]))

Common interceptor use cases: attach auth token, retry on 503, show/hide global loading spinner, log all requests, add correlation ID header, handle 401 token refresh.

How do deferrable views (@defer) work? Which triggers exist, and what do @placeholder, @loading and @error do?
Medium▼

@defer moves the standalone components, directives and pipes used only inside the block into a separate lazy chunk, and renders the block when a trigger fires. It shipped in developer preview in v17 and has been stable since v18. It defers code, not data — fetching still belongs in services or resources.

HTML
@defer (on viewport; prefetch on idle) {
  <app-reviews [productId]="id" />          <!-- in its own chunk -->
} @placeholder (minimum 500ms) {
  <div class="reviews-skeleton"></div>      <!-- shown before the trigger; must be ONE root element for on viewport -->
} @loading (after 100ms; minimum 1s) {
  <app-spinner />                           <!-- shown while the chunk downloads -->
} @error {
  <p>Could not load reviews.</p>
}
TriggerFires when
on idle (default)The browser is idle (requestIdleCallback)
on viewportThe placeholder (or a referenced element) scrolls into view
on interaction / on hoverclick/keydown, or mouseover/focusin, on the placeholder or a referenced element
on immediate / on timer(2s)Right after the page renders / after a delay
when condA boolean expression becomes true (one-way: it does not revert)
prefetch on … / prefetch when …Download the chunk earlier than rendering it
  • Dependencies are deferred only if they are standalone and not referenced anywhere else in the same component (for example by a viewChild query or outside the block); otherwise they are loaded eagerly.
  • Give the placeholder the final size of the content, or the page jumps when it loads (layout shift, CLS).
  • With SSR the server renders the @placeholder. Incremental hydration (hydrate on …) lets the server render the real content and hydrate it later.

What is zoneless change detection, what is its status in each Angular version, and what breaks when you remove Zone.js?
Hard▼

With Zone.js, Angular patches every async API and runs change detection after any async task finishes, whether or not it changed state. Zoneless mode drops Zone.js; change detection is scheduled only when Angular is told that something changed.

VersionStatusAPI
v18ExperimentalprovideExperimentalZonelessChangeDetection()
v20.0Developer preview, renamedprovideZonelessChangeDetection()
v20.2StableprovideZonelessChangeDetection()
v21+Default for new apps; Zone.js is opt-inprovideZoneChangeDetection() to go back to zones

What schedules change detection without Zone.js: a signal read in a template changes; markForCheck() (the async pipe calls it); ComponentRef.setInput(); a template or host event listener fires; a view marked dirty by one of these gets attached.

TypeScript
// v20.2+ opt-in (not needed in v21+ new apps). Also remove 'zone.js' from polyfills in angular.json.
bootstrapApplication(AppComponent, { providers: [provideZonelessChangeDetection()] });

@Component({ template: `<p>{{ status() }}</p>  <p>{{ legacy }}</p>` })
export class StatusComponent {
  status = signal('loading');
  legacy = 'loading';

  constructor() {
    setTimeout(() => this.status.set('ready'), 1000);  // view updates: the signal notifies Angular
    setTimeout(() => (this.legacy = 'ready'), 2000);   // zoneless: no notification, the view stays stale
  }
}
  • Breaks: plain fields mutated in setTimeout, subscribe or a third-party callback; NgZone.onStable / onMicrotaskEmpty never emit and NgZone.isStable is always true; reactive-form setValue does not schedule a check on its own; libraries that rely on Zone.js.
  • Gains: no Zone.js in the bundle, fewer useless change-detection runs, readable stack traces, no monkey-patched browser APIs.
  • Migration path: move state to signals (or async pipe), make components OnPush (zoneless-compatible by design), replace onStable waits with afterNextRender. In v21+ TestBed also runs zoneless by default, so tests surface missing notifications.

TypeScript & Web Fundamentals

Types, the event loop, closures, CORS, browser security, state

23
TypeScript: what is the difference between any, unknown and never? How do generics and utility types help?
Medium▼
  • any switches the type checker off, and it spreads: anything you read from an any is any too.
  • unknown is the safe top type: anything can be assigned to it, but you must narrow it (typeof, instanceof, in, a type guard) before using it. Use it for JSON.parse, catch (e) and other untrusted input.
  • never is the empty type — no value has it. It is the return type of a function that always throws, and the tool for exhaustive switch checks.
TypeScript
function isUser(v: unknown): v is User {                 // user-defined type guard

How does the JavaScript event loop work? In what order do synchronous code, microtasks and tasks run?
Hard▼

JavaScript runs your code on one thread with one call stack. Async work (timers, network, events) is handled by the browser, and its callbacks wait in queues until the stack is empty. Each turn of the event loop does three things, in this order:

JavaScript
console.log('1 sync');
setTimeout(() => console.log('5 task'), 0);
Promise.resolve().then(() => console.log('3 microtask'));
queueMicrotask(() => console.log('4 microtask'));
console.log('2 sync');
// prints 1, 2, 3, 4, 5 — sync code first, then every microtask, then the next task

async function load() {
  console.log('A');          // runs synchronously, like any function body
  await fetchUser();         // everything after await is a microtask continuation
  console.log('B');
}
  • Tasks (often called macrotasks): the initial script, setTimeout/setInterval, UI events, MessageChannel, network callbacks. One per turn.
  • Microtasks: Promise reactions (then/catch/await continuations), queueMicrotask, MutationObserver. The whole queue is drained after every task.
  • setTimeout(fn, 0) is "after the current task and all microtasks", never immediate; timers nested more than 5 levels deep are clamped to at least 4 ms.
  • A task longer than 50 ms is a long task: input and rendering wait for it. Split the work into chunks or move it to a Web Worker.
  • Node.js has the same idea with phases, and runs process.nextTick callbacks before Promise microtasks.
  • Angular link: Zone.js knows when to run change detection because it patches exactly these task and microtask APIs.

What is a closure, and how is this determined in JavaScript (regular functions vs arrow functions)?
Medium▼

A closure is a function together with the variables of the scope it was created in. The function keeps those variables alive and can read and change them after the outer function has returned — the basis of private state, factories and every callback that uses outer variables.

TypeScript
function counter() {
  let count = 0;                          // private: only the returned functions can reach it
  return { inc: () => ++count, get: () => count };
}

for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));   // 3 3 3: one shared var
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j));   // 0 1 2: new binding per iteration

class Timer {
  seconds = 0;
  start() {
    setInterval(function () { this.seconds++; }, 1000);  // wrong: 'this' is not the Timer
    setInterval(() => this.seconds++, 1000);              // arrow: 'this' from start()
  }
}

class Greeter {
  name = 'Ann';
  hello() { return 'Hi ' + this.name; }
}
const g = new Greeter();
const hello = g.hello;
hello();                                              // TypeError: 'this' is undefined (classes are strict mode)
button.addEventListener('click', g.hello);            // 'this' is the button, not g
button.addEventListener('click', () => g.hello());    // fine: called as a method
Callthis in a regular function
obj.method()obj — decided at the call site, not where it was defined
fn()undefined in strict mode (modules, classes); the global object in sloppy scripts
new Fn()The new object
fn.call(x), fn.apply(x), fn.bind(x)x
Arrow functionNo own this: it uses the this of the enclosing scope, and call/bind cannot change it
Closures and memory: A closure keeps everything it references alive. An event listener or subscription that is never removed keeps its component (and everything that component references) in memory — the usual source of SPA memory leaks.

What happens in a CORS preflight, and why does the same API call work from Postman or curl but fail in the browser?
Hard▼

The same-origin policy is enforced by the browser: a page from https://app.example.com may send requests to https://api.example.com, but it may not read the response unless the server allows that origin. An origin is scheme + host + port. Postman and curl are not browsers, so they ignore CORS entirely — "works in Postman" says nothing about CORS.

Text — preflight seen in DevTools → Network
OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 3600            # browser may cache this answer

then the real request:  POST /api/orders  with  Origin: https://app.example.com
  • When a preflight happens: any method other than GET/HEAD/POST, any non-safelisted header (Authorization, custom headers), or a Content-Type other than text/plain, multipart/form-data, application/x-www-form-urlencoded. A JSON POST with a bearer token always preflights.
  • Simple requests skip the preflight — the request reaches and runs on the server; the browser only hides the response. CORS is not a server-side protection, which is why CSRF defenses are still needed.
  • Cookies (withCredentials: true): the server must answer with the exact origin (not *) and Access-Control-Allow-Credentials: true.
  • Classic Spring bug: the preflight OPTIONS has no Authorization header, Spring Security rejects it with 401, and the browser reports a CORS error. Enable http.cors(…) so the CORS filter answers the preflight before authentication.
  • In development, the Angular CLI proxy (proxy.conf.json) makes API calls same-origin, so no CORS configuration is needed locally.

How do XSS and CSRF attacks work, what does Angular sanitize automatically, and what is still your job?
Hard▼

XSS: attacker-controlled data ends up executed as script in your page. The script runs with your origin's rights — it can read non-HttpOnly cookies and storage and send requests as the user. CSRF: another site makes the victim's browser send a state-changing request to your API, and the browser attaches the victim's cookies automatically.

TypeScript
@Component({
  template: `
    <p>{{ comment }}</p>                  <!-- escaped: tags shown as text -->
    <div [innerHTML]="comment"></div>      <!-- sanitized: onerror and <script> stripped -->
  `
})
export class CommentComponent {
  comment = '<img src=x onerror="alert(1)"><b>hi</b>';
  private host = inject(ElementRef);
  private sanitizer = inject(DomSanitizer);

  unsafe() {
    this.host.nativeElement.insertAdjacentHTML('beforeend', this.comment);  // bypasses Angular: real XSS
    this.sanitizer.bypassSecurityTrustHtml(this.comment);                   // you vouch for it: audit every use
  }
}
  • Angular protects everything that goes through its templates: interpolation is escaped, and bindings to HTML, style and URL contexts ([innerHTML], [href], [style]) are sanitized. Resource URLs (<iframe [src]>, script URLs) are blocked unless marked trusted.
  • Your job: direct DOM writes through ElementRef/document, every bypassSecurityTrust… call, third-party libraries that write HTML, and never building Angular templates on the server from user input (template injection). Add a Content-Security-Policy; Angular also supports Trusted Types.
  • CSRF defenses: SameSite cookies (Lax or Strict) plus a CSRF token. Angular's HttpClient reads the XSRF-TOKEN cookie and sends it as the X-XSRF-TOKEN header on mutating requests to relative URLs (not on GET/HEAD, and by default not to absolute URLs) — the default names Spring Security's CookieCsrfTokenRepository uses.
  • If the API authenticates only with a bearer token in the Authorization header (no cookies), CSRF does not apply — but then XSS can steal the token, so XSS becomes the main risk.
TypeScript
provideHttpClient(withXsrfConfiguration({ cookieName: 'XSRF-TOKEN', headerName: 'X-XSRF-TOKEN' }));

Where should a single-page app keep a JWT — localStorage, sessionStorage, memory or an HttpOnly cookie? What are the trade-offs?
Hard▼
StorageReadable by JS (XSS can steal it)Survives reloadSent automatically (CSRF risk)
localStorageYesYes, until removedNo
sessionStorageYesPer tab, until the tab closesNo
In memory (a service field / signal)Only while the page runsNo — needs a silent refreshNo
HttpOnly; Secure; SameSite cookieNoYesYes — add CSRF protection

What a senior answer says: no storage survives XSS. Even with an HttpOnly cookie, injected script can call your API as the user while the page is open — HttpOnly only stops the token from being stolen and reused elsewhere. So the order is: prevent XSS first, then reduce what a stolen token is worth.

  1. Backend-for-Frontend (BFF) — the option the IETF draft "OAuth 2.0 for Browser-Based Applications" ranks as most secure: the server does the OAuth flow and keeps the tokens; the browser only holds an HttpOnly session cookie (with SameSite and CSRF protection). No token ever reaches JavaScript.
  2. Pure SPA: Authorization Code flow with PKCE (never the implicit flow), short-lived access token in memory, refresh token rotation, strict CSP.
  3. localStorage is the weakest option for long-lived tokens: one XSS anywhere on the origin, and the token works from the attacker's machine until it expires.

State management in Angular: when is a signal-based service enough, and when do you reach for NgRx Store or NgRx SignalStore?
Hard▼

First separate the kinds of state: local UI state (an open panel — a signal in the component), shared client state (cart, filters, current user), and server state (data that belongs to the backend and must be cached and refetched). Most bugs come from treating server state as if the client owned it.

TypeScript
// 1. A service with signals: enough for most apps
@Injectable({ providedIn: 'root' })
export class CartStore {
  private readonly _items = signal<CartItem[]>([]);
  readonly items = this._items.asReadonly();                       // components cannot write
  readonly total = computed(() => this._items().reduce((s, i) => s + i.price * i.qty, 0));
  add(item: CartItem) { this._items.update(items => [...items, item]); }
}

// 2. NgRx SignalStore (@ngrx/signals): same idea with structure and plugins
export const CartSignalStore = signalStore(
  { providedIn: 'root' },
  withState({ items: [] as CartItem[] }),
  withComputed(({ items }) => ({
    total: computed(() => items().reduce((s, i) => s + i.price * i.qty, 0)),
  })),
  withMethods(store => ({
    add(item: CartItem) { patchState(store, s => ({ items: [...s.items, item] })); },
  })),
);
OptionChoose it whenCost
Signals in a serviceSmall/medium app, state owned by one feature, one teamConventions are up to you; no DevTools history
NgRx SignalStoreSeveral features need the same patterns (loading flags, entities, persistence) and you want them consistentA library to learn, lighter than Store
NgRx Store (Redux: actions, reducers, effects, selectors)Large app, many teams, complex async flows, need for an event log and time-travel debuggingMost boilerplate; indirection for simple changes

Whatever you choose: keep state immutable (new arrays/objects, so OnPush and computed see the change), expose read-only views, and keep one owner per piece of state.
