Kafka Architecture

Brokers, ZooKeeper/KRaft, topics, partitions, replication

1
Explain Kafka's core architecture. What are brokers, topics, partitions, and replicas?
Medium▼
  • Broker — a Kafka server. A cluster has multiple brokers for fault tolerance and load distribution. Each broker holds some topic partitions.
  • Topic — a named, durable, append-only log. Messages are never deleted on consume — retained by time or size policy.
  • Partition — unit of parallelism and ordering. A topic splits into N partitions distributed across brokers. Messages within one partition are strictly ordered. Consumers in a group each own a subset of partitions.
  • Replica — each partition has a leader + N-1 follower replicas on different brokers. Leader handles all reads/writes; followers replicate. If the leader fails, a follower is elected.
  • Controller — in KRaft mode (the only mode since Kafka 4.0) a small quorum of controller nodes stores the metadata log; the active controller of that quorum runs partition leader elections and pushes metadata to brokers.

Records with the same key always land in the same partition, so per-key order holds. Inside one group a partition has exactly one owner; a third consumer here would take a partition from Consumer 1, and a fourth would sit idle. A second group reads the same partitions independently with its own offsets.

Text — Cluster layout
Topic: orders  (3 partitions, replication-factor 3)

Partition 0:  Leader=Broker1  Replicas=[Broker1, Broker2, Broker3]  ISR=[1,2,3]
Partition 1:  Leader=Broker2  Replicas=[Broker2, Broker3, Broker1]  ISR=[2,3,1]
Partition 2:  Leader=Broker3  Replicas=[Broker3, Broker1, Broker2]  ISR=[3,1,2]

ISR = In-Sync Replicas (replicas fully caught up to leader)
If Broker1 dies → Partition 0 leader election → Broker2 or Broker3 takes over
💡
Key interview insight
Kafka achieves high throughput by writing sequentially to disk (not random I/O) and using zero-copy transfer (sendfile syscall) to deliver messages to consumers. This is why Kafka outperforms systems that use random writes. Caveat: zero-copy only applies to plaintext listeners; with TLS the broker must copy data into user space to encrypt it, so TLS clusters lose part of that advantage.

What is ZooKeeper's role in Kafka? What is KRaft mode and why was it introduced?
Hard▼

ZooKeeper (legacy) stored Kafka cluster metadata: broker registration, topic configs, partition assignments, controller election, ACLs and, in very old versions, consumer offsets. One broker acted as controller and had to load the whole state from ZooKeeper on failover, so failover time and partition count were bounded by ZooKeeper, and you operated two distributed systems with two security models.

KRaft (Kafka Raft) replaces ZooKeeper with a Raft quorum of controller nodes that keep the metadata as an event log (__cluster_metadata). Brokers replicate that log instead of querying ZooKeeper. Timeline: production-ready in 3.3, ZooKeeper deprecated in 3.5, migration path GA in 3.6, ZooKeeper support removed in 4.0. Any 4.x cluster is KRaft-only; a ZK cluster must migrate on 3.x first.

  • One system to operate and secure (no ZooKeeper ensemble)
  • Fast controller failover: standby controllers already hold the metadata log in memory, so there is no full reload
  • Higher partition ceilings, because metadata changes are log appends rather than ZooKeeper writes
  • Controllers can run as dedicated nodes (recommended for production) or combined with brokers (process.roles=broker,controller, fine for dev)
Properties — KRaft mode config
# controller.properties (dedicated controller node)
process.roles=controller
node.id=1
controller.listener.names=CONTROLLER
listeners=CONTROLLER://:9093
# Kafka 3.9+ (KIP-853 dynamic quorum): bootstrap servers instead of a fixed voter list
controller.quorum.bootstrap.servers=host1:9093,host2:9093,host3:9093
log.dirs=/var/kafka/meta

# Older static quorum style, still supported:
# controller.quorum.voters=1@host1:9093,2@host2:9093,3@host3:9093

# Format storage before first start (dynamic quorum): either all controllers with
#   kafka-storage.sh format -t $CLUSTER_ID -c controller.properties --initial-controllers ...
# or the first one with --standalone and add the others later (kafka-metadata-quorum.sh add-controller)
💡
Interview angle
Run 3 controllers (tolerates 1 failure) or 5 (tolerates 2), same majority rule as any Raft or ZooKeeper quorum. The "why" behind KRaft is less about speed and more about having one metadata model, one security model and one thing to upgrade.

How does Kafka handle message retention? What are the retention strategies?
Medium▼

Kafka retains all messages regardless of consumer state. Consumers track their own position (offset) — re-reading is free. Three retention strategies per topic (time and size can be combined; cleanup.policy=compact,delete combines compaction with time-based deletion):

StrategyConfigBehaviour
Time-basedretention.ms (default: 7 days)Delete segments older than N ms
Size-basedretention.bytes per partitionDelete oldest segments when partition exceeds size
Compactcleanup.policy=compactKeep only the latest message per key — like a changelog; tombstone (null value) = deletion
Bash
# Create compacted topic — useful for event sourcing / CDC
kafka-topics.sh --bootstrap-server kafka:9092 --create --topic user-updates \
  --partitions 6 --replication-factor 3 \
  --config cleanup.policy=compact \
  --config min.cleanable.dirty.ratio=0.1

# Override retention on existing topic (1 day)
kafka-configs.sh --bootstrap-server kafka:9092 --alter \
  --entity-type topics --entity-name orders \
  --add-config retention.ms=86400000

Retention works on whole segments: only closed segments are deleted or compacted, so data can live longer than retention.ms until its segment rolls (segment.ms, segment.bytes). Very small segment settings make compaction aggressive but create many files, so keep them for demos only.

💡
Log compaction use case
Use compacted topics for "latest state" scenarios: user profiles, product inventory, feature flags. New consumers can bootstrap current state by reading the compacted topic — no need for a separate snapshot mechanism.
4
How do you choose the number of partitions for a topic?
Hard▼

Partitions determine maximum parallelism. Key factors:

  • Target throughput — one partition handles ~10-100 MB/s depending on message size. If you need 1 GB/s, you need at least 10-100 partitions
  • Consumer parallelism — max parallel consumers = number of partitions. 20 partitions → max 20 consumers in a group
  • Ordering requirements — if all messages must be globally ordered: 1 partition (but no parallelism). Per-key order: use key-based routing across partitions
  • Broker capacity — every partition replica costs open file handles (segment and index files), memory and replication work, and adds to leader-election and recovery time. The old "≈4,000 partitions per broker / 200K per cluster" guidance came from the ZooKeeper era; KRaft raises the ceiling, but measure on your own hardware instead of trusting a fixed number
⚠️
You cannot decrease partitions
Kafka has no way to remove partitions from a topic; the only route is a new topic plus migration. Increasing partitions is allowed, but it changes the key-to-partition mapping (same key → different partition), so per-key ordering breaks across the change and Kafka Streams co-partitioning breaks. Plan capacity upfront and over-provision moderately. A common formula: partitions = max(target_throughput_MB/s ÷ producer_throughput_per_partition, num_consumers_needed)

What is a Schema Registry? Why is it important in a Kafka ecosystem?
Hard▼

Schema Registry (Confluent or Apicurio) stores and enforces Avro/Protobuf/JSON Schema definitions. Producers register a schema; the serializer writes a small prefix in front of the payload (Confluent wire format: a magic byte plus a 4-byte schema ID), and consumers fetch the schema by that ID and cache it. The registry checks each new schema version against the compatibility rule, so breaking changes are rejected at registration time, before they reach consumers.

Java — Avro with Spring Kafka
// Avro schema (order.avsc)
// {
//   "type": "record",
//   "name": "OrderEvent",
//   "fields": [
//     {"name": "orderId", "type": "string"},
//     {"name": "userId",  "type": "long"},
//     {"name": "total",   "type": "double"},
//     {"name": "status",  "type": {"type":"enum","name":"Status","symbols":["PLACED","PAID","SHIPPED"]}}
//   ]
// }

// application.yml
// spring.kafka.producer.value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
// spring.kafka.properties.schema.registry.url: http://schema-registry:8081

// Producer — sends Avro-serialized message
kafkaTemplate.send("orders", orderId, OrderEvent.newBuilder()
    .setOrderId(orderId)
    .setUserId(userId)
    .setTotal(total)
    .setStatus(Status.PLACED)
    .build());

Compatibility modes: BACKWARD (new schema reads old data), FORWARD (old schema reads new data), FULL (both), NONE. Use BACKWARD or FULL in production — lets you deploy consumers before producers.

Explain producer acks=0, acks=1, and acks=all. What are the trade-offs?
Hard▼
acksDurabilityLatencyRisk
0 (fire-and-forget)None — broker may not receive itLowest (no wait)Message loss on any failure
1 (leader only)Leader acknowledges writeLow (~1 RTT)Loss if leader crashes before replication
all / -1 (all ISR)All ISR replicas acknowledgeHigher (~2+ RTT)No loss as long as ≥1 ISR is alive
Properties
# Production-safe producer config (these are the defaults since Kafka 3.0 —
# set them explicitly so a conflicting override fails loudly)
acks=all                    # wait for all in-sync replicas
retries=2147483647          # retry forever (rely on delivery.timeout.ms)
delivery.timeout.ms=120000  # 2 min overall delivery deadline
enable.idempotence=true     # no duplicates from retries, per partition and session (requires acks=all)
max.in.flight.requests.per.connection=5  # max with idempotence; order is still kept

# Performance tuning
batch.size=65536            # 64 KB batch (default 16KB — too small for high throughput)
linger.ms=10                # default is 5 since Kafka 4.0 (KIP-1030), 0 before
compression.type=snappy     # good ratio + fast decompression (lz4 also good)
buffer.memory=67108864      # 64MB producer buffer
🚫
acks=all is not enough
Also set min.insync.replicas=2 on the broker/topic. With replication-factor=3 and min.insync.replicas=2, the broker rejects acks=all writes with NotEnoughReplicasException when fewer than 2 replicas are in sync; the producer retries until delivery.timeout.ms and then fails the send. You trade availability for durability on purpose. Without this setting (the broker default is 1), acks=all with only the leader in the ISR behaves like acks=1.

How does Kafka producer batching and compression work? How do you maximise throughput?
Medium▼

The producer accumulates messages in a per-partition buffer (RecordAccumulator). A batch is sent when either batch.size is reached OR linger.ms elapses (whichever first). Compression is applied per batch — larger batches compress better.

Java
// High-throughput producer with Spring Kafka
@Bean
public ProducerFactory<String, OrderEvent> producerFactory() {
    Map<String, Object> props = new HashMap<>();
    props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
    props.put(ProducerConfig.ACKS_CONFIG, "all");
    props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
    props.put(ProducerConfig.BATCH_SIZE_CONFIG, 65536);   // 64KB
    props.put(ProducerConfig.LINGER_MS_CONFIG, 5);
    props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "snappy");
    props.put(ProducerConfig.BUFFER_MEMORY_CONFIG, 67108864L); // 64MB
    return new DefaultKafkaProducerFactory<>(props);
}

Compression algorithms: gzip (good ratio, highest CPU cost), snappy (fast, moderate ratio), lz4 (usually the fastest, moderate ratio), zstd (Kafka 2.1+, usually the best ratio at a CPU cost close to lz4/snappy). A common default today is lz4 for latency-sensitive traffic and zstd when network or storage cost dominates. The batch stays compressed on the broker and is only decompressed by consumers, so compression saves network, disk and replication bandwidth at once — as long as the topic's compression.type is producer (the default), so the broker does not recompress.

What is the Kafka Transactional API? How do you implement exactly-once across multiple topics?
Hard▼

Kafka transactions allow atomically writing to multiple partitions (and marking consumer offsets). Either all writes commit or all abort — prevents partial writes on failure.

Java
// Producer config for transactions
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-processor-1"); // unique per producer instance
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

// Init once at startup
producer.initTransactions();

// Atomic write to multiple topics
try {
    producer.beginTransaction();

    producer.send(new ProducerRecord<>("orders", order));
    producer.send(new ProducerRecord<>("audit-log", auditEntry));
    producer.send(new ProducerRecord<>("notifications", notification));

    // Commit consumer offsets atomically with the produce
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);

    producer.commitTransaction();
} catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException e) {
    producer.close(); // fatal: another instance with the same transactional.id took over, or the producer is broken
} catch (KafkaException e) {
    producer.abortTransaction(); // abortable error: roll back and retry the batch
}

// Consumer must set isolation.level=read_committed to skip aborted transactions

Scope: the atomicity covers Kafka writes and consumer offsets only. A database write inside the same block is not part of the transaction; for DB + event atomicity use the Outbox pattern.

⚠️
Performance cost
Each transaction adds coordinator round trips and commit markers, and read_committed consumers cannot read past an open transaction, so end-to-end latency grows with the commit interval. The overhead per message shrinks as you put more records into each transaction. Use them when you genuinely need cross-topic atomicity. For most cases, idempotent producers + idempotent consumers (dedup by event ID) is simpler and faster.

How does the Kafka partitioner work? When would you write a custom partitioner?
Medium▼

No key — "sticky partitioning" (Kafka 2.4, KIP-480): the producer fills a batch for one partition, then switches. Better batching than round-robin. Kafka 3.3 (KIP-794) moved this into the producer itself as a built-in uniform sticky partitioner that also avoids slow brokers; DefaultPartitioner and UniformStickyPartitioner are deprecated, so leave partitioner.class unset.

Key-based — if a message has a key: partition = toPositive(murmur2(keyBytes)) % numPartitions. Same key always → same partition (ordering per key) as long as the partition count does not change. It is murmur2 on the serialized bytes, not Java hashCode(), which is why non-Java clients can be configured to produce the same mapping.

Custom partitioner use cases:

  • Route by region: EU customers → EU partition (data residency)
  • A hot key problem: one user sends 80% of traffic → all goes to 1 partition; route to random partition for that key
  • Business priority routing: VIP orders → dedicated partition consumed by faster consumer
Java
public class RegionPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);
        OrderEvent order = (OrderEvent) value;
        int half = numPartitions / 2;
        int hash = Utils.toPositive(Utils.murmur2(keyBytes)); // Math.abs(Integer.MIN_VALUE) is negative
        // Route EU orders to first half, others to second half
        if ("EU".equals(order.getRegion())) {
            return hash % half;
        }
        return half + hash % (numPartitions - half);
    }

    @Override public void configure(Map<String, ?> configs) { }
    @Override public void close() { }
}

This sketch assumes every record has a key and at least 2 partitions. Note that a custom partitioner couples producers to partition layout; a separate topic per region is often simpler to operate and to secure.

Poll loop, offset management, rebalancing, lag

How does the Kafka consumer poll loop work? What is max.poll.records and max.poll.interval.ms?
Hard▼

The consumer's poll() fetches records (and runs rebalance callbacks and auto-commit). Heartbeats are sent by a separate background thread since Kafka 0.10.1 (KIP-62), so liveness and progress are checked separately: missing heartbeats for session.timeout.ms means "the process is dead", and not calling poll() within max.poll.interval.ms means "the process is alive but stuck". Either one removes the consumer from the group.

Java
// Manual poll loop (Spring Kafka hides this — shown for understanding)
while (true) {
    ConsumerRecords<String, OrderEvent> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<?, ?> record : records) {
        processRecord(record);  // must complete before next poll()
    }
    consumer.commitSync(); // commit after processing batch
}

// Key configs:
// max.poll.records=500          — max records returned per poll (default 500)
// max.poll.interval.ms=300000   — if poll() not called within 5min, consumer is kicked
// session.timeout.ms=45000      — no heartbeat for this long = consumer crashed (default 45s since 3.0)
// heartbeat.interval.ms=3000    — heartbeat frequency (keep it at most 1/3 of session.timeout)
🚫
Common bug
If processing 500 records takes longer than max.poll.interval.ms, the consumer is kicked from the group, causing a rebalance. Fix: lower max.poll.records, increase max.poll.interval.ms, or process records asynchronously (but then you must manage offset commits carefully).

What is Consumer Group Rebalancing? What is Cooperative Rebalancing (Kafka 2.4+)?
Hard▼

When consumers join/leave a group, partitions are reassigned — this is a rebalance. How much processing stops depends on the protocol.

Triggers: consumer joins, consumer leaves (gracefully or timeout), partition count changes, subscription changes.

Eager rebalance (classic protocol, Range/RoundRobin/Sticky assignors): all consumers release all partitions, then re-assign from scratch. Processing stops for the entire group — this is the "stop-the-world" rebalance.

Cooperative/Incremental rebalance (Kafka 2.4+, CooperativeStickyAssignor): only the partitions that must move are revoked, over two short rounds; consumers keep processing the rest. Since Kafka 3.0 the default assignor list is [RangeAssignor, CooperativeStickyAssignor], which allows a rolling upgrade to cooperative by removing Range in a second bounce.

New consumer protocol (KIP-848, GA in Kafka 4.0): the group coordinator on the broker computes assignments and each consumer reconciles incrementally through its heartbeats — no group-wide synchronization barrier at all. Brokers enable it by default in 4.0, but clients must opt in with group.protocol=consumer; the client default is still classic.

Properties
# Option A — classic protocol with cooperative rebalancing
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# Option B — Kafka 4.0+ brokers and clients: new rebalance protocol
group.protocol=consumer
group.remote.assignor=uniform   # optional: server-side assignor (uniform or range); partition.assignment.strategy is ignored

# group.instance.id — static membership (Kafka 2.3, KIP-345)
# A restarted member with the same id gets its partitions back without a rebalance,
# provided it returns within session.timeout.ms
group.instance.id=order-consumer-pod-1
💡
K8s + Kafka
In Kubernetes, set group.instance.id to the Pod name (via Downward API env var) — stable names come from a StatefulSet; Deployment pods get new names. When a pod restarts within session.timeout.ms, it reclaims its partitions without rebalancing the whole group. Trade-off: if the pod is really gone, its partitions sit unconsumed until the session times out, so do not raise the timeout blindly.

What is consumer lag and how do you monitor and reduce it?
Medium▼

Consumer lag = difference between the latest offset produced and the consumer's current committed offset. High lag = consumer falling behind producers.

Bash
# Check lag for a consumer group
kafka-consumer-groups.sh --bootstrap-server kafka:9092 \
  --describe --group order-processors

# Output:
# GROUP              TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# order-processors   orders  0          1023400         1025000         1600
# order-processors   orders  1          987200          990000          2800

# Export lag to Prometheus via kafka-exporter or burrow
# Alert when lag > 10000 and growing

Reducing lag:

  • Add more consumers (up to partition count)
  • Increase partition count (then also add consumers)
  • Optimise processing: async I/O, batch DB writes, connection pooling
  • Increase fetch.min.bytes and fetch.max.wait.ms to reduce round trips
  • Scale consumer horizontally (multiple pods)

Java — Spring Kafka manual commit
// application.yml
// spring.kafka.listener.ack-mode: MANUAL_IMMEDIATE
// spring.kafka.consumer.enable-auto-commit: false

@KafkaListener(topics = "orders")
public void process(ConsumerRecord<String, OrderEvent> record,
                    Acknowledgment ack) {
    processOrder(record.value());
    ack.acknowledge(); // commit only after successful processing
    // On failure: let the exception propagate. The container's DefaultErrorHandler
    // seeks back, retries with back-off and finally hands the record to a
    // DeadLetterPublishingRecoverer (see the DLT question). Simply not acking does NOT
    // redeliver: the next records are still fetched, and a later ack commits past the failed one.
}

Delivery Guarantees & Error Handling

Idempotence, DLT, retry strategies

14
How do you implement a Dead Letter Topic (DLT) pattern with Spring Kafka?
Hard▼

When a consumer fails to process a message after N retries, the message is sent to a Dead Letter Topic (e.g. orders.DLT) for later inspection and manual remediation.

Java
// DefaultErrorHandler with exponential backoff + DLT (Spring Kafka 2.8+)
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template,
        (r, e) -> new TopicPartition(r.topic() + ".DLT", r.partition()));

    ExponentialBackOffWithMaxRetries backoff = new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(1_000L);  // 1s, 2s, 4s
    backoff.setMultiplier(2.0);
    backoff.setMaxInterval(10_000L);    // cap at 10s

    var handler = new DefaultErrorHandler(recoverer, backoff);
    // Don't retry on deserialization errors or business logic exceptions
    handler.addNotRetryableExceptions(DeserializationException.class, BusinessRuleException.class);
    return handler;
}

// DLT consumer — for monitoring/reprocessing
@KafkaListener(topics = "orders.DLT")
public void handleDlt(@Payload OrderEvent order,
                      @Header(KafkaHeaders.DLT_EXCEPTION_MESSAGE) String errorMsg) {
    log.error("DLT received: {} reason: {}", order, errorMsg);
    alertingService.notify(order, errorMsg);
}

Blocking retries like these hold up the whole partition while the back-off runs. For long back-offs use non-blocking retry topics (@RetryableTopic, see the retry-topics question in MQ Patterns). The DLT needs at least as many partitions as the source topic, because the default resolver keeps the same partition number.

Practical advice
Always enable idempotence (enable.idempotence=true) — it's free safety. Use transactions only for the consume-transform-produce pattern (Kafka Streams uses them automatically). For most microservices, idempotent consumer (dedup table) + idempotent producer is simpler and sufficient.

Kafka Streams

Stream processing, stateful operations, windowing, KTable

16
What is Kafka Streams? How does it differ from using Kafka consumers directly?
Hard▼

Kafka Streams is a client library for building stateful stream processing apps on top of Kafka. It runs inside your application process — no separate cluster needed (unlike Flink or Spark).

Plain ConsumerKafka Streams
Stateful operationsManual (DB, Redis)Built-in: count, aggregate, join with RocksDB state store
Exactly-onceComplex to implementBuilt-in (processing.guarantee=exactly_once_v2)
WindowingManualTumbling, hopping, sliding, session windows
Stream-Stream/Stream-Table joinsManualKStream-KStream, KStream-KTable join operators
DeploymentAny JVM appAny JVM app — scales by partition count
Java — Kafka Streams order aggregation
StreamsBuilder builder = new StreamsBuilder();

// Read from orders topic
KStream<String, OrderEvent> orders = builder.stream("orders");

// Count orders per user in a 1-hour tumbling window
KTable<Windowed<String>, Long> orderCounts = orders
    .groupBy((key, order) -> order.getUserId())     // re-key by userId
    .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofHours(1)))
    .count(Materialized.as("order-count-store"));  // RocksDB state store

// Filter high-value orders and enrich with user data (KStream-KTable join)
KTable<String, User> users = builder.table("user-updates");
orders
    .filter((k, o) -> o.getTotal() > 1000)
    .join(users, (order, user) -> new VIPOrderAlert(order, user))
    .to("vip-alerts");

A KStream-KTable join is local to each instance, so it requires co-partitioning: both topics keyed by the same key (here the user id), with the same partition count and partitioner. If orders is keyed by order id, re-key first with selectKey(...), which makes Streams write a repartition topic — or use a GlobalKTable for small lookup data.

What is the difference between KStream and KTable? What is a changelog topic?
Hard▼

KStream — unbounded sequence of events. Each record is an independent event. Reading the stream replays all events.

KTable — materialised view of the latest value per key. Like a database table updated by a stream. A new message with key K replaces the previous K entry. A null value = tombstone (delete).

GlobalKTable — like KTable but fully replicated on every application instance (useful for lookup tables like products or currencies — avoids co-partitioning requirement for joins).

Changelog topic — Kafka Streams backs every state store with a changelog topic (usually <app-id>-<store-name>-changelog). When an instance restarts, it restores state by replaying this topic into its local RocksDB store — no external DB needed.

💡
Late data
Declare the grace period explicitly: TimeWindows.ofSizeAndGrace(Duration.ofHours(1), Duration.ofMinutes(5)) accepts events up to 5 minutes late (by event time). Events later than that are dropped and counted in the dropped-records metric. Since Kafka 3.0 the old .grace() method and the implicit 24-hour default grace are deprecated; use ofSizeAndGrace() or ofSizeWithNoGrace(). Window results are emitted as updates; use suppress(untilWindowCloses(...)) if downstream needs one final value per window.

A consumer group's lag is constantly growing. How do you diagnose and fix it?
Hard▼

Diagnosis steps:

  1. Check lag per partition: is lag even or concentrated on one partition? → hot partition or slow consumer
  2. Check consumer CPU/memory: is the consumer process under-resourced?
  3. Check processing time per record: slow DB query, HTTP call, or lock contention?
  4. Check rebalance events: frequent rebalances reset lag measurement and waste time
  5. Check producer throughput: sudden spike in messages?

Fixes ranked by effort:

  • Add consumer instances (up to partition count) — fastest
  • Optimise processing: batch DB inserts, async I/O, connection pool tuning
  • Increase partitions (then scale consumers accordingly)
  • Offload heavy processing to a thread pool (but manage acks carefully)
  • KEDA auto-scaling: scale consumer pods on lag metric

How do you safely increase the number of partitions on a live production topic?
Hard▼
Bash
# Increase partitions — safe to do live (no data loss)
# WARNING: breaks key-to-partition mapping for existing keys
kafka-topics.sh --bootstrap-server kafka:9092 \
  --alter --topic orders --partitions 12

# No manual step needed: producers and consumers notice the new partitions on
# their next metadata refresh (metadata.max.age.ms, default 5 min), and the
# group rebalances to assign them. Set auto.offset.reset=earliest, or consumers
# may skip records written to new partitions before they were assigned.

Risks and mitigations:

  • Keys that previously went to partition 0 may now go to partition 7 → ordering guarantee per key is broken across the change (old records for a key sit in one partition, new ones in another). If strict ordering matters: pause producers, let consumers drain the lag, then add partitions and resume
  • For Kafka Streams: adding partitions to an input topic breaks co-partitioning with other inputs and invalidates state keyed to the old layout. Streams does not fix this automatically; the safe route is a new topic, or stopping the app and running the application reset tool
  • For compacted topics: existing data isn't redistributed — old data stays in old partitions; only new messages go to new partitions

How do you configure concurrency in Spring Kafka listeners? What is ConcurrentKafkaListenerContainerFactory?
Medium▼
Java
@Bean
public ConcurrentKafkaListenerContainerFactory<String, OrderEvent> batchFactory(
        ConsumerFactory<String, OrderEvent> cf, DefaultErrorHandler errorHandler) {

    var factory = new ConcurrentKafkaListenerContainerFactory<String, OrderEvent>();
    factory.setConsumerFactory(cf);

    // Bean name "batchFactory" is what containerFactory = "batchFactory" refers to below;
    // Boot's auto-configured default factory is named "kafkaListenerContainerFactory".
    // concurrency = number of consumer threads (one KafkaConsumer each) per listener per instance.
    // Threads beyond the partition count (summed over all app instances) sit idle.
    factory.setConcurrency(6);  // 6 threads, each owns 2 partitions (12 total)

    factory.setCommonErrorHandler(errorHandler);

    // Batch listener — process a list of records at once
    factory.setBatchListener(true);

    // AckMode — MANUAL_IMMEDIATE requires Acknowledgment param
    factory.getContainerProperties().setAckMode(AckMode.MANUAL_IMMEDIATE);

    return factory;
}

// Batch listener
@KafkaListener(topics = "orders", containerFactory = "batchFactory")
public void processBatch(List<OrderEvent> orders, Acknowledgment ack) {
    orderRepository.saveAll(orders.stream().map(mapper::toEntity).toList());
    ack.acknowledge();
}

How does the Outbox Pattern integrate with Kafka in a Spring Boot application?
Hard▼
Java
// 1. Outbox entity
@Entity @Table(name = "outbox_events")
@Data
public class OutboxEvent {
    @Id @GeneratedValue private UUID id;
    private String aggregateId, topic, eventType, payload;
    @CreationTimestamp private Instant createdAt;
    private boolean published = false;
}

// 2. Service — writes order + event in same transaction
@Transactional
public Order placeOrder(PlaceOrderRequest req) {
    Order order = orderRepo.save(mapper.toEntity(req));
    outboxRepo.save(new OutboxEvent(order.getId(), "orders", "ORDER_PLACED", toJson(order)));
    return order;
}

// 3. Outbox relay (polling variant) — runs every 500ms
@Scheduled(fixedDelay = 500)
public void publishPendingEvents() throws Exception {
    for (OutboxEvent event : outboxRepo.findTop100ByPublishedFalseOrderByCreatedAt()) {
        // key = aggregate id keeps all events of one order in one partition, in order
        kafkaTemplate.send(event.getTopic(), event.getAggregateId(), event.getPayload())
            .get(10, TimeUnit.SECONDS);   // wait for the broker ack before marking
        outboxRepo.markPublished(event.getId());
    }
}
// A crash between send and markPublished re-sends the event: delivery is
// at-least-once, so consumers must deduplicate by event id.

Kafka-specific points: use the aggregate id as the record key so per-aggregate order survives; wait for the send result before marking a row as published (marking it from an async callback outside the transaction can lose or reorder updates); run one relay instance per outbox (or lock rows with SELECT … FOR UPDATE SKIP LOCKED) so two pods do not publish the same rows. The CDC variant replaces the poller with Debezium plus its Outbox Event Router SMT (io.debezium.transforms.outbox.EventRouter), which routes each outbox row to a topic and uses the aggregate id as the key.

What causes "NotLeaderForPartitionException" and how do you handle it?
Hard▼

Thrown when a producer/consumer sends a request to a broker that is no longer the leader for a partition — happens during leader elections (broker failure, controlled shutdown, rolling restart, partition reassignment). In current clients the error is NotLeaderOrFollowerException (renamed because, since KIP-392, consumers can also fetch from follower replicas); you may still see the old name in logs and older tools.

Handling: Kafka clients (and Spring Kafka) handle this automatically — they fetch updated metadata and retry the request. You should see this as a brief latency spike, not a failure, as long as ISR has at least one replica.

If persistent: check replica.lag.time.max.ms — followers too far behind are removed from ISR, reducing durability. Investigate broker disk I/O or network between brokers.

A message keeps failing and going to DLT. How do you reprocess DLT messages?

# The pipe drops keys and headers unless you print and parse them, so per-key
# ordering and trace/exception headers are lost. Fine for a one-off, not as a process.

# Option 2 (better): a small "DLT replayer" service or admin endpoint that
# consumes orders.DLT with its own group, filters by exception header or time,

# Option 3: prevent most DLT traffic with non-blocking retry topics (below).
# Topic names depend on the back-off settings and Spring Kafka version:
# by default a "-retry" suffix (per attempt or per delay) and "-dlt" for the DLT.
# Note: DeadLetterPublishingRecoverer used with DefaultErrorHandler defaults to ".DLT".
Java
// Spring Kafka 2.7+ non-blocking retry (retry topics), annotation style
@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 2.0))
@KafkaListener(topics = "orders")
public void onOrder(OrderEvent order) { orderService.process(order); }

@DltHandler // same class; called once all attempts are used up
public void onDlt(OrderEvent order, @Header(KafkaHeaders.RECEIVED_TOPIC) String topic) {
    log.error("Gave up on {} from {}", order.getOrderId(), topic);
}

Retry topics break strict per-key ordering: a failed record waits in a retry topic while later records with the same key are processed. If order matters for that key, use blocking retries in the container instead.

What is Kafka MirrorMaker 2? When do you need it?
Hard▼

MirrorMaker 2 (MM2) is a Kafka Connect-based cluster replication tool that continuously copies topics between Kafka clusters. Use cases:

  • Active-Passive DR — replicate from primary cluster to DR cluster; fail over in case of disaster
  • Active-Active — bidirectional replication (tricky — need cycle detection)
  • Data migration — move topics to a new cluster without downtime
  • Cross-region — aggregate regional clusters into a central cluster for analytics

By default (DefaultReplicationPolicy) MM2 prefixes replicated topics with the source cluster alias (primary.orders), which is also how it avoids replication cycles in active-active setups; IdentityReplicationPolicy keeps the names but only suits one-way replication. Offsets differ between clusters, so MM2 writes checkpoints that map consumer group offsets to the target cluster and can sync them (sync.group.offsets.enabled=true). After failover consumers resume close to where they stopped; expect a small number of duplicates, since replication is asynchronous.

What is the "hot partition" problem? How do you detect and fix it?
Hard▼

A hot partition occurs when one partition receives disproportionately more messages than others — usually caused by a skewed key distribution: a few key values carry most of the traffic (e.g. one tenant generates 80% of events), or a low-cardinality key (country, status) is used as the partition key.

Detection: broker metrics are per topic, not per partition, so compare the log-end-offset growth per partition (kafka-consumer-groups.sh --describe, kafka-exporter kafka_topic_partition_current_offset), lag concentrated on one partition, or partition size on disk. One partition growing 10x faster than the others = hot partition.

Fixes:

  • Choose a better key — a higher-cardinality key that still gives the ordering you need (order id instead of customer id, if per-order ordering is enough)
  • Key salting — append a bounded suffix to known hot keys at produce time: tenantId + "-" + (hash(orderId) % 8). The hot key now spreads over up to 8 partitions, so ordering holds only per salted key; consumers that aggregate per tenant must merge the sub-streams
  • Custom partitioner — detect known hot keys and spread them across multiple partitions (same ordering trade-off as salting)
  • Separate topic — route traffic from very large tenants to a dedicated topic with more partitions and its own consumers

Message Queue vs Event Bus vs Broker

Message Queue vs Event Bus vs Message Broker — core differences and when to use each
Medium▼

These three terms are often confused. They represent different patterns for asynchronous communication:

Message Queue — point-to-point channel. Producer sends a message; exactly one consumer receives and processes it. Message is removed after consumption. Classic use: job/task queue (background email sending, image processing). Examples: AWS SQS, RabbitMQ queues.

Event Bus — publish/subscribe within a single process or bounded context. Publishers emit events; multiple in-process listeners react. No persistence. Examples: Spring's ApplicationEventPublisher, Guava EventBus. Useful for decoupling layers within a service.

Message Broker — infrastructure component that routes, filters, and delivers messages between distributed services. Supports both point-to-point and pub/sub. Adds persistence, delivery guarantees, and routing rules. Examples: RabbitMQ (broker with exchanges/queues), Apache Kafka (distributed log broker).

Java — Spring in-process Event Bus
// Publisher — within the same Spring application
@Service
class OrderService {
    private final ApplicationEventPublisher publisher;

    public void placeOrder(Order order) {
        orderRepo.save(order);
        publisher.publishEvent(new OrderPlacedEvent(order)); // in-process, sync
    }
}

// Listener — decoupled but in the same JVM
@Component
class NotificationListener {
    @EventListener
    @Async // make it async to avoid blocking the caller
    public void onOrderPlaced(OrderPlacedEvent event) {
        emailService.sendConfirmation(event.getOrder());
    }
}
ℹ️
When to escalate to a broker
Use an in-process event bus for lightweight decoupling within one service. Escalate to a message broker (Kafka/RabbitMQ) when: consumers are in different services, you need durability (survive restarts), or you need replay/fan-out to multiple independent consumers.

Dead Letter Queue (DLQ) — what is it? Spring Boot implementation with @DltHandler
Medium▼

A Dead Letter Queue is a holding area for messages that failed processing after all retries are exhausted. Instead of silently dropping failed messages or blocking the queue with a poison pill, DLQ captures them for human review, alerting, or replay after fixing the bug.

Without DLQ: a bad message (e.g. malformed JSON, null pointer) causes infinite retry loops, blocking queue processing for all subsequent messages.

With DLQ: after N retries, the message is moved to the DLQ topic. Other messages continue processing. Ops team investigates the DLQ separately.

Java — Spring Kafka DLQ with @DltHandler
// Non-blocking retry + DLT (Dead Letter Topic) pattern
@Configuration
class KafkaRetryConfig {
    @Bean
    public RetryTopicConfiguration retryConfig(KafkaTemplate<?, ?> template) {
        return RetryTopicConfigurationBuilder
            .newInstance()
            .maxAttempts(3)                // 3 attempts total = 1 original + 2 retries
            .exponentialBackoff(1000, 2, 10000) // waits 1s, then 2s (capped at 10s)
            .retryOn(TransientException.class)   // only retry transient errors
            .notRetryOn(ValidationException.class) // send directly to DLT
            .includeTopic("orders")
            .create(template);
        // Creates retry topics with a "-retry" suffix plus a "-dlt" topic;
        // the exact retry topic names depend on the back-off and version
    }
}

@Component
class OrderConsumer {

    @KafkaListener(topics = "orders")
    public void processOrder(String payload) {
        // Throws TransientException on DB timeout — will be retried
        orderService.process(payload);
    }

    @DltHandler
    public void handleDlt(String payload, @Header(KafkaHeaders.RECEIVED_TOPIC) String topic) {
        // Called when message lands in the dead letter topic
        log.error("Message failed all retries. Topic: {}, Payload: {}", topic, payload);
        alertService.notifyOps(payload); // PagerDuty / Slack alert
        deadLetterRepository.save(new DeadLetter(topic, payload, Instant.now()));
    }
}
✅
Non-blocking retry advantage
Spring Kafka's non-blocking retry routes failed messages to separate retry topics instead of blocking the original partition. Other messages in the same partition continue processing while the failed message waits in the retry topic — far better than blocking retry which can cascade into partition lag. The price: per-key ordering is no longer guaranteed, and every retry topic needs partitions, retention and monitoring.

Message delivery guarantees — at-most-once, at-least-once, exactly-once with Kafka examples
Hard▼

Delivery semantics define what happens to a message when a failure occurs between produce and consume:

At-most-once — fire and forget. Message may be lost if producer/broker fails. Offset committed before processing. Use for: metrics, telemetry, non-critical logs. acks=0, auto-commit before processing.

At-least-once — message is delivered at least once but may be duplicated on retry. Offset committed after successful processing. Consumers must be idempotent. Use for: most business events. acks=all, commit after processing.

Exactly-once — the effect of each message is applied once, no duplicates, no loss. Kafka gives this for read-process-write loops that stay inside Kafka (idempotent producer + transactions + read_committed consumers; Kafka Streams with exactly_once_v2). As soon as a side effect leaves Kafka (DB write, HTTP call, email), you are back to at-least-once delivery plus an idempotent consumer. Highest overhead. Use for: stream processing pipelines, financial aggregations inside Kafka.

Java — Kafka exactly-once with transactions
// application.yml — exactly-once semantics
spring:
  kafka:
    producer:
      transaction-id-prefix: tx-  # enables idempotent producer + transactions
      acks: all
    consumer:
      isolation-level: read_committed  # skip records of aborted (and still open) transactions
      enable-auto-commit: false

// Java — consume-transform-produce (Kafka-to-Kafka) in a transaction.
// With transaction-id-prefix set, Boot gives the listener container a
// KafkaTransactionManager: the container starts the transaction, and sends the
// consumed offsets into it (sendOffsetsToTransaction) before committing.
@KafkaListener(topics = "payments")
public void processPayment(String payload) {
    Payment payment = parse(payload);
    kafkaTemplate.send("payment-events", payment.getAccountId(), payment.toEvent());
    // Exception → transaction aborted: output invisible to read_committed readers,
    // offsets not committed, record redelivered.
}

// A DB write here (accountRepository.debit(...)) would NOT be part of the Kafka
// transaction. It is a second resource: if the Kafka commit fails after the DB
// commit, the record is redelivered and the debit runs twice. Make it idempotent:

// Idempotent consumer for at-least-once (the usual answer for DB side effects)
@Transactional // DB transaction
public void processIdempotent(String messageId, Payment payment) {
    // INSERT into processed_messages(id) with a primary key; a duplicate violates it
    if (!processedRepo.insertIfAbsent(messageId)) return;
    accountRepository.debit(payment.getAccountId(), payment.getAmount());
    // dedup row and debit commit together, or neither does
}
⚠️
Exactly-once complexity
Kafka's exactly-once only covers the Kafka-to-Kafka path. Kafka transactions cannot enlist a database, so if your consumer writes to a DB AND produces to Kafka, use an idempotent consumer (dedup table in the same DB transaction) for the DB side and the Outbox pattern for the events it emits. That combination is simpler than any distributed transaction and is what most production systems run.

Pub/Sub vs Point-to-Point messaging patterns with real Java examples
Medium▼

These are the two fundamental messaging patterns. Most message brokers support both.

Point-to-Point (P2P) — one producer sends a message to a queue; exactly one consumer receives and processes it. Other consumers compete for the next message. The message is deleted after processing. Think: task distribution.

Publish/Subscribe (Pub/Sub) — one producer publishes an event to a topic; ALL subscribers receive a copy. Each subscriber processes independently. Think: event broadcasting, change notification.

Java — P2P vs Pub/Sub with Spring
// POINT-TO-POINT with RabbitMQ — competing consumers
// 3 consumers compete — only one gets each message (load balancing)
@RabbitListener(queues = "image-processing")
class ImageProcessor { // instance 1
    @RabbitHandler // a class-level listener needs a handler method
    public void process(ImageUploadedEvent event) {
        imageResizer.resize(event.getImageId()); // this work item is done
    }
}
// instances 2 and 3 are identical — RabbitMQ round-robins messages

// PUBLISH/SUBSCRIBE with Kafka — independent consumer groups
// Both groups receive EVERY order event independently
@KafkaListener(topics = "orders", groupId = "inventory-service")
class InventoryConsumer {
    @KafkaHandler
    public void onOrder(String event) {
        inventory.reserveStock(event); // inventory gets every order
    }
}

@KafkaListener(topics = "orders", groupId = "billing-service")
class BillingConsumer {
    @KafkaHandler
    public void onOrder(String event) {
        billing.chargeCustomer(event); // billing also gets every order
    }
}
// Different groupId = independent subscription = pub/sub
// Same groupId = competing consumers = point-to-point
ℹ️
Kafka's unification of both patterns
Kafka implements both patterns through consumer group IDs. Same groupId across instances = P2P (work queue). Different groupId per service = Pub/Sub (each service sees all events). This makes Kafka exceptionally versatile — you don't choose the pattern at the broker level, you choose it at the consumer configuration level. The limit of Kafka as a work queue: parallelism is capped by the partition count and there is no per-message ack, so one slow message holds up its partition. Kafka 4.0 added share groups ("Queues for Kafka", KIP-932) as early access to address exactly this.
