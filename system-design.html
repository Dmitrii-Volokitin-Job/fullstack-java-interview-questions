Distributed Systems Fundamentals

CAP, consistency, scalability, load balancing

1
Explain the CAP theorem. Give a real example of a CP vs AP system.
Hard▼

The usual "pick 2 of 3" summary is misleading. The precise statement: when a network partition happens, a replicated system must choose between consistency (refuse or fail some requests) and availability (answer every request, possibly with stale data). When there is no partition, you can have both.

PropertyMeaning
Consistency (C)Linearizability: every read gets the most recent write or an error — the system behaves as if there were a single copy of the data
Availability (A)Every request gets a (possibly stale) response — system is always responsive
Partition Tolerance (P)System continues operating despite network failures between nodes — always required in a real distributed system

Since P is mandatory (networks fail), the real choice is CP vs AP:

  • CP systems — HBase, ZooKeeper, etcd: prefer consistency; the minority side of a partition returns errors rather than stale data
  • AP systems — Cassandra, CouchDB, DynamoDB (default settings): prefer availability; may return stale data during partition; eventually consistent

Many databases are tunable, so the label belongs to a configuration, not a product: Cassandra with QUORUM reads and writes behaves much more like CP than with ONE; DynamoDB offers strongly consistent reads per request. PACELC extends CAP with the everyday trade-off: if Partitioned choose A or C, Else choose Latency or Consistency — synchronous replication costs latency even when the network is fine.

💡
Real example
A bank balance query should be CP — better to show an error than a stale (incorrect) balance. A social media "like count" can be AP — showing 2,341 instead of 2,342 for a few seconds is acceptable.

How does a Load Balancer work? Compare L4 vs L7 load balancing.
Medium▼
L4 (Transport Layer)L7 (Application Layer)

SpeedVery fast (no content inspection)Slower (parses HTTP)
Routing decisionsRound-robin, least connections, hashURL path, host header, cookie, content type

ExamplesAWS NLB, HAProxy TCP mode, Kubernetes Service (kube-proxy)Nginx, AWS ALB, Envoy, HAProxy HTTP mode; in Kubernetes the controller behind an Ingress or Gateway API resource

Kubernetes Ingress and Gateway API are APIs, not load balancers: a controller (Envoy Gateway, NGINX, HAProxy, a cloud LB) implements them. Gateway API is the newer, role-oriented and more expressive standard (GA since v1.0, October 2023); the Ingress API is frozen but still supported.

Algorithms: Round Robin (even distribution), Least Connections (route to least busy), IP Hash or consistent hashing (sticky sessions — same client → same server), Weighted (more traffic to powerful servers), and "power of two random choices" (pick 2 at random, send to the less loaded one — what Envoy and many service meshes use for least-request). Health checks remove failed backends; connection draining lets in-flight requests finish during deploys.

4
Design a URL shortener (like bit.ly). Discuss trade-offs.
Hard▼

Requirements clarification: 100M URLs/day created, 10B redirects/day (read-heavy 100:1), URLs expire after 5 years, analytics needed.

High-level design:

  • Shorten API — generate unique 7-char key (Base62: a-z, A-Z, 0-9 = 62^7 = 3.5T combinations)
  • Redirect — look up key in cache → DB, respond with 301 (cached by browser) or 302 (enables analytics on repeat visits)
  • Storage — PostgreSQL for URL mapping; Redis for cache (TTL matching URL expiry)
SQL
-- URL table
CREATE TABLE urls (
  short_key  CHAR(7)     PRIMARY KEY,
  long_url   TEXT        NOT NULL,
  user_id    BIGINT,
  created_at TIMESTAMPTZ DEFAULT now(),
  expires_at TIMESTAMPTZ,
  click_count BIGINT     DEFAULT 0
);

CREATE INDEX idx_expires ON urls(expires_at);  -- for cleanup jobs

Key generation approaches:

  • Hash (MD5/SHA256) + take 7 chars — fast but collision risk; need collision handling
  • Auto-increment ID → Base62 encode — no collisions, but predictable sequential keys
  • Random key generation — check uniqueness in DB/Redis Bloom filter before saving

Scale to 10B redirects/day (~115K/sec): Cache top 20% of URLs in Redis (hot URLs = 80% of traffic). Use CDN for redirect responses. Read replicas for DB.

6
What is database sharding and what are its challenges?
Hard▼

Sharding splits data across multiple databases (shards) based on a shard key. Each shard holds a subset of the data.

Sharding strategies:

  • Range-based — shard by value range (user_id 1-1M → shard 1, etc.). Simple but creates hot spots if one range is accessed more
  • Hash-based — hash(shard_key) % N_shards. Even distribution but hard to add shards (consistent hashing solves this)
  • Directory-based — lookup table maps each key to a shard. Flexible but lookup table is a bottleneck/SPOF

Challenges:

  • Cross-shard queries / joins — very expensive, avoided by denormalisation
  • Cross-shard transactions — 2PC or saga required
  • Rebalancing — adding a shard means moving data
  • Schema changes — must apply to all shards
7
Explain ACID vs BASE. What is eventual consistency?
Medium▼

ACID — Atomicity (all or nothing), Consistency (valid state before and after: constraints and invariants hold), Isolation (concurrent tx don't interfere, to the degree of the isolation level), Durability (committed data survives failures). Guaranteed by most relational DBs. Note: the C in ACID (integrity constraints) is a different idea from the C in CAP (linearizable reads across replicas). Also, most databases default to a weaker isolation level than serializable — PostgreSQL and Oracle use Read Committed, MySQL InnoDB uses Repeatable Read.

BASE — Basically Available, Soft state, Eventually consistent. NoSQL trade-off: sacrifice strong consistency for availability and performance.

Eventual consistency — replicas may temporarily return stale data but will eventually converge to the same value. The window might be milliseconds (Cassandra within a data center) to seconds (cross-region).

ℹ️
ACID in microservices
ACID guarantees end at the service boundary. Cross-service operations can't use database transactions — this is why patterns like Saga and Outbox exist.

8
What is the Outbox Pattern? How does it solve dual-write problems?
Hard▼

Dual-write problem: Writing to a DB and publishing a Kafka message in two separate operations — if the app crashes between them, they go out of sync.

Outbox pattern: Write the event to an outbox table in the same DB transaction as the business data, so both commit or neither does. A separate relay — a poller, or a CDC (Change Data Capture) tool such as Debezium reading the WAL — publishes the rows to the broker.

Guarantee: no lost events, but at-least-once delivery: if the relay crashes after publishing and before recording progress, the event goes out again. Consumers must be idempotent (deduplicate by event id). Order per aggregate is kept by using the aggregate id as the message key.

SQL
-- In a single transaction:
BEGIN;
  INSERT INTO orders (id, user_id, total) VALUES (...);
  INSERT INTO outbox_events (aggregate_id, event_type, payload)
    VALUES ('...', 'ORDER_PLACED', '{"orderId": "...", "userId": "..."}');
COMMIT;
-- The relay publishes the row afterwards (at-least-once)

Caching Strategies

Cache patterns, eviction, Redis, CDN

9
What are the main caching patterns? When do you use Cache-Aside vs Write-Through?
Hard▼
PatternHowGood forRisk
Cache-Aside (Lazy)App checks cache first; on miss, reads DB, populates cacheRead-heavy, tolerate eventual consistencyCache stampede on cold start; stale data
Write-ThroughWrite to cache and DB simultaneouslyData that will be read soon after writeWrite latency doubles; cache fills with unread data
Write-Behind (Write-Back)Write to cache; asynchronously flush to DB laterWrite-heavy workloads (gaming leaderboards)Data loss if cache fails before flush
Read-ThroughCache sits in front of DB; on miss, cache fetches from DBTransparent caching via frameworkComplex cache logic; cold start problem

Cache-aside, read path (green): R1 look in the cache; on a miss R2 read the database and R3 store the result with a TTL. Write path (amber): W1 update the database first, then W2 delete the key so the next read reloads it. Deleting is safer than writing the new value into the cache: two concurrent writers can SET in the opposite order of their DB commits and leave the older value cached for the whole TTL. A small race still exists (a slow reader that missed before W1 can SET the old value after W2), which is why every key keeps a TTL as the upper bound on staleness; a delayed second DEL or CDC-driven invalidation narrows it further.

⚠️
Cache stampede
When many requests hit an expired hot key at the same moment and all go to the DB. Fixes: let only one request rebuild the value with a short-lived lock (SET lock:key token NX PX 3000 — an expiry so a crashed holder cannot block others forever; the old SETNX command has no expiry), probabilistic early refresh before the TTL ends, jitter on TTLs so keys do not expire together, or warming hot keys ahead of time.

What are Redis cache eviction policies? Which would you use for a session store vs a product catalog?
Medium▼
PolicyWhat gets evictedUse case
noeviction (default)Nothing — writes fail with an OOM error once maxmemory is reached; reads still workData that must not disappear silently: sessions, queues, locks
allkeys-lruLeast recently used across all keysGeneral caching — most common choice
allkeys-lfuLeast frequently used — better for skewed (Zipfian) popularityProduct catalog (popular items stay; cold items evicted)
allkeys-randomA random keyUniform access patterns
volatile-lru / volatile-lfu / volatile-randomSame as above, but only among keys that have a TTLCache keys (with TTL) and persistent keys (without) in one instance
volatile-ttlAmong keys with a TTL, the one with the shortest remaining TTLWhen the TTL itself expresses "least valuable"

Redis LRU and LFU are approximated: Redis samples a few keys (maxmemory-samples, default 5) and evicts the best candidate, rather than keeping an exact ordering. Eviction only starts when maxmemory is set; TTL expiry is a separate mechanism that runs regardless.

Session store: sessions should end by their own TTL (a sliding expiry refreshed on each request), not be thrown out under memory pressure — an evicted session is a user logged out at random. Use a dedicated instance with noeviction and enough memory, alert on memory use, or at least volatile-lru if it shares an instance with cache data.
Product catalog: allkeys-lfu — popular products stay in cache; rarely-viewed products evicted.

Messaging & Event Streaming

Kafka, queues, event-driven architecture

11
How does Apache Kafka work? What are Topics, Partitions, Consumer Groups, and Offsets?
Hard▼
  • Topic — named category of messages (like a table); append-only, durable log
  • Partition — unit of parallelism within a topic; messages ordered within a partition; distributed across brokers
  • Offset — each message's position within a partition; each consumer group commits the offset it has processed up to, stored in the internal __consumer_offsets topic
  • Consumer Group — group of consumers sharing a topic's partitions; each partition is read by exactly one consumer in the group, so the useful parallelism is at most the number of partitions
💡
Key trade-off
Kafka ordering is guaranteed only within a partition. To ensure all events for one orderId are ordered, use orderId as the message key — Kafka routes same-key messages to the same partition.

In a system-design interview the point is why you pick Kafka: a durable, replayable log that decouples producers from consumers, lets several independent consumer groups read the same events, and scales by partitions. The price: ordering only per partition, a partition count that is hard to change later, and consumers that must cope with duplicates.

What is at-most-once, at-least-once, and exactly-once delivery? How does Kafka achieve exactly-once?
Hard▼
SemanticsMessages may be?How
At-most-onceLost (never duplicated)Commit offset before processing; fire and forget
At-least-onceDuplicated (never lost)Commit offset only after successful processing; retry on failure
Exactly-onceEffect applied once (the message may still be delivered more than once)Kafka: idempotent producer + transactions + isolation.level=read_committed, for read-process-write between Kafka topics

What Kafka's exactly-once really covers: the idempotent producer removes duplicates caused by producer retries, and a transaction writes the output records and the consumer offsets atomically. That holds only while input and output are both Kafka (Kafka Streams with processing.guarantee=exactly_once_v2 does this for you). As soon as a side effect leaves Kafka — a DB write, an email, an HTTP call — you are back to at-least-once plus an idempotent consumer.

Practically: most systems use at-least-once + idempotent consumers. Make the duplicate check atomic: a unique constraint on the event id inserted in the same DB transaction as the business change. A plain "check, then insert" lets two concurrent deliveries both pass the check.

Java
// Idempotent consumer — processed_events.event_id has a PRIMARY KEY / UNIQUE constraint
@KafkaListener(topics = "orders")
@Transactional   // DB transaction: dedup row and business change commit together
public void process(OrderEvent event) {
    // INSERT ... ON CONFLICT DO NOTHING; returns 0 if the id was already there
    if (processedEventRepo.insertIfAbsent(event.getEventId()) == 0) {
        log.info("Skipping duplicate event {}", event.getEventId());
        return;
    }
    inventoryService.reserve(event);
}

Architecture Patterns

Microservices, SOLID, design patterns

13
What are the SOLID principles? Give a Java example for each.
Medium▼
  • S — Single Responsibility: a class has one reason to change (one actor it serves) — UserService holds rules, UserRepository persistence, UserEmailer notifications
  • O — Open/Closed: add behaviour by adding code, not editing tested code — a new Discount implementation instead of another if branch
  • L — Liskov Substitution: a subtype must keep the parent's contract — a mutable Square extends Rectangle breaks callers that set width and height independently
  • I — Interface Segregation: small, client-specific interfaces — a read-only file implements Readable, not a fat interface with a write() it must throw from
  • D — Dependency Inversion: high-level code depends on an abstraction it owns — AlertService takes a NotificationSender, Spring injects the email or SMS implementation

System-design angle: the same ideas scale up to service boundaries — single responsibility becomes "one service, one business capability", dependency inversion becomes ports and adapters around infrastructure. Applied dogmatically they also produce one-implementation interfaces and needless indirection; use them where change is actually expected.

14
What design patterns do you use regularly? Explain Strategy, Observer, and Decorator with examples.
Medium▼
  • Strategy (behavioural) — swap an algorithm behind one interface, e.g. PaymentStrategy with card and PayPal implementations. In Spring: inject a Map<String, PaymentStrategy> of beans and pick one by key, instead of a switch
  • Observer (behavioural) — publishers notify subscribers without knowing them: ApplicationEventPublisher + @EventListener in-process; use @TransactionalEventListener to react only after the commit. Across services the same idea becomes a message broker
  • Decorator (structural) — wrap an object that has the same interface to add behaviour (caching, logging, retries) without subclassing; servlet filters and Spring AOP proxies work this way
Java
// Decorator: same interface, wraps the inner object
interface TextFormatter { String format(String text); }
class PlainFormatter implements TextFormatter {
    public String format(String t) { return t; }
}
class UpperDecorator implements TextFormatter {
    private final TextFormatter inner;
    UpperDecorator(TextFormatter inner) { this.inner = inner; }
    public String format(String t) { return inner.format(t).toUpperCase(); }
}

💡
Martin Fowler's "MonolithFirst"
In paraphrase: start with a monolith and extract services once you understand the domain boundaries and have a concrete reason (independent deployment for separate teams, very different scaling or reliability needs). A modular monolith — clear modules with enforced boundaries in one deployable — is the usual middle ground.

The deciding factor is usually organisational, not technical: microservices pay off when many teams need to ship independently. Their costs — network failures, eventual consistency, distributed tracing, platform work — arrive on day one.

16
Design a rate limiter. What algorithms would you use?
Hard▼

Algorithms:

  • Fixed Window Counter — count requests in fixed time window (e.g. 100/min). Simple but bursts at window edges (98 at end of minute + 98 at start of next = 196 effectively)
  • Sliding Window Log — log each request timestamp; count within sliding window. Accurate but memory-intensive
  • Token Bucket — bucket holds up to N tokens; each request consumes one; tokens refill at rate R/sec. Allows bursts up to N while holding the average to R. Widely used (API gateways, Bucket4j, the Spring Cloud Gateway Redis limiter)
  • Leaky Bucket — requests enter a fixed-size queue that drains at a constant rate. Smooths bursts completely; when the queue is full, new requests are rejected
  • Sliding Window Counter — keep the current and previous fixed-window counts and weight the previous one by how much of it still overlaps the window. Nearly as accurate as the log at the memory cost of two counters — a common production choice
Java
// Fixed-window counter in Redis — simplest correct distributed limiter
// Lua runs atomically; EXPIRE is set only when the window's key is created,
// so later requests do not keep pushing the window end forward
private static final String RATE_LIMIT_SCRIPT = """
    local count = redis.call('INCR', KEYS[1])
    if count == 1 then
        redis.call('EXPIRE', KEYS[1], ARGV[2])
    end
    if count <= tonumber(ARGV[1]) then
        return 1  -- allowed
    end
    return 0      -- rejected
    """;

public boolean isAllowed(String userId) {
    String key = "rate_limit:" + userId;
    Long result = redisTemplate.execute(
        RedisScript.of(RATE_LIMIT_SCRIPT, Long.class),
        List.of(key),
        "100",   // max requests per window
        "60"    // window in seconds
    );
    return Long.valueOf(1).equals(result);
}

A true token bucket stores two fields per client (tokens left, last refill time) and computes the refill inside the script; don't hand-roll it — use Bucket4j or the gateway's limiter. Design points interviewers look for: return 429 Too Many Requests with a Retry-After header, decide what happens when Redis is down (fail open for availability or fail closed for protection), limit by user or API key rather than IP where possible, and keep a cheap local limiter in front so a Redis outage or a hot key cannot take the service down.

17
How would you design a notification system (email, SMS, push) at scale?
Hard▼

Requirements: 10M notifications/day, multi-channel (email/SMS/push), user preferences, guaranteed delivery, retries.

Architecture:

  1. Notification Service API — receives notification requests, validates, stores in DB
  2. Preference Service — determines which channels a user wants for each notification type
  3. Priority Queue (Kafka topics per priority) — routes to channel-specific workers
  4. Channel Workers — Email Worker (SES/SendGrid), SMS Worker (Twilio), Push Worker (FCM/APNs)
  5. Retry with exponential backoff — failed notifications re-enqueued with delay
  6. Delivery tracking — webhooks from providers update delivery status in DB
💡
Key design decisions
Deduplication: use idempotency keys to prevent duplicate sends on retry. Rate limiting: respect each provider's sending quotas, which differ per account and region — throttle in the channel worker and back off on 429 responses. Templating: store template IDs + variables in DB, render at send time for localisation.
18
What is a CDN? How does it improve performance and what are its limitations?
Easy▼

A CDN (Content Delivery Network) caches static assets at edge servers geographically close to users, reducing latency and origin server load.

How it works: User requests cdn.example.com/logo.png → DNS routes to nearest PoP (Point of Presence) → If cached: serve immediately. If not: fetch from origin, cache at edge, serve.

Good for: Static assets (JS, CSS, images, videos), API responses with Cache-Control headers, geographic distribution.

Limitations:

  • Not suitable for personalised or authenticated content (though edge auth is evolving)
  • Cache invalidation is hard — purges need CDN API calls and take time to propagate; the usual fix is versioned (content-hashed) file names with long Cache-Control: max-age, so you never need to purge
  • Cost at high volume
  • Trust and dependency — the CDN terminates TLS, so it sees your traffic in plaintext; Subresource Integrity (SRI) hashes protect against tampered scripts, and an outage of the CDN takes your site with it (multi-CDN for critical sites)
  • Cache keys and headers must be right — a missing Vary or a cached Set-Cookie can serve one user's response to another

What is the Service Mesh pattern? What does Istio provide that Kubernetes doesn't?
Hard▼

A service mesh puts a proxy in the path of all service-to-service traffic — classically an Envoy sidecar in every Pod (Istio), or per-node proxies in Istio ambient mode — and gives you observability, security and traffic control as infrastructure, without changing application code.

FeatureKubernetes aloneWith Istio
Mutual TLS (mTLS)Not provided; NetworkPolicy restricts by IP/label, no encryption or workload identityAutomatic per-workload identity (SPIFFE certificates) and mTLS
Traffic splittingPlain Services split only by pod count; Gateway API HTTPRoute weights can split at the edgeWeight- and header-based routing between any services (10%/90% canary)
ObservabilityBasic metricsGolden signals per service pair, trace spans
Retries/timeoutsApp codeDeclarative policies in YAML
Fault injectionNot availableInject delays/errors for chaos testing
⚠️
Complexity cost
Every proxy hop adds latency — typically around a millisecond or less at the median, more at the tail and under load; measure it for your own traffic. The bigger costs are memory and CPU for a proxy per Pod (reduced by ambient mode), upgrades of the mesh itself, and a new layer to debug. Adopt a mesh for a concrete need — mTLS everywhere for compliance, uniform traffic policy across many services — not by default.

20
How would you design a system to handle 1 million concurrent WebSocket connections?
Hard▼

Challenge: 1M persistent connections — a platform-thread-per-connection model won't scale (with the common 1MB default stack reservation, 1M threads means about 1TB of reserved address space, plus scheduler overhead).

Solution components:

  1. Non-blocking I/O — Netty/Vert.x or Spring WebFlux with Reactor Netty (event loop, not thread per connection)
  2. Horizontal scaling — 20 WebSocket servers × 50K connections each = 1M. Route with sticky L7 load balancer (same client → same server)
  3. Message fan-out — when server A needs to send to user on server B: publish to Redis Pub/Sub; all servers subscribe; the one holding the connection delivers
  4. Presence tracking — Redis hash map of userId → serverId
  5. Heartbeat + reconnect — client sends ping every 30s; server disconnects on timeout; client auto-reconnects with exponential backoff
  6. OS limits — each connection is a file descriptor and kernel socket buffers: raise ulimit -n / fs.file-max, tune buffer sizes, and make sure the load balancer and any NAT in between can track that many connections (ephemeral ports cap at about 64K per source-IP/destination pair)
  7. Deploys — a restart drops every connection on that node at once; drain gradually and add jitter to client reconnects to avoid a thundering herd
ℹ️
Java 21 alternative
With virtual threads (Project Loom, final in Java 21) you can keep blocking, thread-per-connection code: a million virtual threads are cheap because they are not OS threads, and the JVM parks them during blocking I/O. It removes most of the need for reactive code, but not the memory per connection (buffers, session state) or the OS limits above; check that the WebSocket library actually runs on virtual threads.
