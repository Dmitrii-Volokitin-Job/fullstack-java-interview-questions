What is the difference between a Pod, Deployment, ReplicaSet, and StatefulSet?
Medium▼
ObjectPurposeKey property
PodSmallest schedulable unit; 1+ containers sharing network/storageEphemeral — a bare Pod is not recreated if its node dies or it is deleted (the kubelet only restarts its containers); controllers recreate Pods
ReplicaSetEnsures N copies of a Pod are runningManaged by Deployment; rarely created directly
DeploymentManages ReplicaSets; enables rolling updates and rollbacksStateless workloads — use for web apps, APIs
StatefulSetLike Deployment but Pods get stable identity (pod-0, pod-1)Persistent volume per Pod; ordered startup/shutdown; use for DBs, Kafka

YAML
# Deployment — stateless web service
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: user-service
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # allow 1 extra pod during update
      maxUnavailable: 0   # zero downtime
  template:
    metadata:
      labels:
        app: user-service
    spec:
      containers:
      - name: user-service
        image: myregistry/user-service:1.2.0

What is the difference between Liveness, Readiness, and Startup probes?
Hard▼
ProbeWhat happens on failureUse for
LivenessContainer is restartedDetect deadlock/crash that doesn't exit — "is the app still alive?"
ReadinessPod is removed from Service endpoints (not killed)Signal "not ready for traffic right now" — warming up, or temporarily overloaded. Checked for the whole life of the Pod, not just at start
StartupContainer is restarted if startup takes too longSlow-starting apps (JVM warm-up) — liveness and readiness checks only start after it succeeds
YAML
containers:
- name: api
  image: myapp:latest
  startupProbe:            # gives app up to 30*5=150s to start; liveness waits until it passes
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    failureThreshold: 30
    periodSeconds: 5

  livenessProbe:           # restart if app crashes/deadlocks
    httpGet:
      path: /actuator/health/liveness
      port: 8080
    initialDelaySeconds: 0 # startup probe protects the early window
    periodSeconds: 10
    failureThreshold: 3

  readinessProbe:          # remove from LB until ready
    httpGet:
      path: /actuator/health/readiness
      port: 8080
    periodSeconds: 5
    failureThreshold: 3
💡
Spring Boot integration
Spring Boot Actuator exposes /actuator/health/liveness and /actuator/health/readiness. They are enabled automatically when the app detects it runs on Kubernetes; elsewhere set management.endpoint.health.probes.enabled=true. Keep external dependencies (database, broker) out of the liveness group: a database outage should not make Kubernetes restart every Pod. Put the startup probe on the liveness endpoint, not the full /actuator/health, for the same reason.
3
What happens when you run `kubectl apply -f deployment.yaml`? Walk through the Kubernetes API flow.
Hard▼
  1. kubectl reads the file, fetches the live object and sends a PATCH (or a POST if it does not exist yet) to the API Server. Classic client-side apply computes the diff itself using the last-applied-configuration annotation; kubectl apply --server-side lets the API server merge and track field ownership (managed fields)
  2. The API Server runs the request through authentication (certificates, tokens, OIDC) → authorization (RBAC) → mutating admission (defaults, injected sidecars) → schema validation → validating admission (policies), then persists the object in etcd. Only the API server talks to etcd
  3. The Deployment controller (in kube-controller-manager) is watching Deployments; it sees the new spec and creates or updates a ReplicaSet
  4. The ReplicaSet controller sees fewer Pods than desired and creates Pod objects — with no node assigned yet
  5. The Scheduler watches for Pods without a node, filters and scores nodes (resources, affinity, taints, topology spread) and writes the binding back to the API server
  6. The kubelet on that node sees a Pod bound to it and asks the container runtime via CRI (containerd or CRI-O; dockershim was removed in 1.24) to pull the image and start containers; CNI sets up the Pod network and CSI attaches volumes
  7. kubelet reports status back; once the readiness probe passes, the Pod's IP is added to the Service's EndpointSlices and kube-proxy (or the CNI) starts sending traffic to it

The diagram shows the key property: components never call each other. Each one watches the API server for the objects it cares about and writes its result back; the next component reacts to that write. That is why a crashed scheduler or controller simply resumes from the stored state when it comes back.

💡
Key interview insight
Everything in K8s is a reconciliation loop (controller pattern): watch desired state → compare with actual → take action to converge. This is the fundamental design philosophy of Kubernetes.
4
How do rolling deployments work? How do you do a rollback?
Easy▼

A rolling update gradually replaces old Pods with new ones, controlled by maxSurge (extra Pods allowed during update) and maxUnavailable (how many Pods can be down). With maxUnavailable: 0 you get zero-downtime deployments.

Bash
# Update image — triggers rolling update
kubectl set image deployment/user-service user-service=myregistry/user-service:1.3.0

# Watch rollout progress
kubectl rollout status deployment/user-service

# View rollout history
kubectl rollout history deployment/user-service

# Rollback to previous version
kubectl rollout undo deployment/user-service

# Rollback to specific revision
kubectl rollout undo deployment/user-service --to-revision=2

# Pause a rollout mid-way (inspect the new Pods before continuing)
kubectl rollout pause deployment/user-service
kubectl rollout resume deployment/user-service

A rollback simply scales an older ReplicaSet back up; Deployments keep revisionHistoryLimit old ReplicaSets (default 10). Rollback only reverts the Pod template — not ConfigMaps, Secrets or database migrations — so schema changes must stay backward compatible (expand, then contract). Zero downtime also needs a readiness probe and graceful shutdown (server.shutdown=graceful, a preStop delay) so old Pods finish in-flight requests after they leave the endpoints.

Production pattern
Use ClusterIP for everything internal. How does Kubernetes Ingress work? What is an IngressClass?
Medium▼

Ingress is an API object that defines HTTP routing rules (host, path, TLS). It does nothing by itself: an Ingress controller (Traefik, HAProxy, a cloud controller such as AWS Load Balancer Controller) watches Ingress objects and programs the actual reverse proxy or load balancer.

An IngressClass names a controller. A cluster can run several controllers (say, a public and an internal one); each Ingress picks one with spec.ingressClassName, and one IngressClass can be marked as the default for Ingresses that name none. Anything beyond host/path/TLS — rewrites, timeouts, auth — is a controller-specific annotation, which is the main weakness Gateway API fixes.

YAML
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod  # cert-manager issues the TLS cert
    # controller-specific annotations (rewrites, timeouts) would go here
spec:
  ingressClassName: traefik      # which controller handles this
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls          # cert-manager populates this Secret
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /api/users
        pathType: Prefix
        backend:
          service:
            name: user-service
            port: { number: 80 }
      - path: /api/orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port: { number: 80 }

The same routing with Gateway API: the platform team owns the Gateway (listeners, TLS), and each app team attaches its own HTTPRoute. Weights, header matches and rewrites are portable fields instead of annotations.

YAML
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-routes
spec:
  parentRefs:
  - name: public-gateway         # Gateway owned by the platform team
  hostnames: [api.example.com]
  rules:
  - matches:
    - path: { type: PathPrefix, value: /api/users }
    backendRefs:
    - name: user-service
      port: 80
  - matches:
    - path: { type: PathPrefix, value: /api/orders }
    backendRefs:
    - name: order-service        # 90/10 canary split, no annotations needed
      port: 80
      weight: 90
    - name: order-service-canary
      port: 80
      weight: 10
7
How does Kubernetes DNS work? How do services communicate by name?
Easy▼

CoreDNS runs as a Deployment in the cluster and serves DNS for all Pods. Every Service gets a DNS entry:

<service-name>.<namespace>.svc.cluster.local

Bash
# Full DNS name (always works across namespaces)
http://user-service.production.svc.cluster.local:8080/api/users

# Short name works within the SAME namespace
http://user-service:8080/api/users

# From order-service in 'staging' namespace calling user-service in 'production'
http://user-service.production:8080                    # short form, resolved via search domains
http://user-service.production.svc.cluster.local:8080  # fully qualified

# Verify DNS from inside a pod
kubectl exec -it <pod> -- nslookup user-service

How the short name works: the kubelet writes the Pod's /etc/resolv.conf with search domains (<ns>.svc.cluster.local, svc.cluster.local, cluster.local) and options ndots:5. Any name with fewer than five dots is tried against each search domain first, so a lookup of an external name such as api.stripe.com can cost several failed queries before the real one. For hot external calls use a trailing dot (api.stripe.com.) or lower ndots in the Pod's dnsConfig; NodeLocal DNSCache reduces load on CoreDNS. A normal Service name resolves to its ClusterIP; a headless Service resolves to the Pod IPs.

What are Network Policies and how do you implement micro-segmentation?
Hard▼

Network Policies are L3/L4 firewall rules at the Pod level, selected by labels. By default, all Pods can talk to each other. As soon as any policy selects a Pod for a direction (ingress or egress), only traffic allowed by some policy is accepted in that direction — so the usual pattern is a namespace-wide default-deny plus narrow allow rules.

YAML
# Default deny all ingress in a namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}   # selects all pods in namespace
  policyTypes: [Ingress]
---
# Allow order-service to talk to user-service only
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-order-to-user
spec:
  podSelector:
    matchLabels:
      app: user-service
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: order-service
    ports:
    - protocol: TCP
      port: 8080
⚠️
Requires a CNI plugin
Network Policies require a CNI plugin that enforces them — Calico, Cilium, or Antrea (Weave Net, often listed here, is no longer maintained). Flannel alone does NOT enforce NetworkPolicies, and the API server accepts the objects anyway, so an unenforced policy fails silently. If you also default-deny egress, explicitly allow DNS (UDP and TCP port 53 to CoreDNS in kube-system), or every name lookup breaks. Policies are additive: there is no "deny" rule, only allow rules on top of a default deny.

ConfigMaps & Secrets

Configuration management, secret rotation

9
What is the difference between ConfigMap and Secret? How do you inject them into Pods?
Medium▼

ConfigMap — stores non-sensitive config (env vars, config files, feature flags). Stored in plaintext in etcd.

Secret — stores sensitive data (passwords, tokens, certs). Stored base64 encoded (NOT encrypted by default — enable etcd encryption at rest or use external secret manager).

YAML
# ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: INFO
  DB_URL: jdbc:postgresql://postgres:5432/mydb

---
# Secret (base64-encoded values)
apiVersion: v1
kind: Secret
metadata:
  name: app-secrets
type: Opaque
data:
  DB_PASSWORD: cGFzc3dvcmQxMjM=  # echo -n 'password123' | base64

---
# Inject into Pod as env vars
spec:
  containers:
  - name: app
    image: myapp:latest
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secrets
    # Or mount Secret as a file (for certs, kubeconfig)
    volumeMounts:
    - name: tls-certs
      mountPath: /etc/ssl/certs
      readOnly: true
  volumes:
  - name: tls-certs
    secret:
      secretName: app-tls
🚫
Security note
Base64 is encoding, not encryption. For production: enable etcd encryption at rest (ideally with a KMS provider), restrict get/list on Secrets with RBAC (anyone who can create a Pod in the namespace can mount them), and use an external secret manager (AWS Secrets Manager, HashiCorp Vault) with the Secrets Store CSI Driver or External Secrets Operator. Never commit plain Secret manifests to Git — if they must live in Git, encrypt them with Sealed Secrets or SOPS.

Updates: environment variables are read once at container start, so a changed ConfigMap or Secret does not reach envFrom until the Pod restarts. Mounted volumes are refreshed by the kubelet after a delay (its sync period plus cache propagation, typically up to a minute or two), but not when mounted with subPath, and the app still has to re-read the file. A common pattern is to roll the Deployment on change: a checksum annotation in the Helm template, or a controller such as Stakater Reloader. Marking a ConfigMap immutable: true protects against accidental edits and reduces API-server load.

10
How do you manage secrets at scale in Kubernetes? Explain External Secrets Operator.
Hard▼

External Secrets Operator (ESO) pulls secrets from external stores (AWS Secrets Manager, Vault, GCP Secret Manager) and creates Kubernetes Secrets automatically. Secrets are never committed to Git.

YAML
# ExternalSecret — syncs from AWS Secrets Manager
apiVersion: external-secrets.io/v1   # v1beta1 is no longer served since ESO v0.17
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h          # re-read the provider every hour; rotation happens in the provider
  secretStoreRef:
    name: aws-secret-store
    kind: ClusterSecretStore
  target:
    name: db-credentials       # creates this K8s Secret
    creationPolicy: Owner
  data:
  - secretKey: DB_PASSWORD
    remoteRef:
      key: /production/myapp/db
      property: password

Rotation end to end: the secret is rotated in the provider (for example AWS Secrets Manager rotation, or Vault dynamic database credentials with a lease); ESO copies the new value into the Kubernetes Secret on the next refresh; the Pod still needs to pick it up — mounted files update, env vars need a restart (Reloader or a rolling restart). During rotation both the old and new credentials must be valid for a while, or connections fail.

Alternatives: the Secrets Store CSI Driver mounts secrets straight from the provider as files (optionally also syncing a K8s Secret); the Vault Agent Injector adds a sidecar that writes secrets to a shared volume and renews leases. Both avoid storing the value in etcd at all, which ESO does not.

Scaling & Resource Management

HPA, VPA, resource limits, node affinity

11
What is the difference between HPA, VPA, and KEDA? How do you configure HPA?
Hard▼
TypeWhat it scalesTrigger
HPANumber of Pods (horizontal)CPU, memory, custom metrics (Prometheus)
VPACPU/memory requests per Pod (vertical)Historical usage — recommends or auto-applies resource adjustments
KEDAPods (including scale-to-zero)Event-driven: Kafka lag, queue depth, HTTP request rate, cron
Cluster AutoscalerNumber of Nodes in the clusterPods that can't be scheduled due to insufficient capacity
YAML
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: user-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: user-service
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70       # scale up if avg CPU > 70%
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # scale down based on the highest recommendation of the last 5 min (this is the default)

How HPA decides: every 15 seconds it computes desired = ceil(current × currentMetric / target) (with a 10% tolerance). Utilization is measured against the Pod's requests, so HPA on CPU only works when requests are set and realistic. Metrics come from metrics-server (CPU/memory) or a custom/external metrics adapter (Prometheus Adapter, KEDA).

⚠️
Pitfalls
Memory is a poor HPA signal for JVM services: the heap grows to its limit and rarely shrinks after GC, so memory utilization stays high and the HPA scales up but never back down. Prefer CPU, request rate or queue lag (KEDA). Don't let VPA and HPA act on the same metric (both on CPU): VPA raises requests, which lowers utilization, which makes HPA scale in. Use VPA in recommendation mode, or HPA on custom metrics with VPA on resources. KEDA builds on HPA (it creates and drives one) and adds scale-to-zero.

What are resource requests and limits? What happens when a Pod exceeds its memory limit?
Medium▼

Requests — what the scheduler reserves: a Pod only lands on a node whose unreserved capacity covers its requests. CPU requests also set the container's share of CPU under contention.

Limits — the maximum. CPU over the limit is throttled (CFS quota), not killed. Memory over the limit gets the container OOMKilled (exit code 137) and restarted according to its restart policy. Separately, when a node runs short of memory, the kubelet evicts Pods — BestEffort first, then Burstable Pods using more than they requested; Guaranteed Pods (requests = limits) go last.

Common practice: always set memory requests = limits for JVM services (predictable, no eviction surprises); set CPU requests, and either a generous CPU limit or none, because CPU limits cause throttling and latency spikes even when the node is idle.

YAML
resources:
  requests:
    memory: "256Mi"    # scheduler uses this to find a node
    cpu: "250m"        # 250 millicores = 0.25 CPU
  limits:
    memory: "512Mi"    # OOMKilled if exceeded
    cpu: "1000m"       # throttled (not killed) if exceeded
⚠️
JVM tip
Modern JVMs (JDK 10+, and 8u191+) are container-aware and read the cgroup memory limit. The problem is the default: the max heap is only 25% of that limit, which wastes memory. Set -XX:MaxRAMPercentage (commonly 50–75%) and leave the rest for metaspace, thread stacks, code cache, direct buffers and GC structures — set it too high and the process exceeds the limit and is OOMKilled even though the heap is fine. See the JVM-in-containers question in the Docker section below.

What are Taints, Tolerations, and Node Affinity? When do you use them?
Hard▼

Taints — applied to Nodes: "repel all Pods unless they tolerate this taint". Prevents pods from being scheduled on specialist nodes (GPU, high-memory).

Tolerations — applied to Pods: "I can run on nodes with this taint".

Node Affinity — attracts pods to nodes matching certain labels (required or preferred).

You need both for dedicated nodes: a toleration only allows a Pod onto the tainted node, it does not send it there; the affinity does that. Effects: NoSchedule (new Pods stay away), PreferNoSchedule (soft), NoExecute (also evicts running Pods without a toleration — used by node-failure taints). "IgnoredDuringExecution" means a label change does not evict Pods already running. To spread replicas across nodes or zones use podAntiAffinity or topologySpreadConstraints.

YAML
# Node taint — only GPU-tolerant pods can run here
kubectl taint nodes gpu-node-1 hardware=gpu:NoSchedule

# Pod toleration + affinity: MUST run on a GPU node, PREFERS zone eu-west-1a
spec:
  tolerations:
  - key: hardware
    operator: Equal
    value: gpu
    effect: NoSchedule

  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: hardware
            operator: In
            values: [gpu]
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 1
        preference:
          matchExpressions:
          - key: zone
            operator: In
            values: [eu-west-1a]

Helm

Charts, values, lifecycle, best practices

14
What is Helm and how does it work? Explain Charts, Releases, and Values.
Medium▼

Helm is the package manager for Kubernetes. A Chart is a templated package of K8s manifests. A Release is an installed instance of a chart. Values are configuration overrides that parameterise the templates.

Bash
# Install a chart from a repository
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace

# Charts are also distributed as OCI artifacts (Helm 3.8+)
helm install my-app oci://registry.example.com/charts/my-app --version 1.2.0

# Install your own chart with values file
helm install user-service ./charts/user-service \
  -f values/production.yaml \
  --namespace production

# Upgrade a release
helm upgrade user-service ./charts/user-service \
  --set image.tag=1.4.0 -f values/production.yaml

# Rollback: without a revision number Helm goes to the previous one;
# "1" means revision 1, not "one step back"
helm history user-service
helm rollback user-service
helm rollback user-service 3

# Render templates locally without a cluster
helm template user-service ./charts/user-service -f values/production.yaml
# Preview an upgrade against the cluster (helm-diff plugin)
helm diff upgrade user-service ./charts/user-service -f values/production.yaml

Helm 3 has no server-side component (Tiller was removed); release state is stored as Secrets in the release's namespace, one per revision. Use --atomic with --wait in CI so a failed upgrade rolls itself back. Values passed with --set end up in the stored release, so don't pass real passwords that way.

YAML
# templates/deployment.yaml — Helm template syntax
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        resources:
          {{- toYaml .Values.resources | nindent 12 }}
        {{- if .Values.env }}
        env:
          {{- range $key, $val := .Values.env }}
          - name: {{ $key }}
            value: {{ $val | quote }}
          {{- end }}
        {{- end }}
15
How do you structure Helm charts for multiple environments (dev/staging/prod)?
Medium▼
Bash
# Chart structure
charts/user-service/
├── Chart.yaml
├── values.yaml          # defaults (dev-safe)
├── values/
│   ├── staging.yaml     # staging overrides
│   └── production.yaml  # production overrides (more replicas, limits)
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    ├── configmap.yaml
    └── _helpers.tpl     # named template functions

# values.yaml (defaults)
replicaCount: 1
image:
  repository: myregistry/user-service
  tag: latest
resources:
  limits:
    cpu: 500m
    memory: 256Mi

# production.yaml (overrides)
replicaCount: 3
image:
  tag: 1.4.0              # pinned version, not latest
resources:
  limits:
    cpu: "2"
    memory: 1Gi

Keep one chart and layer values files: helm upgrade -f values.yaml -f values/production.yaml — later files win, so environments only state their differences. Pin image tags (or digests) everywhere, including the defaults: latest makes a rollback or a node re-pulling the image silently change what runs. Keep secrets out of values files (External Secrets, or SOPS via helm-secrets). In GitOps setups the per-environment values usually live in a separate config repo that Argo CD or Flux applies, and promotion is a PR that bumps the tag.

CI/CD & Docker

Pipelines, Docker best practices, GitOps

16
Write a production-ready Dockerfile for a Spring Boot application.
Medium▼
Dockerfile
# Multi-stage build — builder stage uses full JDK, runtime uses JRE only
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /app

# Copy dependency files first (layer cache: only re-runs if pom.xml changes)
COPY pom.xml .
COPY .mvn .mvn
COPY mvnw .
RUN ./mvnw dependency:go-offline -q

COPY src src
RUN ./mvnw package -DskipTests -q   # tests run in CI before the image build

# Extract the jar into layers (Spring Boot 3.3+ "tools" jar mode;
# the older -Djarmode=layertools is deprecated)
RUN cp target/*.jar application.jar \
 && java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# ── Runtime stage ────────────────────────────────────────
FROM eclipse-temurin:21-jre-alpine AS runtime

# Security: non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

WORKDIR /app

# Layers from least to most frequently changed
COPY --from=builder /app/extracted/dependencies/ ./
COPY --from=builder /app/extracted/spring-boot-loader/ ./
COPY --from=builder /app/extracted/snapshot-dependencies/ ./
COPY --from=builder /app/extracted/application/ ./

EXPOSE 8080

# Exec form on ONE line: java runs as PID 1 and receives SIGTERM directly.
# Container support is on by default; only the heap share needs setting.
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "application.jar"]

What changed against older versions of this file you may find online: -XX:+UseContainerSupport is the default since JDK 10 and redundant; -Djava.security.egd=file:/dev/./urandom was a workaround for slow startup on old JDKs and is not needed on modern ones; and a JSON ENTRYPOINT split over several lines without \ continuations is not valid Dockerfile syntax. The extracted application.jar finds its libraries in lib/ next to it, which also makes it ready for Class Data Sharing / AOT cache training to speed up startup.

💡
Layer caching tip
Layered jar + multi-stage build means Docker only rebuilds the application layer when your code changes (a few MB), not the dependencies layer (hundreds of MB). This dramatically speeds up CI builds.
17
Describe a complete CI/CD pipeline for a Java microservice deployed to Kubernetes.
Hard▼

A mature pipeline has these stages:

YAML
# GitHub Actions example
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  IMAGE: registry.example.com/user-service

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    - name: Setup Java 21
      uses: actions/setup-java@v4
      with:
        java-version: '21'
        distribution: 'temurin'
        cache: 'maven'

    - name: Run tests             # unit + integration
      run: ./mvnw verify

    - name: SonarQube analysis    # code quality gate
      run: ./mvnw sonar:sonar -Dsonar.token=${{ secrets.SONAR_TOKEN }}

    - name: Build image
      run: docker build -t "$IMAGE:${{ github.sha }}" .

    - name: Scan image            # fail on HIGH/CRITICAL CVEs; pin the Trivy version in real pipelines
      run: |
        docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
          aquasec/trivy image --exit-code 1 --severity HIGH,CRITICAL "$IMAGE:${{ github.sha }}"

    - name: Log in to registry
      if: github.event_name == 'push'   # PRs build and test, but never push or deploy
      uses: docker/login-action@v3
      with:
        registry: registry.example.com
        username: ${{ secrets.REGISTRY_USER }}
        password: ${{ secrets.REGISTRY_TOKEN }}

    - name: Push image            # immutable tag = commit SHA
      if: github.event_name == 'push'
      run: docker push "$IMAGE:${{ github.sha }}"

  deploy-staging:
    needs: build-and-test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: staging
    steps:
    - uses: actions/checkout@v4   # the chart lives in the repo
    # (cluster credentials step omitted — e.g. OIDC to the cloud provider, then get kubeconfig)
    - name: Helm upgrade staging
      run: |
        helm upgrade --install user-service ./charts/user-service \
          --set image.tag=${{ github.sha }} \
          -f values/staging.yaml \
          --namespace staging --wait --timeout 5m

    - name: Smoke test
      run: curl -f https://staging.api.example.com/actuator/health

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production       # approval comes from the environment's protection rules
    steps:
    - uses: actions/checkout@v4
    - name: Helm upgrade production
      run: |
        helm upgrade --install user-service ./charts/user-service \
          --set image.tag=${{ github.sha }} \
          -f values/production.yaml \
          --namespace production --wait --atomic

Design points worth saying out loud: build the image once and promote the same digest through every environment (never rebuild per environment); tag it with the commit SHA, not latest; keep cluster credentials short-lived (OIDC federation instead of a stored kubeconfig); and run DB migrations as a separate, backward-compatible step. In a GitOps setup the last two jobs are replaced by a commit that bumps the image tag in the config repo, and Argo CD or Flux applies it.

What is GitOps? How do ArgoCD or Flux implement it?
Hard▼

GitOps — Git is the single source of truth for cluster state. Every change goes through a PR; the cluster automatically reconciles toward the Git-declared state. Benefits: audit trail, easy rollback (git revert), self-healing.

ArgoCD watches a Git repo for Kubernetes manifests/Helm charts. When a change is pushed, it applies it to the cluster. If someone manually changes something via kubectl, ArgoCD detects drift and either alerts or auto-syncs back.

Flux does the same with a set of small controllers and CRDs instead of one server with a UI: a GitRepository (or OCI) source, a Kustomization or HelmRelease that applies it, and optional image-automation controllers that commit new image tags back to Git. Argo CD's UI, multi-cluster view and ApplicationSets suit platform teams; Flux is lighter and fully CRD-driven.

The key shift is pull, not push: the agent inside the cluster pulls from Git, so CI no longer needs cluster credentials. Secrets still cannot go into Git in plain form — use Sealed Secrets, SOPS or External Secrets.

YAML
# ArgoCD Application CRD
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: user-service
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/k8s-configs
    targetRevision: main
    path: services/user-service/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true     # delete resources removed from git
      selfHeal: true  # auto-revert manual kubectl changes
    syncOptions:
    - CreateNamespace=true

How do you implement a blue-green or canary deployment in Kubernetes?
Hard▼
StrategyHowRisk
Rolling (default)Gradually replace old pods with newBoth versions run simultaneously during update
Blue-GreenRun both in parallel; switch Service selector from blue to green instantlyDouble resource cost; instant traffic switch (no gradual)
CanarySend small % of traffic to new version; monitor errors; gradually increaseMore complex; needs traffic splitting (Istio, Argo Rollouts)
YAML
# Blue-Green: two deployments, one Service
# Switch by changing Service selector
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  selector:
    app: user-service
    version: blue    # change to 'green' to cut over instantly
  ports:
  - port: 80
    targetPort: 8080

# Canary with Argo Rollouts (weights)
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
      - setWeight: 10    # 10% traffic to new version
      - pause: {duration: 5m}
      - setWeight: 50
      - pause: {duration: 10m}
      - setWeight: 100   # full traffic if no errors
      analysis:
        templates:
        - templateName: error-rate-check

Without a traffic router (a service mesh, a Gateway API plugin, an ingress controller), Argo Rollouts can only approximate weights by replica count — 10% needs at least 10 Pods. The analysis step is what makes canaries worthwhile: it queries Prometheus for error rate and latency and aborts the rollout automatically. Both strategies run two versions against the same database at once, so schema changes must be backward compatible (expand, then contract).

How do you troubleshoot a Pod that is stuck in CrashLoopBackOff or Pending?
Medium▼
Bash
# CrashLoopBackOff — container starts then immediately exits
# Step 1: describe the pod — look at Events section
kubectl describe pod <pod-name> -n <namespace>

# Step 2: read logs from crashed container
kubectl logs <pod-name> --previous     # -p = previous container run
kubectl logs <pod-name> -c <container> --previous

# Step 3: check the exit code and reason (lastState.terminated)
#   137 = SIGKILL, usually OOMKilled; 143 = SIGTERM; 1 = app error
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[*].lastState.terminated}'

# Step 4: exec into the container while it is up, or attach a debug
# container (ephemeral containers, GA since 1.25) — works for distroless
# images without a shell and for containers that crash too fast to exec into
kubectl exec -it <pod-name> -- /bin/sh
kubectl debug -it <pod-name> --image=busybox --target=<container>
kubectl debug <pod-name> -it --copy-to=<pod-name>-debug --container=<container> -- sh  # copy with a shell as the command

# Pending — pod can't be scheduled
# Check events — common causes:
#   Insufficient cpu/memory: nodes don't have enough
#   No nodes match nodeSelector/affinity
#   PersistentVolumeClaim not bound
#   Taint has no matching toleration
kubectl get events -n <namespace> --sort-by='.lastTimestamp'
kubectl describe node <node-name> | grep -A5 Conditions

# ImagePullBackOff — wrong image name/tag, or missing imagePullSecrets
kubectl describe pod <pod-name> | grep -A10 Events

Typical CrashLoopBackOff causes for a Spring Boot service: missing config or Secret key (startup exception in the logs), a liveness probe that fires before the app is up (add a startup probe), OOMKilled because the heap plus non-heap exceeds the limit, or a dependency that is not reachable at startup. The back-off between restarts grows exponentially up to five minutes, so after a fix delete the Pod instead of waiting.

What is a PersistentVolume and PersistentVolumeClaim? Explain the StorageClass.
Medium▼

PersistentVolume (PV) — a piece of storage provisioned by an admin or dynamically. Lifecycle independent of any Pod.

PersistentVolumeClaim (PVC) — a request for storage by a user (size, access mode, StorageClass). K8s binds the PVC to a matching PV.

StorageClass — defines how PVs are dynamically provisioned through a CSI driver (AWS EBS, GCP PD, NFS, etc.), plus the reclaimPolicy (Delete by default for dynamic volumes — deleting the PVC deletes the disk; use Retain for data you cannot lose) and volumeBindingMode. With WaitForFirstConsumer the volume is created only once the Pod is scheduled, in the same zone as the node — with Immediate a zonal disk can end up in a zone where the Pod cannot run.

YAML
# PVC — request 20Gi SSD storage
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
  - ReadWriteOnce       # RWO: one NODE (several Pods on it may share); RWOP: one Pod; RWX: many nodes (NFS, EFS)
  storageClassName: gp3  # AWS EBS gp3 StorageClass
  resources:
    requests:
      storage: 20Gi

# Mount in StatefulSet
volumeClaimTemplates:   # each replica gets its own PVC automatically
- metadata:
    name: data
  spec:
    accessModes: [ReadWriteOnce]
    storageClassName: gp3
    resources:
      requests:
        storage: 20Gi

ReadWriteOncePod (GA since 1.29, CSI volumes only) guarantees a single writer Pod, which ReadWriteOnce does not. PVCs created by volumeClaimTemplates are not deleted when the StatefulSet is scaled down or deleted, unless you set persistentVolumeClaimRetentionPolicy.

What is the difference between a Docker image layer and a container? Explain image security best practices.
Medium▼

An image is a read-only stack of layers (each RUN/COPY/ADD instruction creates a layer). A container is a running image with a writable layer on top.

Security best practices:

  • Use distroless, Alpine or other minimal base images (smaller attack surface; Alpine uses musl libc, which occasionally behaves differently from glibc)
  • Run as non-root user (USER appuser)
  • Don't install dev tools in production images (multi-stage)
  • Use .dockerignore to exclude secrets, .git, test data
  • Pin base image versions (alpine:3.19 not alpine:latest), or a digest for full reproducibility — and rebuild regularly so the pinned base still gets security patches
  • Scan images for CVEs: docker scout cves, Trivy, Snyk
  • Never embed secrets in the image — every layer is readable, and a file deleted in a later layer is still in the earlier one. For build-time secrets use BuildKit RUN --mount=type=secret; at runtime prefer mounted secret files over environment variables, which leak more easily (crash dumps, /proc, logs that print the environment)
  • Read-only root filesystem: securityContext.readOnlyRootFilesystem: true (mount an emptyDir for /tmp); also allowPrivilegeEscalation: false and drop all Linux capabilities
  • Enforce this at the cluster level with Pod Security Admission (the restricted profile, set per namespace by label) — PodSecurityPolicy was removed in 1.25 — or a policy engine such as Kyverno or OPA Gatekeeper
  • Sign images and generate an SBOM (cosign / Sigstore), and verify signatures at admission

Git branching strategies vs trunk-based development — which do you choose for continuous delivery, and why?
Medium▼
ModelHow it worksFitsCost
GitFlowLong-lived develop and main, plus feature, release and hotfix branchesSoftware shipped in versions that must be maintained side by side (installed products, libraries)Late, painful merges; work waits in branches; slow feedback — a poor fit for a service deployed many times a day
GitHub flowOne main; short feature branches merged by pull request, then deployedMost web services and teams using PR reviewFine while branches live a day or two; degrades into GitFlow-like merge pain when they live for weeks
Trunk-basedEveryone integrates into main at least daily, directly or through very short-lived branches; main is always releasableContinuous delivery / deploymentNeeds fast, trustworthy CI, good automated tests and a way to hide unfinished work

Why trunk-based wins for CD: the cost of a merge grows with the time two lines of work stay apart, so integrating small changes often keeps every merge trivial and every build a real candidate for production. The DORA research (summarised in the book Accelerate) associates trunk-based development — few active branches, merged at least daily, no code freezes — with higher delivery performance.

What makes it safe:

  • Feature flags separate deploy from release: unfinished code ships switched off. Flags are debt — give each an owner and remove it once it is fully on
  • Branch by abstraction for large refactorings: introduce an interface, move callers over step by step, delete the old implementation — no long-lived branch
  • Fast CI on every commit (minutes, not an hour) and a culture of fixing a red main immediately
  • Fast reviews — small PRs reviewed within hours, or pair/mob programming instead
💡
Release branches still exist
If you must support a released version, cut a release branch from trunk at release time and never develop on it. Fix bugs on trunk first and cherry-pick the fix to the release branch — the reverse order is how fixes get lost in the next release.

Image builds, layer caching, the JVM in containers

How do multi-stage builds and layer caching work? How do you keep Java image builds fast?
Medium▼

Layer cache: each instruction produces a layer, cached by the instruction plus its inputs — for COPY/ADD, a checksum of the copied files. The first instruction whose cache misses is rebuilt, and so is every instruction after it. Hence the rule: order instructions from least to most frequently changing — base image, OS packages, build-tool files and dependency resolution, then source code last.

Multi-stage build: several FROM stages in one Dockerfile. The builder stage has the JDK, Maven and sources; the final stage starts from a small JRE (or distroless) image and only COPY --from=builders the artifacts. Build tools, sources and caches never reach the shipped image, which is smaller and has fewer CVEs. Stages that the target does not depend on are skipped by BuildKit, and independent stages build in parallel.

Dockerfile
# syntax=docker/dockerfile:1
FROM eclipse-temurin:21-jdk AS builder
WORKDIR /app

# 1. Build files only: this layer is reused until pom.xml changes
COPY .mvn .mvn
COPY mvnw pom.xml ./
# 2. Cache mount: ~/.m2 survives between builds but is NOT stored in a layer
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q dependency:go-offline

# 3. Sources last: a code change only re-runs from here
COPY src src
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q package -DskipTests

FROM eclipse-temurin:21-jre AS runtime
COPY --from=builder /app/target/*.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

This shows the caching idea in its simplest form; the Spring Boot Dockerfile question above adds layered jar extraction, so a code change also produces only a small new image layer to push and pull, not a whole new fat jar.

  • .dockerignore — exclude target/, .git, IDE files. Otherwise any of them changing invalidates the COPY and leaks into the build context
  • CI runners start with an empty cache. Export and import it, for example docker buildx build --cache-to type=registry,ref=registry.example.com/app:buildcache,mode=max --cache-from type=registry,ref=registry.example.com/app:buildcache, or type=gha on GitHub Actions
  • Pin the base image (tag or digest), or the cache — and your build — changes whenever the upstream tag moves
ℹ️
No Dockerfile at all
Jib (Maven/Gradle plugin) builds OCI images without a Docker daemon and already splits dependencies, resources and classes into separate layers. Cloud Native Buildpacks (./mvnw spring-boot:build-image) pick a JRE, apply the memory settings and produce layered images too. Both give reproducible, well-layered images for standard Spring Boot apps; a hand-written Dockerfile is worth it when you need custom OS packages or full control.

How does the JVM behave inside a container? How do you size heap and CPU (MaxRAMPercentage, CPU limits)?
Hard▼

The JVM is container-aware (JDK 10+, backported to 8u191): it reads the cgroup memory and CPU limits instead of the host's values. cgroup v2, the default on current Linux distributions, needs a recent JDK (15+, or an updated 11/8 build). The surprises today come from the defaults, not from missing support.

Memory. The default max heap is only 25% of the container limit (MaxRAMPercentage=25), so a 2Gi container gets a 512MB heap. But the heap is not the whole process: the limit must also cover metaspace, the JIT code cache, one stack per thread, direct and NIO buffers (Netty), GC data structures and native allocations. Raise -XX:MaxRAMPercentage to about 60–75% for containers of 1–2Gi and up, less for small ones, and measure instead of guessing: -XX:NativeMemoryTracking=summary plus jcmd <pid> VM.native_memory summary.

SymptomMeaning
java.lang.OutOfMemoryError: Java heap spaceThe heap is too small for the live data, or there is a leak. The JVM is still running; a heap dump is possible
Pod OOMKilled, exit code 137The whole process exceeded the cgroup limit and the kernel killed it — usually heap share too high or non-heap growth. No heap dump, no Java stack trace

CPU. Runtime.availableProcessors() is derived from the CPU limit (quota ÷ period, rounded up); on current JDKs CPU requests (shares) are ignored for this, so a container with no CPU limit sees every core of the node. That number sizes GC threads, JIT compiler threads, the common ForkJoinPool and Netty event loops, and it drives GC ergonomics: with fewer than 2 CPUs or less than about 1.8GB of memory the JVM does not consider the machine "server class" and silently picks Serial GC. Set -XX:ActiveProcessorCount to override the count and choose the collector explicitly.

CFS throttling: a CPU limit is a quota per 100ms period. A JVM that runs many threads at once — at startup (JIT compilation, class loading) or during GC — can use up the quota early in the period and then stand still until the next one, which shows up as slow startup and p99 latency spikes even when the node is idle. Check container_cpu_cfs_throttled_periods_total; common fixes are a higher CPU limit, or CPU requests with no CPU limit plus ActiveProcessorCount.

YAML
containers:
- name: order-service
  image: registry.example.com/order-service:1.4.0
  resources:
    requests: { cpu: "1", memory: 2Gi }
    limits:   { memory: 2Gi }   # memory request = limit; no CPU limit -> no CFS throttling
  env:
  - name: JAVA_TOOL_OPTIONS     # picked up by the JVM without changing the image
    value: >-
      -XX:MaxRAMPercentage=70
      -XX:ActiveProcessorCount=2
      -XX:+UseG1GC
      -XX:+ExitOnOutOfMemoryError
      -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps

# Verify what the JVM actually sees, inside the container
# java -Xlog:os+container=info -version
# java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount|Use.*GC '
💡
Senior answer in one breath
Set memory request = limit, give the heap 60–75% of it and leave the rest for native memory; avoid tight CPU limits, or match ActiveProcessorCount to what you really get; choose the GC explicitly; exit on OutOfMemoryError so Kubernetes restarts a broken JVM instead of leaving it half-alive; and watch both heap metrics and container memory, because they fail differently. The resource requests and limits question above covers the Kubernetes side.
