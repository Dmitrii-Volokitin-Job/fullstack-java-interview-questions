What are the key features introduced from Java 8 to Java 21 that you use daily?
Medium ▼

Java 8: Lambdas, Streams, Optional, default interface methods, new Date/Time API (LocalDate, etc.).

Java 11: var in lambdas, String methods (isBlank(), strip(), lines()), Files.readString().

Java 8 — Lambdas & Functional Interfaces: explain with examples
Medium ▼

A lambda is a short anonymous function: (parameters) -> body. It can be used wherever the expected type is a functional interface — any interface with exactly one abstract method (SAM = Single Abstract Method). The annotation @FunctionalInterface enforces this at compile time.

Java 8 — Lambda syntax forms
// 1. Full form: parameter types declared, block body
Comparator<String> c1 = (String a, String b) -> {
    return a.compareTo(b);
};

// 2. Inferred types + expression body (most common)
Comparator<String> c2 = (a, b) -> a.compareTo(b);

// 3. Single parameter — parens optional
Predicate<String> isEmpty = s -> s.isEmpty();

// 4. No parameters
Runnable r = () -> System.out.println("running");

Built-in functional interfaces — memorise these four, they appear constantly:

InterfaceMethodTakesReturnsTypical use
Predicate<T>test(T)Tbooleanfilter(), anyMatch()
Function<T,R>apply(T)TRmap(), transform
Consumer<T>accept(T)TvoidforEach(), side effects
Supplier<T>get()—Tlazy init, orElseGet()
BiFunction<T,U,R>apply(T,U)T, URmerge, combine two values
UnaryOperator<T>apply(T)TT (same type)map when type stays same
Java 8 — Method references (shorter than lambdas)
// Instead of: x -> System.out.println(x)
list.forEach(System.out::println);          // instance method on specific object

// Instead of: s -> s.toUpperCase()
list.stream().map(String::toUpperCase);     // instance method on parameter

// Instead of: () -> new ArrayList<>()
Supplier<List> s = ArrayList::new;       // constructor reference

// Instead of: (a, b) -> Integer.compare(a, b)
Comparator<Integer> cmp = Integer::compare; // static method reference

// Practical: sort list of employees by salary then name
employees.sort(
    Comparator.comparingInt(Employee::getSalary)
              .thenComparing(Employee::getName)
);
Java 8 — Variable capture (effectively final rule)
int threshold = 50_000;  // effectively final — never reassigned
Predicate<Employee> highEarner = e -> e.getSalary() > threshold; // ✅ OK

int counter = 0;
list.forEach(e -> counter++); // ❌ compile error: counter is not effectively final

// Fix for mutable state in lambdas: use AtomicInteger or collect to a result
AtomicInteger count = new AtomicInteger();
list.forEach(e -> count.incrementAndGet()); // ✅ object reference is effectively final
💡
Interview angle
Interviewers often ask "what is a functional interface?" — the answer is any interface with exactly one abstract method. It can have multiple default or static methods. Examples: Runnable (run), Callable (call), Comparator (compare), all java.util.function types.

Java 8 — Streams: complete API, Collectors, flatMap, reduce — with examples
Hard ▼

A Stream is a one-time-use pipeline over a data source. Operations are intermediate (lazy, return a new Stream) or terminal (eager, trigger the whole pipeline and produce a result).

Java 8 — Creating streams
// From a collection
list.stream()
list.parallelStream()

// From values
Stream.of("a", "b", "c")

// Infinite stream — generate a value on demand
Stream.generate(Math::random).limit(10)

// Infinite stream — iterate from a seed
Stream.iterate(0, n -> n + 2).limit(5)  // 0, 2, 4, 6, 8

// From a range of ints (IntStream)
IntStream.rangeClosed(1, 10)           // 1..10 inclusive
Java 8 — Intermediate operations (lazy, return Stream)
employees.stream()
  .filter(e -> e.getDept().equals("Engineering"))  // keep matching
  .map(Employee::getSalary)                          // transform each element
  .mapToInt(Integer::intValue)                       // unbox to a primitive IntStream
  .distinct()                                        // remove duplicates
  .sorted()                                          // natural order (or pass Comparator)
  .peek(n -> log.debug("salary: {}", n))           // side effect without consuming
  .limit(10)                                        // take first 10
  .skip(2)                                          // skip first 2
  .sum();                                            // terminal (IntStream)
Java 8 — flatMap: flattening nested collections
// Problem: each Order has a List<OrderItem> — you want all items across all orders
List<Order> orders = getOrders();

// WITHOUT flatMap: Stream<List<OrderItem>> — wrong, need Stream<OrderItem>
orders.stream().map(Order::getItems); // ❌ nested

// WITH flatMap: flattens each List into the stream → Stream<OrderItem>
List<String> allProductNames = orders.stream()
    .flatMap(order -> order.getItems().stream()) // flatten
    .map(OrderItem::getProductName)
    .distinct()
    .sorted()
    .collect(Collectors.toList());
Java 8 — reduce: aggregate to a single value
// Sum all salaries (identity = starting value)
int totalSalary = employees.stream()
    .map(Employee::getSalary)
    .reduce(0, Integer::sum);              // 0 + e1 + e2 + e3 + ...

// Without identity — result is Optional (stream could be empty)
Optional<Integer> max = salaries.stream()
    .reduce(Integer::max);

// For simple aggregations, prefer IntStream methods — cleaner
int total = employees.stream()
    .mapToInt(Employee::getSalary)
    .sum();                                // same as reduce but more readable
double avg = employees.stream()
    .mapToInt(Employee::getSalary)
    .average().orElse(0);
Java 8 — Collectors (the most important ones)
// Group employees by department → Map<String, List<Employee>>
Map<String, List<Employee>> byDept =
    employees.stream()
        .collect(Collectors.groupingBy(Employee::getDepartment));

// Count per department → Map<String, Long>
Map<String, Long> countByDept =
    employees.stream()
        .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.counting()));

// Average salary per department
Map<String, Double> avgByDept =
    employees.stream()
        .collect(Collectors.groupingBy(
            Employee::getDepartment,
            Collectors.averagingInt(Employee::getSalary)));

// Split into two groups: earns > 70k vs not
Map<Boolean, List<Employee>> split =
    employees.stream()
        .collect(Collectors.partitioningBy(e -> e.getSalary() > 70_000));

// Join names as comma-separated string
String names = employees.stream()
    .map(Employee::getName)
    .collect(Collectors.joining(", ", "[", "]"));  // [Alice, Bob, Charlie]

// Collect to unmodifiable map
Map<Long, String> idToName = employees.stream()
    .collect(Collectors.toUnmodifiableMap(Employee::getId, Employee::getName));
🚫
Common mistakes
1. Reusing a stream — streams are single-use; a second terminal operation throws IllegalStateException. 2. Using parallelStream() for I/O work — it uses ForkJoinPool.commonPool which has few threads; starving it blocks other parts of the app. 3. sorted() on an unbounded stream — it must see all elements before producing output, causing OOM.

Java 8 — Date/Time API: LocalDate, ZonedDateTime, Duration, Period — why was it introduced?
Medium ▼

Why the old API was replaced: java.util.Date is mutable (can be changed after creation → threading bugs), confuses months (January = 0 — countless production bugs), has no timezone concept built in cleanly, and has terrible API design. Calendar was even worse. The new java.time API (inspired by Joda-Time) is immutable, thread-safe, and expressive.

Java 8 — java.time core classes
// ── LocalDate: a date only, NO time, NO timezone ──
LocalDate today   = LocalDate.now();
LocalDate birthday = LocalDate.of(1990, Month.MAY, 15);  // Month enum avoids 0-index bug
LocalDate nextWeek = today.plusDays(7);
LocalDate parsed   = LocalDate.parse("2024-06-01");

boolean isBefore = birthday.isBefore(today);               // true
int dayOfYear   = today.getDayOfYear();
DayOfWeek dow    = today.getDayOfWeek();                    // MONDAY, TUESDAY...

// ── LocalTime: a time only, NO date, NO timezone ──
LocalTime now      = LocalTime.now();
LocalTime meeting  = LocalTime.of(14, 30);                 // 14:30:00
LocalTime inAnHour = now.plusHours(1).truncatedTo(ChronoUnit.MINUTES);

// ── LocalDateTime: date + time, still NO timezone ──
LocalDateTime dt  = LocalDateTime.of(today, meeting);
LocalDateTime dt2 = LocalDateTime.now().minusMonths(3);
Java 8 — Timezone-aware types
// ZonedDateTime = LocalDateTime + timezone. Use for user-facing datetimes.
ZoneId vienna   = ZoneId.of("Europe/Vienna");
ZonedDateTime zdt = ZonedDateTime.now(vienna);
ZonedDateTime utc = zdt.withZoneSameInstant(ZoneOffset.UTC);  // convert TZ

// Instant = a point on the UTC timeline (epoch seconds + nanos). Use for DB timestamps, event/record timestamps.
Instant now    = Instant.now();
long epochMs   = now.toEpochMilli();
Instant before = now.minus(5, ChronoUnit.MINUTES);

// Convert Instant ↔ ZonedDateTime
ZonedDateTime from = now.atZone(vienna);
Instant back       = from.toInstant();

Duration twoHours = Duration.ofHours(2);

Database / JPA integration
Hibernate (the JPA provider under Spring Data JPA) maps LocalDate → SQL DATE, LocalDateTime → SQL TIMESTAMP, and in Hibernate 6 Instant → a UTC timestamp column. Always store timestamps as Instant in the DB and convert to the user's timezone in the presentation layer. This avoids DST bugs when servers or databases are in different timezones.

Java 8 — Default & static interface methods: what problem do they solve? What is the diamond problem?
Medium ▼

Before Java 8, adding a new method to a published interface was a breaking change — every class implementing it would fail to compile. default methods solve this: they provide an implementation directly in the interface, so existing implementors inherit it without any changes.

Java 8 — Default methods
interface Greeter {
    String getName();       // abstract — must implement

    default String greet() {          // default — inheritors get this for free
        return "Hello, " + getName();
    }

    static Greeter formal(String name) {   // static — called on the interface itself
        return () -> "Dear " + name;
    }
}

class EnglishGreeter implements Greeter {
    public String getName() { return "Alice"; }
    // greet() is inherited — no need to override
}

// Real-world example: Java itself added List.sort(), Map.forEach(), Iterable.forEach()
// without breaking every existing List / Map / Iterable implementation
List<String> names = ...;
names.sort(Comparator.naturalOrder()); // List.sort() is a default method added in Java 8
names.forEach(System.out::println);     // Iterable.forEach() — also default
Java 8 — Diamond problem: what to do when two interfaces conflict
interface A {
    default String hello() { return "Hello from A"; }
}
interface B {
    default String hello() { return "Hello from B"; }
}

class C implements A, B {
    // ❌ Compile error: C inherits unrelated defaults for hello() from A and B
    // ✅ Must override and explicitly resolve:
    public String hello() {
        return A.super.hello();  // explicitly pick A's version
    }
}

// Rule: class implementation always wins over interface default
// If class C extends a concrete class that also has hello() — that wins over both A and B
💡
Compose with default methods
Comparator, Predicate, and Function all have default methods for chaining: Predicate.and(), Predicate.or(), Predicate.negate(), Function.andThen(), Function.compose(). Example: isActive.and(hasEmail).and(isVerified) — much cleaner than nested ifs.

Java 14–17: Records, Pattern Matching instanceof, Sealed Classes, Text Blocks — all with examples
Medium ▼

Records (Java 16 final) — immutable data carriers. A record auto-generates: canonical constructor, accessors (no getX prefix — just name()), equals(), hashCode(), toString(). Replaces 20+ lines of boilerplate DTO/POJO.

Java 16 — Records
// Declaration: that's it — all the boilerplate is generated
record Point(int x, int y) {}

Point p = new Point(3, 4);
p.x();               // 3  (accessor, NOT getX())
p.y();               // 4
p.toString();        // "Point[x=3, y=4]"

// Compact constructor — validates without repeating assignments
record EmailAddress(String value) {
    EmailAddress {    // no parens — this is the compact constructor
        Objects.requireNonNull(value, "email must not be null");
        if (!value.contains("@")) throw new IllegalArgumentException("invalid email");
        value = value.toLowerCase();  // normalise — compact constructor can reassign params
    }
}

// Records CAN: implement interfaces, have static fields/methods, add custom methods
record UserDto(Long id, String name) implements Serializable {
    static UserDto anonymous() { return new UserDto(0L, "anonymous"); }
    boolean isAnonymous() { return id == 0; }
}

// Records CANNOT: extend classes (implicitly final, extend java.lang.Record), be abstract,
// or declare instance fields beyond the components (static fields are allowed).
// Components are final but shallow: a List component is still mutable — copy it with List.copyOf.

Pattern Matching for instanceof (Java 16 final) — eliminates the explicit cast after an instanceof check.

Java 16 — Pattern Matching instanceof
// Old way — repetitive cast
if (obj instanceof String) {
    String s = (String) obj;   // redundant cast
    System.out.println(s.length());
}

// New way — type test + binding variable in one step
if (obj instanceof String s) {
    System.out.println(s.length());  // s is in scope here, already cast
}

// Can combine with conditions in the same if
if (obj instanceof String s && s.length() > 5) {
    System.out.println(s.toUpperCase());
}

// Useful in equals() — eliminates all casts
@Override
public boolean equals(Object o) {
    return o instanceof Point other
        && x == other.x && y == other.y;
}

Text Blocks (Java 15 final) — multiline strings without escape hell.

Java 15 — Text Blocks
// Old: string concatenation nightmare
String json = "{\n" + "  \"name\": \"" + name + "\"\n}";

// New: Text Block — triple quotes, indentation is stripped automatically

        {
          "name": "%s",
          "active": true
        }

String sql = """

Java 17 — Sealed Classes: what problem do they solve and how do they pair with pattern matching?
Medium ▼

Before sealed classes: a class hierarchy was either completely open (any class can extend) or completely closed (final — nothing can extend). There was no middle ground. Sealed classes let you define exactly which classes are permitted to extend or implement a type — giving you a controlled, known hierarchy.

Java 17 — Sealed classes & permits
// Sealed class: only these three classes may extend Shape
public sealed class Shape permits Circle, Rectangle, Triangle {}

// Each permitted subclass must be one of: final, sealed, or non-sealed
public final class Circle    extends Shape { double radius; }
public final class Rectangle extends Shape { double width, height; }
public non-sealed class Triangle extends Shape {} // anyone can extend Triangle
Java 21 — Sealed classes + pattern switch = exhaustiveness
// The compiler knows ALL possible subtypes, so this switch is exhaustive
// No default needed — a missing case is a compile ERROR (non-exhaustive switch)
double area(Shape s) {
    return switch (s) {
        case Circle    c -> Math.PI * c.radius * c.radius;
        case Rectangle r -> r.width * r.height;
        case Triangle  t -> calculateTriangleArea(t);
    }; // if you add a 4th subclass, this switch won't compile → safety
}

// Practical pattern: Result type (Success or Failure — like Rust's Result<T, E>)
public sealed interface Result<T> permits Result.Success, Result.Failure {
    record Success<T>(T value)           implements Result<T> {}
    record Failure<T>(String errorMsg)  implements Result<T> {}
}

// Usage — exhaustive handling
return switch (processPayment(req)) {
    case Result.Success<Order> s -> ResponseEntity.ok(s.value());
    case Result.Failure<Order> f -> ResponseEntity.badRequest().body(f.errorMsg());
};
💡
Why this matters for APIs
Sealed types express a complete, known set of variants — like an enum but with data. They model domain concepts like PaymentMethod (CreditCard | BankTransfer | Crypto), NotificationChannel (Email | SMS | Push), or HTTP response variants. Adding a new subclass forces you to update every switch — the compiler becomes your safety net.

Java 21 — Virtual Threads (Project Loom): how do they work, and when do they outperform platform threads?
Hard ▼

The problem with platform threads: each Java platform thread maps 1:1 to an OS thread. OS threads are expensive (~1MB stack, kernel context switch). A typical JVM can handle ~2000-10000 concurrent platform threads before memory and scheduling overhead kills throughput. Blocking I/O (DB query, HTTP call) wastes the thread — it just sits there waiting.

Virtual threads are JVM-managed, very lightweight threads (~few KB). The JVM multiplexes thousands of virtual threads onto a small pool of platform "carrier" threads. When a virtual thread blocks (I/O, sleep, lock), the JVM unmounts it from the carrier thread — the carrier is immediately free to run another virtual thread. No OS thread is wasted waiting.

Java 21 — Creating and using virtual threads
// 1. Create a single virtual thread
Thread vt = Thread.ofVirtual().name("my-vt").start(() -> {
    System.out.println("Running in: " + Thread.currentThread().isVirtual()); // true
});

// 2. Executor that creates a new virtual thread per task — the main pattern
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = urls.stream()
        .map(url -> executor.submit(() -> httpClient.fetchBody(url)))
        .collect(Collectors.toList());
    // All 10,000 URLs fetched concurrently with just virtual threads
    // Carrier thread pool is typically # of CPU cores (e.g. 8)
}

// 3. Spring Boot 3.2+ — enable with one property (replaces Tomcat thread pool)
// application.yml:
// spring.threads.virtual.enabled: true
// Tomcat/Jetty request handling, @Async and @Scheduled tasks then run on virtual threads.
// Connection pools still cap DB concurrency — size HikariCP for the DB, not for the thread count.
Java 21 — Virtual threads: what to watch out for
// ⚠️ Pinning (JDK 21–23): blocking inside synchronized PREVENTS unmounting — the carrier thread is blocked!
// JDK 24 (JEP 491) removed this for synchronized; native frames and class initializers still pin.
synchronized (this) {
    Thread.sleep(1000);  // carrier thread is PINNED for 1 second — defeats the purpose
}
// Fix on Java 21: replace synchronized with java.util.concurrent.locks.ReentrantLock
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try { Thread.sleep(1000); } finally { lock.unlock(); } // ✅ virtual thread can unmount

// ⚠️ ThreadLocal at scale: millions of virtual threads × ThreadLocal data = memory pressure
// ScopedValue is the designed alternative: preview in Java 21–24, final in Java 25 (JEP 506)
ScopedValue<String> USER_ID = ScopedValue.newInstance();
ScopedValue.where(USER_ID, "user-42")
           .run(() -> processRequest());  // USER_ID visible within this scope only

// ⚠️ CPU-bound work: virtual threads don't help — they don't add more CPU
// For CPU work, use parallel streams or a bounded thread pool

The big picture
Virtual threads make the "one-thread-per-request" model viable at very high concurrency — the same model Spring MVC has always used. This is why reactive programming (WebFlux, Project Reactor) is less necessary with Java 21+. The blocking code stays readable, and scalability comes from the JVM runtime, not from async callbacks.

Java 21 — Pattern Matching for switch and Sequenced Collections
Medium ▼

Pattern Matching for switch (Java 21 final) — extends instanceof pattern matching into switch, making it the clean way to deconstruct sealed hierarchies and heterogeneous data.

Java 21 — Pattern switch with type patterns and guards
// Old style: if-else instanceof chain — verbose and error-prone
static String describe(Object obj) {
    if (obj instanceof Integer i) return "int: " + i;
    else if (obj instanceof String s) return "str: " + s;
    else return "unknown";
}

// New: pattern switch — clean, exhaustive (compiler checks for sealed types)
static String describe(Object obj) {
    return switch (obj) {
        case Integer i when i < 0 -> "negative int: " + i;   // guarded pattern
        case Integer i              -> "positive int: " + i;
        case String  s when s.isEmpty() -> "empty string";
        case String  s              -> "str of length " + s.length();
        case null                    -> "null value";  // explicit null handling
        default                      -> "something else";
    };
}

// With sealed types — no default needed, compiler verifies exhaustiveness
static double area(Shape s) {  // Shape is sealed: Circle | Rectangle | Triangle
    return switch (s) {
        case Circle    c             -> Math.PI * c.radius() * c.radius();
        case Rectangle r             -> r.width() * r.height();
        case Triangle  t when t.isRight() -> 0.5 * t.base() * t.height();
        case Triangle  t             -> calculateTriangleArea(t);
    }; // no default — compiler ensures all Shape subtypes are covered
}

// Record deconstruction pattern (also Java 21) — extract record components in case
if (event instanceof OrderCreated(Long orderId, Long customerId, BigDecimal total)) {
    log.info("Order {} for customer {} worth {}", orderId, customerId, total);
}

Sequenced Collections (Java 21) — a new interface hierarchy that adds getFirst(), getLast(), addFirst(), addLast(), reversed() to List, Deque, SortedSet, LinkedHashSet.

Java 21 — SequencedCollection
List<String> list = new ArrayList<>(List.of("a", "b", "c"));

// Before Java 21 — awkward
list.get(0);                     // first

What states can a Java thread be in, and what moves a thread from one state to another?
Medium ▼

Thread.getState() returns one of six Thread.State values. They are JVM states, not OS scheduler states — which is exactly what you need to know when you read a thread dump.

  • RUNNABLE covers both "running on a CPU" and "ready to run". A thread blocked in native socket I/O also shows as RUNNABLE in a dump — so RUNNABLE does not mean "burning CPU".
  • BLOCKED only means waiting to enter a synchronized monitor. A thread waiting for a ReentrantLock is parked and shows as WAITING (parking to wait for <0x…>).
  • After notify(), the woken thread must re-acquire the monitor, so it goes through BLOCKED if the monitor is still held.
  • TERMINATED is final: calling start() a second time throws IllegalThreadStateException. Calling run() directly runs the code on the current thread — a classic trick question.

What does volatile guarantee under the Java Memory Model, and what does happens-before mean?
Hard ▼

The Java Memory Model (JMM, JLS chapter 17) says when a write in one thread is guaranteed to be visible to a read in another. Without that guarantee, CPUs and the JIT may cache values in registers and reorder instructions. The rule: a read is guaranteed to see a write only if the write happens-before the read. Two conflicting accesses without a happens-before order are a data race.

Main happens-before edges (transitive):

  • Program order: each action in a thread happens-before the next action in that thread.
  • Monitor: unlock of a monitor/lock → every later lock of the same monitor/lock.
  • volatile: a write to a volatile field → every later read of that field.
  • Thread.start() → every action of the started thread; every action of a thread → another thread's successful return from join().
  • java.util.concurrent: putting into a concurrent collection / submitting to an executor → the actions after the take / in the task; a task's actions → Future.get() returning.
  • final fields: values set in the constructor are visible to any thread that sees the object, provided this did not escape during construction.

volatile gives visibility and ordering (no reordering of earlier writes after a volatile write, or later reads before a volatile read) and atomic reads/writes of long/double. It does not make compound actions atomic: count++ on a volatile is still read-modify-write and loses updates.

Java
// 1. Stop flag — the classic correct use of volatile
private volatile boolean running = true;
void loop() { while (running) { work(); } }   // without volatile the JIT may hoist the read → never stops
void stop() { running = false; }

// 2. Safe publication: everything written BEFORE the volatile write is visible after the read
private Config config;               // plain field
private volatile boolean ready;
// writer:  config = load(); ready = true;
// reader:  if (ready) use(config);   // guaranteed to see the loaded config

// 3. Double-checked locking needs volatile, or another thread can see a half-constructed object
private static volatile Service instance;
static Service get() {
    Service s = instance;
    if (s == null) {
        synchronized (Service.class) {
            s = instance;
            if (s == null) instance = s = new Service();
        }
    }
    return s;
}
// Simpler and lazy: the holder idiom — class initialisation is thread-safe by the JLS
private static class Holder { static final Service INSTANCE = new Service(); }
Interview trap: "volatile makes it thread-safe" is wrong for counters and check-then-act. Use AtomicLong/LongAdder or a lock for those; use volatile for flags and for publishing an immutable object.

How do you choose an ExecutorService and size its thread pool?
Hard ▼

Know what the Executors factories hide: newFixedThreadPool and newSingleThreadExecutor use an unbounded LinkedBlockingQueue — under overload the queue grows until the heap is gone. newCachedThreadPool has an unbounded thread count. In production, build a ThreadPoolExecutor with a bounded queue, a rejection policy and named threads.

How ThreadPoolExecutor grows (a favourite trap): below corePoolSize it starts a new thread; once at core size it queues; only when the queue is full does it add threads up to maximumPoolSize; when that is also full, the RejectedExecutionHandler runs. With an unbounded queue, maximumPoolSize is never reached.

Java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    16, 32,                                   // core, max
    60, TimeUnit.SECONDS,                       // idle time before extra threads die
    new ArrayBlockingQueue<>(500),            // BOUNDED queue
    Thread.ofPlatform().name("pricing-", 0).factory(), // named threads = readable dumps (Java 21)
    new ThreadPoolExecutor.CallerRunsPolicy()); // back-pressure: the submitter does the work

// Blocking I/O on Java 21+: one virtual thread per task — never pool virtual threads
try (var vexec = Executors.newVirtualThreadPerTaskExecutor()) {   // ExecutorService is AutoCloseable since 19
    urls.forEach(u -> vexec.submit(() -> fetch(u)));
}   // close() waits for all tasks
// Limit concurrency to a downstream with a Semaphore, not with a small pool

Sizing (Goetz, Java Concurrency in Practice):

  • CPU-bound work: about the number of cores (Runtime.availableProcessors(), which respects container CPU limits), maybe +1.
  • Blocking work: threads ≈ cores × target CPU utilisation × (1 + wait time / compute time). Example: 8 cores, tasks wait 90 ms and compute 10 ms → 8 × 1 × (1 + 9) = 80.
  • Cross-check with Little's law: concurrent requests = throughput × latency. 200 req/s × 0.25 s = 50 in flight.
  • The real limit is usually a downstream resource — a pool of 200 threads in front of a 10-connection DB pool just moves the queue. Use separate pools per dependency (bulkhead) so one slow service can't starve the rest.
Common mistakes: blocking I/O in ForkJoinPool.commonPool() (it is shared by parallel streams and the default async CompletableFuture stages); tasks that wait for other tasks in the same bounded pool (thread-starvation deadlock); forgetting shutdown() + awaitTermination() on application stop.

Pitfalls a senior names:

  • *Async methods without an executor run on ForkJoinPool.commonPool() — sized for CPU work, shared JVM-wide. Pass your own executor for blocking calls.
  • Non-async stages (thenApply) run on whichever thread completed the previous stage — or on the caller if it was already complete. Don't assume a thread.
  • Exceptions are swallowed unless some stage handles them or someone calls join()/get(). join() throws unchecked CompletionException, get() checked ExecutionException.
  • cancel(true) does not interrupt the running task; it only completes the future.
  • ThreadLocal context (MDC trace ids, SecurityContext, transactions) does not follow the task to another thread — wrap the executor (e.g. DelegatingSecurityContextExecutor, Micrometer context propagation).
Modern alternative: with virtual threads, plain blocking code inside executor.submit() is often clearer than a chain of stages. StructuredTaskScope (structured concurrency — cancels sibling tasks when one fails) is still a preview API as of Java 25.

How does ConcurrentHashMap achieve thread safety in Java 8+, and which operations are still not atomic?
Hard ▼

Java 7 used segments — 16 sub-tables by default, each guarded by its own lock. Java 8 rewrote it: one table of bins, like HashMap, with locking per bin:

  • Reads are lock-free — node values and links are read with volatile semantics, so get() never blocks.
  • Insert into an empty bin uses a single CAS — no lock at all.
  • Insert into a non-empty bin locks (synchronized) only the first node of that bin; writers to other bins proceed in parallel.
  • Long bins become red-black trees, as in HashMap.
  • Resize is cooperative: moved bins are marked with a forwarding node, and threads that hit one help transfer bins instead of waiting.
  • size() sums a base counter plus striped counter cells (the LongAdder idea), so it's an estimate while updates are in flight. mappingCount() returns a long.

Guarantees and non-guarantees:

  • No null keys or values — otherwise get() returning null would be ambiguous between "absent" and "mapped to null".
  • Iterators are weakly consistent: they never throw ConcurrentModificationException and may or may not show updates made after they were created.
  • Each method is atomic, but a sequence of calls is not: if (!map.containsKey(k)) map.put(k, v) is a race. Use the atomic compound methods instead.
Java
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();
ConcurrentHashMap<String, Rate> cache = new ConcurrentHashMap<>();

// 🚫 Race: two threads both see "absent" and one count is lost
if (!counts.containsKey(word)) counts.put(word, 1); else counts.put(word, counts.get(word) + 1);

// ✅ Atomic per key
counts.merge(word, 1, Integer::sum);
hits.computeIfAbsent(path, p -> new LongAdder()).increment();
Rate r = cache.computeIfAbsent(currency, c -> loadRate(c)); // loaded once per key

// ⚠️ The mapping function runs while the bin is locked: keep it short,
//    no slow remote calls, and never modify the same map inside it
//    (can throw IllegalStateException "Recursive update" or block other writers)
Compared with alternatives: Collections.synchronizedMap and the legacy Hashtable use one lock for the whole map — every read and write serialises, and iterating needs manual synchronized(map). ConcurrentSkipListMap is the concurrent sorted map.

Java

Account first  = from.id() < to.id() ? from : to;
Account second = first == from ? to : from;
synchronized (first) { synchronized (second) { move(from, to, amount); } }

How do atomic classes and compare-and-swap (CAS) work, and when is LongAdder better than AtomicLong?
Medium ▼

CAS is a single CPU instruction (e.g. lock cmpxchg on x86): "set the value to new only if it is still expected; tell me whether it worked". Atomic classes build optimistic, lock-free updates on it: read → compute → CAS → retry if another thread changed the value in between. No thread is ever blocked holding a lock, so there is no deadlock and no context switch.

Java
AtomicLong counter = new AtomicLong();
counter.incrementAndGet();                         // atomic count++

// What updateAndGet does internally — a CAS retry loop
long prev, next;
do {
    prev = counter.get();
    next = Math.max(prev, observed);
} while (!counter.compareAndSet(prev, next));

// The function may run several times under contention → it must be side-effect free
counter.updateAndGet(v -> Math.max(v, observed));

// Write-heavy counters (metrics, hit counts): LongAdder
LongAdder requests = new LongAdder();
requests.increment();                              // threads update different cells
long total = requests.sum();                       // adds the cells on read
  • Contention: with many threads hammering one AtomicLong, most CAS attempts fail and retry, and the cache line bounces between cores. LongAdder spreads updates over several cells and adds them on sum() — much higher write throughput, more memory, and sum() is not an atomic snapshot. Use AtomicLong when you need the exact current value or compareAndSet (IDs, sequence numbers).
  • ABA problem: the value goes A → B → A and a CAS that expected A still succeeds. It matters for lock-free structures that reuse nodes; AtomicStampedReference adds a version stamp.
  • Low level: VarHandle (Java 9) gives CAS and memory-ordering modes on ordinary fields and replaced most uses of sun.misc.Unsafe.

What memory areas does the JVM use — heap generations, Metaspace, thread stacks — and which OutOfMemoryError belongs to each?
Medium ▼
  • Heap — all objects and arrays (and, since Java 7, the interned-String pool). New objects go into Eden, usually through a per-thread TLAB (thread-local allocation buffer — allocation is a pointer bump, no locking). Objects that survive a minor GC are copied between the survivor spaces and age; after the tenuring threshold (max 15) they are promoted to the old generation. In G1 and generational ZGC the generations are sets of regions rather than fixed contiguous blocks, and G1 puts objects of half a region or more straight into "humongous" regions.
  • Metaspace (Java 8+, replaced PermGen) — class metadata in native memory. Unbounded by default; cap it with -XX:MaxMetaspaceSize. It grows with class-loader leaks (redeploys, runaway dynamic proxies or generated classes).
  • Thread stacks — one per platform thread, a frame per method call with local primitives and references (objects themselves are on the heap). Size via -Xss (commonly 1 MB on 64-bit Linux). A virtual thread's stack lives on the heap as stack-chunk objects while it is unmounted — that's why millions of them are cheap.
  • Code cache holds JIT-compiled machine code; direct buffers (ByteBuffer.allocateDirect, Netty) are off-heap and capped by -XX:MaxDirectMemorySize.

How does class loading work — the class-loader hierarchy, parent delegation, and the cases where delegation is bypassed?
Medium ▼

Phases: loading (find the bytes, create the Class) → linking (verify bytecode, prepare static fields with default values, resolve symbolic references) → initialisation (run static initialisers, once, on first active use, thread-safe — which is why the lazy holder idiom works).

Loader hierarchy (Java 9+):

  • Bootstrap — built into the JVM; loads core modules such as java.base. Shows as null from getClassLoader().
  • Platform (was "Extension" before Java 9) — other Java SE modules such as java.sql.
  • Application / System — your class path and module path.
  • Custom loaders — app servers, plug-in systems, Spring Boot's executable-jar launcher (reads nested jars), DevTools' restart loader.

Parent delegation: a loader first asks its parent and only defines the class itself if the parent can't. That stops an application from replacing java.lang.String and keeps one definition of each core class.

A class's identity is its name plus its defining loader. The same com.acme.User loaded by two loaders gives two different types — hence the confusing ClassCastException: com.acme.User cannot be cast to com.acme.User (classic with DevTools restart or a library loaded twice).

Where delegation is bypassed or inverted:

  • Thread context class loader — SPIs (ServiceLoader, JDBC drivers, JNDI) live in a parent loader but must load implementation classes from the application, so they use Thread.currentThread().getContextClassLoader().
  • Servlet containers — Tomcat's web-app loader looks in WEB-INF/classes and WEB-INF/lib before its parent (except for Java SE classes), so each app can ship its own library versions.

What do the JIT compiler and escape analysis do, and why do they make naive micro-benchmarks lie?
Hard ▼

HotSpot starts by interpreting bytecode and profiling it. Methods and loops that get hot are compiled by tiered compilation (default since Java 8): C1 compiles quickly with light optimisation and collects more profile data; the hottest code is recompiled by C2 with aggressive, profile-guided optimisation.

  • Inlining — the most important optimisation: it copies small hot callees into the caller and enables all the others.
  • Speculative optimisation — if a call site has only ever seen one implementation, C2 devirtualises and inlines it. When the assumption breaks (a new class is loaded), the code is deoptimised back to the interpreter and recompiled later.
  • Loop unrolling, range-check elimination, dead-code elimination, constant folding, and intrinsics (hand-written machine code for e.g. System.arraycopy, String.equals, crypto).

Escape analysis asks whether an object can be seen outside the method/thread that created it. If it can't:

  • Scalar replacement — the object is never allocated; its fields live in registers or on the stack. (HotSpot does this instead of real "stack allocation".)
  • Lock elision — synchronized on an object no other thread can see is removed.
Java
double length(double x, double y) {
    Point p = new Point(x, y);     // p never escapes this method
    return Math.sqrt(p.x() * p.x() + p.y() * p.y());
}   // after C2 + escape analysis: no allocation, x and y stay in registers

Why naive benchmarks lie: the first iterations run interpreted (no warm-up), a loop whose result is never used is removed as dead code, constant inputs are folded at compile time, and on-stack replacement compiles a long loop differently from production code. Use JMH: warm-up iterations, forks, and Blackhole to consume results.

Startup and warm-up are the price of JIT: the first requests after a deploy are slow. Mitigations: class-data sharing (CDS/AppCDS), the JDK 24+ ahead-of-time cache from Project Leyden, GraalVM native image (fast start, but closed-world limits on reflection), or sending warm-up traffic before the pod receives real load.

During a production incident, how do you capture and read thread dumps and heap dumps?
Hard ▼

Start from the symptom, because each points at a different tool: high CPU, high latency with low CPU (threads waiting), or memory that keeps growing. Check metrics first — GC pause time, heap used after GC, thread count, connection-pool usage.

Thread dumps — for hangs, slowness and high CPU

  1. jcmd <pid> Thread.print > dump1.txt — take 3 dumps 5–10 s apart. One dump is a photo; several show what is stuck.
  2. Many threads BLOCKED on the same monitor → lock contention; find the owner thread and see what it's doing.
  3. Many threads WAITING in HikariPool.getConnection → the connection pool is exhausted (slow queries, leaked connections, or pool too small).
  4. The same RUNNABLE stack in every dump → hot loop or slow algorithm. For high CPU: top -H -p <pid> shows the busiest thread id; convert it to hex and match nid=0x… in the dump.
  5. A Found one Java-level deadlock section → deadlock (see the Concurrency section).
  6. Virtual threads: jcmd <pid> Thread.dump_to_file -format=json threads.json.

Heap dumps — for memory growth and OutOfMemoryError

  1. Always run with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps (on a persistent volume in Kubernetes) — you get the evidence from the moment of failure.
  2. Quick look without a full dump: jcmd <pid> GC.class_histogram — counts and bytes per class; compare two histograms over time.
  3. Full dump: jcmd <pid> GC.heap_dump /dumps/app.hprof. It pauses the JVM and the file is about as big as the used heap — take one instance out of the load balancer first.
  4. Analyse in Eclipse MAT (or VisualVM / IntelliJ): Leak Suspects report, the dominator tree sorted by retained size (memory freed if that object went away — shallow size is misleading), then path to GC roots to see which reference keeps it alive.
  5. Leak or just too small? If the heap-after-full-GC baseline keeps rising, it's a leak. If it's flat but high, give it more memory or reduce the working set.

How does HashMap work internally — hashing, buckets, treeification and resizing?
Hard ▼
  1. Hash: put(k, v) takes k.hashCode() and spreads it: h ^ (h >>> 16), so the high bits also affect the index.
  2. Index: the table length n is always a power of two, so (n - 1) & hash is a fast modulo. The table is allocated lazily on the first put; the default capacity is 16.
  3. Collision: entries in the same bin form a linked list; lookup walks it comparing the hash first, then equals.
  4. Treeify: when a bin grows beyond 8 nodes (TREEIFY_THRESHOLD = 8) and the table has at least 64 slots (MIN_TREEIFY_CAPACITY), the bin becomes a red-black tree — worst case O(log n) instead of O(n), which also defends against hash-flooding. If the table is smaller than 64, HashMap resizes instead. A tree bin goes back to a list when a resize split leaves it with 6 or fewer nodes (UNTREEIFY_THRESHOLD = 6).
  5. Resize: when size > capacity × loadFactor (default 0.75: 12 entries for 16 slots), the table doubles. No rehashing is needed: one extra hash bit decides whether each node stays at index i or moves to i + oldCapacity.
Java
// Pre-size when you know the count — avoids repeated resizes
Map<Long, User> byId = HashMap.newHashMap(16);  // Java 19+: room for 16 ENTRIES without resizing
Map<Long, User> old  = new HashMap<>(16);   // ⚠️ argument is CAPACITY: the 13th entry triggers a resize (0.75 × 16 = 12)

// 🚫 Mutating a key after insertion: the entry sits in the bin of the OLD hash
List<String> key = new ArrayList<>(List.of("a"));
map.put(key, 1);
key.add("b");                                 // hashCode changed
map.get(key);                                // null — the entry is now unreachable
  • One null key is allowed (it hashes to bin 0); null values too.
  • Not thread-safe: concurrent puts can lose entries or corrupt the size. In Java 7, a concurrent resize could even build a cycle in a bin and hang get() in an endless loop. Java 8 fixed the cycle, not the race — use ConcurrentHashMap.
  • LinkedHashMap adds a doubly linked list for insertion or access order (LRU caches); TreeMap is a red-black tree sorted by key with O(log n) operations.

equals must be reflexive, symmetric, transitive and consistent, and x.equals(null) must be false. hashCode must return the same value while the fields used by equals don't change, and equal objects must have equal hash codes. The reverse is not required: unequal objects may collide (that only costs performance).

    private final Currency currency;

Explain generics wildcards, the PECS rule and type erasure — what does erasure stop you from doing?
Hard ▼

Generics are invariant: a List<Integer> is not a List<Number> — otherwise you could add a Double to a list of integers. Arrays are covariant (Integer[] is an Object[]), and that is why arrays fail at runtime with ArrayStoreException. Wildcards give controlled flexibility:

  • ? extends T — a producer: you can read elements as T, but you can't add (except null), because the real type might be a subtype.
  • ? super T — a consumer: you can add Ts, but reading gives only Object.
  • PECS (Bloch, Effective Java): Producer Extends, Consumer Super. Use wildcards on parameters of public APIs, never on return types.
Java
// The JDK's own signature: src produces T, dest consumes T
public static <T> void copy(List<? super T> dest, List<? extends T> src)

double sum(Collection<? extends Number> nums) {  // accepts List<Integer>, Set<Double>…
    return nums.stream().mapToDouble(Number::doubleValue).sum();
}
void fill(List<? super Integer> out) { out.add(42); } // accepts List<Number>, List<Object>

// Comparator<? super T>: a Comparator<Animal> can sort a List<Dog>
static <T> void sort(List<T> list, Comparator<? super T> c)

Type erasure: generics exist only at compile time. The compiler checks types, inserts casts and replaces type parameters with their bound (Object or e.g. Comparable); it adds bridge methods so overriding still works. At runtime a List<String> and a List<Integer> are the same ArrayList class. So you cannot:

  • write new T() or new T[10], or use T.class;
  • test x instanceof List<String> (only List<?>);
  • overload process(List<String>) and process(List<Integer>) — same erasure, compile error;
  • use primitives as type arguments (List<int>) — boxing instead;
  • have a static field per parameterisation — static T is not allowed at all.

Workarounds: pass a Class<T> token (repo.find(User.class)), or use a super type token such as Jackson's new TypeReference<List<User>>() {} or Spring's ParameterizedTypeReference. They work because the generic type of a superclass is kept in the class-file signature and readable through reflection.

Heap pollution: raw types and unchecked casts let a List<String> hold an Integer; the failure appears later as a ClassCastException at an innocent-looking line. Don't ignore unchecked warnings; generic varargs need @SafeVarargs only when the method really is safe.

Immutability is shallow: List.of(mutableUser) can't change size, but the user inside can. For a safe DTO or record, defensively copy in the constructor: this.items = List.copyOf(items).

Fail-fast iterators (ArrayList, HashMap, …) remember the collection's modCount and throw ConcurrentModificationException on the next step if the collection was structurally modified by anything other than the iterator itself. It's a best-effort bug detector, not a thread-safety mechanism — and it happens in single-threaded code too.

Java
// 🚫 ConcurrentModificationException — single thread, for-each uses an iterator
for (Order o : orders) {
    if (o.isCancelled()) orders.remove(o);
}

// ✅ Remove through the collection's own API
orders.removeIf(Order::isCancelled);

// ✅ Or through the iterator
for (Iterator<Order> it = orders.iterator(); it.hasNext(); ) {
    if (it.next().isCancelled()) it.remove();
}

"Fail-safe" is the informal name; the Javadoc calls them snapshot or weakly consistent iterators. CopyOnWriteArrayList iterates over a snapshot taken at creation (never throws, never sees later changes; every write copies the array, so use it only for read-mostly data). ConcurrentHashMap and the other java.util.concurrent collections are weakly consistent: they never throw CME and may or may not reflect changes made during iteration.

Explain @Transactional — propagation, isolation levels, and common mistakes.
Hard ▼

Propagation — what happens when a @Transactional method calls another:

PropagationBehaviour
REQUIRED (default)Joins existing tx; creates new if none
REQUIRES_NEWSuspends current tx, always starts fresh tx (commits/rolls back independently)
NESTEDSavepoint within current tx — rollback to savepoint only
SUPPORTSRuns in tx if one exists; non-transactional if not
NOT_SUPPORTEDSuspends tx and runs non-transactionally
NEVERThrows if called inside a tx
MANDATORYRequires existing tx; throws if none
Java
@Transactional  // REQUIRED + Isolation.DEFAULT (= the database's default level)
public void processOrder(Order order) {
    repo.save(order);
    auditService.log(order); // runs in the SAME tx
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logAudit(AuditEntry entry) {
    // Commits independently — audit is saved even if outer tx rolls back
    auditRepo.save(entry);
}

// ⚠️ Self-invocation — @Transactional is IGNORED here
public void outer() {
    this.inner(); // proxy is bypassed — no transaction!
}
@Transactional
public void inner() { ... }

// Fix: inject self, or extract inner() to another bean
🚫
Top Spring mistake
Self-invocation skips the AOP proxy. @Transactional and @Cacheable on private methods are also silently ignored because proxies can't intercept them (since Spring 6.0, class-based proxies do honour protected and package-private methods). Second classic: by default only RuntimeException and Error trigger rollback — a checked exception commits unless you add rollbackFor = Exception.class.

Isolation — Isolation.DEFAULT uses the database's level: READ COMMITTED on PostgreSQL, Oracle and SQL Server, REPEATABLE READ on MySQL InnoDB. READ_UNCOMMITTED allows dirty reads; READ_COMMITTED prevents dirty reads; REPEATABLE_READ also prevents non-repeatable reads; SERIALIZABLE also prevents phantoms, at the cost of locking or serialization failures that the caller must retry. Raise the level per method only where an anomaly matters, or use optimistic locking (@Version) instead.

What is Spring AOP? What is the difference between @Before, @After, @Around, and @AfterThrowing?
Medium ▼

AOP (Aspect-Oriented Programming) extracts cross-cutting concerns (logging, transactions, security) into reusable Aspects. Spring uses proxy-based AOP — it wraps the target bean in a proxy that intercepts calls.

Java
@Aspect @Component
public class LoggingAspect {

    // Runs before the method (can't prevent execution here)
    @Before("execution(* com.app.service.*.*(..))")
    public void before(JoinPoint jp) {
        log.info("Calling: {}", jp.getSignature());
    }

    // Runs ONLY when method throws — can inspect exception
    @AfterThrowing(pointcut = "execution(* com.app.*.*(..))", throwing = "ex")
    public void onError(Exception ex) { log.error("Error", ex); }

    // Most powerful — wraps method, can modify args/return value/suppress exceptions
    @Around("@annotation(com.app.Timed)")
    public Object time(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = pjp.proceed(); // call the actual method
        log.info("Took {}ms", System.currentTimeMillis() - start);
        return result;
    }
}

Walk through the Spring bean lifecycle. How does Spring deal with circular dependencies, and why does Spring Boot reject them by default?
Hard ▼

Lifecycle of a singleton bean:

  1. Bean definitions are read (component scan, @Bean methods, auto-configuration). BeanFactoryPostProcessors may change definitions before any bean exists — e.g. resolving ${…} placeholders.
  2. Instantiation — the constructor runs (constructor injection happens here).
  3. Populate properties — field and setter injection (@Autowired, @Value).
  4. Aware callbacks — BeanNameAware, BeanFactoryAware, ApplicationContextAware.
  5. BeanPostProcessor.postProcessBeforeInitialization — this is where @PostConstruct methods are called.
  6. InitializingBean.afterPropertiesSet(), then a custom initMethod.
  7. BeanPostProcessor.postProcessAfterInitialization — AOP proxies are created here. Other beans receive the proxy, not the raw object; this is why @Transactional doesn't work on calls inside @PostConstruct or through this.
  8. The bean is in use. On context shutdown: @PreDestroy → DisposableBean.destroy() → custom destroyMethod.

Spring does not call destroy callbacks for prototype beans — the caller owns them. For "run when the whole app is ready" logic, use ApplicationReadyEvent, SmartInitializingSingleton or SmartLifecycle, not @PostConstruct.

Java
@Component
class RateCache {
    private final RateClient client;
    RateCache(RateClient client) { this.client = client; } // 2. instantiation + constructor injection

    @PostConstruct void warmUp()  { /* 5. dependencies are set; no proxy yet */ }
    @PreDestroy    void flush()   { /* 8. on context close */ }

    @EventListener(ApplicationReadyEvent.class)
    void startPolling() { /* the whole app is started; proxies and the web server are ready */ }
}

Circular dependencies (A needs B, B needs A):

  • Constructor injection cycle — impossible to satisfy: neither object can be built first. Startup fails with BeanCurrentlyInCreationException.
  • Field/setter injection cycle between singletons — Spring can resolve it: it registers an early reference to A (via a three-level singleton cache) before A's properties are set, and hands that to B. Side effects: B sees a half-initialised A, and if A later gets a proxy, the early reference must be proxied too.
  • Spring Boot 2.6+ sets spring.main.allow-circular-references=false, so even these fail at startup. That's deliberate: a cycle is a design smell — two classes that can't exist without each other are one responsibility split badly.

Fixes, best first: extract the shared logic into a third bean; invert one direction with an application event; inject ObjectProvider<B> and resolve lazily; or put @Lazy on one injection point (injects a proxy that resolves on first call). Re-enabling the property is the last resort.

How does Spring's @Cacheable work, and what are the most common caching pitfalls?
Medium ▼

@EnableCaching turns on a proxy-based aspect — the same mechanism as @Transactional. Before the method runs, the proxy computes a key and looks it up in the named cache; on a hit the method is not called; on a miss it calls the method and stores the result. The storage is pluggable through CacheManager: Caffeine (local), Redis (shared), and others.

Java
@Cacheable(cacheNames = "products", key = "#id", unless = "#result == null")
public ProductDto find(Long id) { ... }

@CachePut(cacheNames = "products", key = "#result.id")   // always runs, refreshes the entry
public ProductDto update(ProductUpdate cmd) { ... }

@CacheEvict(cacheNames = "products", key = "#id")
public void delete(Long id) { ... }

@Cacheable(cacheNames = "rates", sync = true)  // one caller loads a missing key, others wait (per JVM)
public Rate rate(String currency) { ... }

# application.yml — always bound the cache
spring.cache.caffeine.spec: maximumSize=10000,expireAfterWrite=10m
# or, for Redis: spring.cache.redis.time-to-live: 10m

Pitfalls interviewers look for:

  • Self-invocation — this.find(id) from the same class bypasses the proxy, so nothing is cached. Same proxy rules as @Transactional.
  • Key collisions — the default key is built from the method arguments only (SimpleKeyGenerator), not the method name. Two methods sharing a cache name with the same argument overwrite each other's entries. Use one cache per method, or an explicit key.
  • No TTL, no size limit — without a cache library on the classpath, Boot falls back to a plain ConcurrentHashMap cache: no expiry, unbounded memory.
  • Stale data across instances — a local Caffeine cache on 5 pods gives 5 different truths after an update. Use a shared cache (Redis) or short TTLs for data that changes.
  • Returned objects are shared — an in-memory cache hands every caller the same instance. If a caller mutates it, the cache is corrupted. Cache immutable DTOs or records, never JPA entities.
  • Transactions — an evict or put that runs before the transaction commits can cache data that is later rolled back, or let another thread re-cache the old value. Make the cache manager transaction-aware (TransactionAwareCacheManagerProxy, or transactionAware() on RedisCacheManager) so writes happen after commit.
  • Stampede — when a hot key expires, many requests load it at once. sync = true helps within one JVM; across instances you need a distributed lock or early refresh.
  • Serialization — Redis needs a serializer (JSON with type info, or JDK serialization with Serializable); a class change can make old entries unreadable — include a version in the cache name or key.

It changes the JSON shape, so treat it as an API change for existing clients.

How do you build centralized error handling with @RestControllerAdvice and ProblemDetail (RFC 9457)?
Medium ▼

Goal: every error leaves the API in one consistent, machine-readable format, and no stack trace or SQL ever reaches the client. Spring Framework 6 ships ProblemDetail, an implementation of RFC 9457 "Problem Details for HTTP APIs" (which replaced RFC 7807 in 2023), served as application/problem+json.

Java
@RestControllerAdvice
class ApiExceptionHandler extends ResponseEntityExceptionHandler { // covers Spring MVC's own exceptions too

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://api.example.com/problems/order-not-found"));
        pd.setTitle("Order not found");
        pd.setProperty("orderId", ex.orderId());              // extension member
        return pd;
    }

    @ExceptionHandler(Exception.class)                       // last resort
    ProblemDetail unexpected(Exception ex) {
        log.error("Unhandled error", ex);                       // full detail in the log, with the trace id
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
            "Unexpected error");                                 // nothing internal to the client
    }
}
JSON — response body
{
  "type": "https://api.example.com/problems/order-not-found",
  "title": "Order not found",
  "status": 404,
  "detail": "Order 42 does not exist",
  "instance": "/api/orders/42",
  "orderId": 42
}
  • Built-in exceptions: extending ResponseEntityExceptionHandler (or setting spring.mvc.problemdetails.enabled=true in Boot 3) renders Spring's own errors — validation failures, 405, 415, missing parameters — as ProblemDetail as well. Override handleMethodArgumentNotValid to add the field errors as an errors extension.
  • Own exceptions: extend ErrorResponseException (or implement ErrorResponse) and Spring renders them without a handler method.
  • Matching: within one advice, the closest exception type in the hierarchy wins. With several advices, order them with @Order and narrow them with basePackages or assignableTypes.
  • Map domain errors deliberately: not found → 404, business conflict or optimistic-lock failure → 409, semantically invalid input → 422, everything unexpected → 500 with a generic message.
Senior touch: make type a stable URI that documents the error, and put the trace id in an extension member (e.g. traceId) so support can find the log line from the client's response.

How does JWT-based authentication work in Spring Boot? Walk me through the full flow.
Hard ▼

Flow: Client sends credentials → Server validates → Server issues signed JWT → Client stores token → Client sends token in Authorization: Bearer <token> header → Server validates signature on every request (stateless).

Java
// 1. SecurityFilterChain — disable sessions, add JWT filter
@Configuration @EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain chain(HttpSecurity http, JwtFilter jwtFilter)
        throws Exception {
        return http
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .csrf(AbstractHttpConfigurer::disable)
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .anyRequest().authenticated())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }
}

// 2. JWT filter — validates token on every request
@Component @RequiredArgsConstructor
public class JwtFilter extends OncePerRequestFilter {
    private final JwtService jwtService;

    @Override
    protected void doFilterInternal(HttpServletRequest req, ...) {
        String header = req.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            filterChain.doFilter(req, res); return;
        }
        String token = header.substring(7);
        String username = jwtService.extractUsername(token); // validates signature
        if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            var auth = new UsernamePasswordAuthenticationToken(username, null, roles);
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        filterChain.doFilter(req, res);
    }
}
⚠️
Security consideration
Store the JWT secret in environment variables or a secrets manager (Vault), never in application.properties. Use RS256 (asymmetric) for microservices so services can verify tokens with the public key without accessing the private key.
What a senior would add: in Spring Security 6 you rarely need a hand-written JWT filter. http.oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults())) with spring.security.oauth2.resourceserver.jwt.issuer-uri (or jwk-set-uri) validates signature, exp/nbf and issuer, and maps scope claims to SCOPE_* authorities. If you do keep a custom filter, remember that a @Component filter is also auto-registered by Boot as a plain servlet filter, so it runs twice unless you disable that registration with a FilterRegistrationBean (setEnabled(false)).

How do CSRF protection and CORS work in Spring Security 6, and when is it safe to disable CSRF?
Hard ▼

They solve different problems and are often confused:

CSRF protectionCORS
Threat / purposeStops a malicious site from making the victim's browser send a state-changing request with the victim's cookiesRelaxes the browser's same-origin policy so a trusted front end on another origin can read your responses
MechanismA secret token the attacker's page can't read, required on POST/PUT/PATCH/DELETEAccess-Control-Allow-* response headers; a preflight OPTIONS request for non-simple requests
Default in Spring SecurityOnOff until you configure it

CORS is not CSRF protection: a "simple" cross-site form POST is sent without a preflight, so CORS headers don't stop it from reaching the server — they only stop the attacker from reading the response.

Java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .cors(Customizer.withDefaults())           // uses the CorsConfigurationSource bean below
        .csrf(csrf -> csrf.disable())              // OK ONLY because auth is a bearer header, not a cookie
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .build();
}

@Bean
CorsConfigurationSource corsConfigurationSource() {
    var cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(List.of("https://app.example.com")); // explicit list, never "*" with credentials
    cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    cfg.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    cfg.setMaxAge(3600L);                                     // cache the preflight for 1 hour
    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", cfg);
    return source;
}

When disabling CSRF is safe: only when the browser never attaches the credential automatically — a bearer token in the Authorization header, sent by your JavaScript. As soon as authentication rides in a cookie (session cookie, or a JWT stored in a cookie), CSRF protection must stay on — SameSite=Lax cookies help but are defence in depth, not a replacement.

  • Spring Security 6 changes: the CSRF token is loaded deferred (only when a request needs it, so no session is created for every request), and the token sent to the page is XOR-masked with a random value per request to defend against BREACH.
  • SPA with cookie sessions: use CookieCsrfTokenRepository.withHttpOnlyFalse() so JavaScript can read the XSRF-TOKEN cookie and send it back as the X-XSRF-TOKEN header (Angular and Axios do this automatically). On 6.x the masked default handler needs extra wiring for this flow; Spring Security 7 adds a one-line csrf.spa().
  • CORS pitfalls: configure CORS in the security chain — otherwise the preflight OPTIONS request, which carries no credentials, is rejected with 401 before it reaches Spring MVC's @CrossOrigin. allowCredentials(true) together with origin "*" is rejected by Spring; use an explicit list or allowedOriginPatterns.

What is the N+1 select problem and how do you fix it?
Hard ▼

When fetching N entities that each have a lazy relationship, Hibernate fires 1 SELECT for the parent list plus N additional SELECTs for each child collection — N+1 queries total.

Java
// 🚫 Problem: fetches authors, then N queries for books
List<Author> authors = authorRepo.findAll();
authors.forEach(a -> System.out.println(a.getBooks().size())); // N extra queries!

// ✅ Fix 1: JOIN FETCH in JPQL
@Query("SELECT a FROM Author a LEFT JOIN FETCH a.books")
List<Author> findAllWithBooks();

// ✅ Fix 2: @EntityGraph — avoids modifying query string
// ⚠️ books AND books.tags both as List = two "bags" → MultipleBagFetchException;
//    use Set for one of them, or fetch the second level in a separate query.
@EntityGraph(attributePaths = {"books", "books.tags"})
List<Author> findAll(); // override JpaRepository method

// ✅ Fix 3: @BatchSize — lazy but loads in batches, not 1-by-1
@OneToMany @BatchSize(size = 25)
private List<Book> books;

// ✅ Fix 4: DTO projection with JOIN in query (most efficient)
@Query("SELECT new com.app.AuthorSummaryDto(a.id, a.name, COUNT(b)) "
     + "FROM Author a LEFT JOIN a.books b GROUP BY a.id, a.name")
List<AuthorSummaryDto> findSummaries();
💡
Detect it
Add spring.jpa.show-sql=true or use Hibernate's statistics to spot N+1. In production use p6spy or datasource-proxy to log slow query patterns. Second trap: JOIN FETCH of a collection combined with Pageable makes Hibernate paginate in memory (warning HHH90003004) — page over IDs first, then fetch those IDs with the join.

Explain the difference between FetchType.LAZY and EAGER. Which should you default to?
Medium ▼

LAZY — loads the related entity only when you access the field. Uses a proxy object. Default for @OneToMany and @ManyToMany.

EAGER — always joins and loads related data with the parent. Default for @ManyToOne and @OneToOne.

🚫
The EAGER trap
The JPA default of EAGER on @ManyToOne/@OneToOne is the trap: every load of the child also loads the parent, and in JPQL queries it becomes an extra SELECT per row (N+1). EAGER cannot be switched off per query. Instead, declare fetch = FetchType.LAZY on every association and use @EntityGraph or JOIN FETCH at query level to load what you need.

LazyInitializationException — accessing lazy data outside a transaction (after the session is closed). Fix: use @Transactional on the service method, load within the session, or use DTO projections. Spring Boot enables spring.jpa.open-in-view by default (and logs a warning about it), which hides this exception by keeping the session open for the whole web request — at the cost of a DB connection held through view rendering and lazy queries fired from the controller. Set it to false in production services.

Hard ▼

Second-level cache — optional, scoped to the SessionFactory (shared across transactions). Stores entity state in memory (Caffeine, Ehcache, Redis). Good for reference data that is read often and rarely changes.

What is the Circuit Breaker pattern? How do you implement it with Resilience4j?
Hard ▼

Circuit Breaker prevents cascading failures: if a downstream service is failing repeatedly, the breaker opens and fast-fails requests for a cooldown period, then half-opens to test recovery.

States: Closed (normal) → Open (failing, return fallback) → Half-Open (probe) → Closed (if probes succeed).

Java
# application.yml
resilience4j:
  circuitbreaker:
    instances:
      paymentService:
        slidingWindowSize: 10
        failureRateThreshold: 50      # open if 50%+ fail in last 10 calls
        waitDurationInOpenState: 10s  # wait before half-open
        permittedNumberOfCallsInHalfOpenState: 3

// Java usage
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
@Retry(name = "paymentService")
public PaymentResult charge(ChargeRequest req) {
    return paymentClient.charge(req);
}

public PaymentResult paymentFallback(ChargeRequest req, Exception ex) {
    log.error("Payment service unavailable", ex);
    return PaymentResult.pending("QUEUED_FOR_RETRY");
}

Order matters: in Resilience4j's Spring aspect the Retry wraps the CircuitBreaker by default, so each retry attempt is counted by the breaker. Library defaults are a count-based window of 100 calls, minimumNumberOfCalls 100 and a 50% failure threshold — tune them, because the defaults react slowly on low-traffic endpoints.

What is the difference between String, StringBuilder, and StringBuffer?
Easy▼

String — immutable. Every operation creates a new object. Safe for sharing, inefficient for many concatenations in a loop.

StringBuilder — mutable, not thread-safe. Use in single-threaded string building (most common case).

StringBuffer — mutable, thread-safe (all methods synchronized). Slower than StringBuilder; rarely needed — prefer proper synchronization at a higher level instead.

ℹ️
Modern Java

Explain Java's memory model: stack vs heap, and what causes a memory leak?
Medium▼

Stack — per-thread, stores local variables and method call frames. Automatically cleaned up when method returns. Stack overflow = infinite recursion.

Heap — shared, stores all objects. GC reclaims unreachable objects. OutOfMemoryError: Java heap space means live (reachable) data no longer fits — either the heap is too small for the workload or a leak keeps objects reachable that are never used again. (The Java Memory Model — happens-before, volatile — is a different topic, covered in the Concurrency section; heap layout and GC are in the JVM section.)

Memory leaks in Java (object is reachable but logically unused):

  • Static collections that keep growing: static Map<K,V> that is never cleared
  • Listeners/callbacks registered but never de-registered
  • ThreadLocal variables not removed after request completes (thread pool reuse)
  • Long-living cache without eviction policy
  • Non-static inner class or anonymous class/lambda that outlives its outer object (holds an implicit reference to it)

Testing asynchronous code — CompletableFuture, @Async, and Awaitility
Hard ▼

Async code is tricky to test because the assertion might run before the async operation completes. Three strategies exist:

1. CompletableFuture.get() — block the test thread until the future completes. Simple but can hang forever if the future never completes.

2. Awaitility — polls a condition with a timeout. Works for any async trigger including @Async, Kafka listeners, event handlers.

3. SyncTaskExecutor — configure a synchronous executor in the test profile so @Async methods execute in the same thread (no real async).

Java — async test strategies
// Strategy 1: CompletableFuture.get() — blocks until done
@Test
void asyncFetch_returnsResult() throws Exception {
    CompletableFuture<String> future = asyncService.fetchData();
    String result = future.get(5, TimeUnit.SECONDS); // timeout guard
    assertThat(result).isEqualTo("expected");
}

// Strategy 2: Awaitility — poll until condition or timeout
// testImplementation 'org.awaitility:awaitility:4.2.0'
@Test
void asyncKafkaConsumer_processesMessage() {
    kafkaTemplate.send("orders", "order-1");

    Awaitility.await()
        .atMost(10, TimeUnit.SECONDS)
        .pollInterval(500, TimeUnit.MILLISECONDS)
        .untilAsserted(() -> {
            assertThat(orderRepository.findByOrderId("order-1")).isPresent();
        });
}

// Strategy 3: SyncTaskExecutor in test config — disables actual async
@TestConfiguration
class SyncExecutorConfig {
    @Bean
    @Primary
    public TaskExecutor taskExecutor() {
        return new SyncTaskExecutor(); // @Async runs synchronously in tests
    }
}
ℹ️
Awaitility is the gold standard
Awaitility's untilAsserted() retries the assertion block on every poll interval, which handles flakiness naturally. Unlike Thread.sleep(), it passes as soon as the condition is true — no unnecessary waiting.

JaCoCo test coverage — what to measure, what NOT to measure, common pitfalls
Medium ▼

JaCoCo (Java Code Coverage) measures which lines/branches of code were executed during tests. High coverage is a hygiene signal, not a quality guarantee — you can reach 100% line coverage with tests that make no assertions.

What to measure:

  • Business logic — service methods, domain rules, validation
  • Branch coverage — ensure both true/false paths of conditions are tested
  • Error handling paths — exception cases, null checks

What NOT to measure (exclude):

  • Generated code — Lombok-generated getters/setters, MapStruct mappers
  • DTOs and POJOs with no logic
  • Configuration classes (@Configuration, @Bean methods)
  • Main application class (*Application.java)

REST best practices — Richardson Maturity Model, idempotency, statelessness
Medium ▼

The Richardson Maturity Model (RMM) defines four levels of REST compliance:

  • Level 0 — Single URI, POST everything (SOAP-like). POST /api?action=getUser
  • Level 1 — Multiple resources (URIs) but still only POST. POST /users/1
  • Level 2 — HTTP verbs used correctly (GET, POST, PUT, DELETE, PATCH) + status codes. This is what most "REST APIs" actually are.
  • Level 3 (HATEOAS) — Responses include hypermedia links to related actions. Rarely used in practice.
HTTP — Level 2 REST conventions

POST   /users          → create user (201 Created, Location header)
PUT    /users/42       → replace user (200 or 204)
PATCH  /users/42       → partial update (200 or 204)
DELETE /users/42       → delete (204 No Content)

// Idempotency: same request → same result (safe to retry)
// Idempotent: GET, PUT, DELETE, HEAD, OPTIONS
// NOT idempotent: POST (creates new resource each time)
// PATCH is NOT guaranteed idempotent (depends on operation)

// Statelessness: server stores no session; each request is self-contained
// Auth via JWT in Authorization header, not server-side session cookie
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...

Common REST mistakes
Using verbs in URIs (/getUser, /deleteOrder), returning 200 for errors with error body, using POST for idempotent operations without idempotency keys, ignoring 409 Conflict for duplicate resources, and not returning the Location header after 201 Created.

GraphQL N+1 problem — what is it and how does DataLoader solve it?
Hard ▼

The N+1 problem is the most common GraphQL performance issue. When you query a list of N items and each item's resolver makes a separate DB call for a related entity, you end up with 1 + N database queries instead of 1.

Example: query 100 users, each user's department field triggers a separate SQL call → 101 queries.

DataLoader solves this by batching and caching — it collects all the IDs requested within one event loop tick, then makes a single batched query.

Java — DGS (Netflix GraphQL) DataLoader example
// Without DataLoader: N+1 problem
@DgsComponent
class UserDataFetcher {
    @DgsData(parentType = "User", field = "department")
    public Department getDepartment(DgsDataFetchingEnvironment dfe) {
        User user = dfe.getSource();
        return deptRepo.findById(user.getDeptId()); // 1 query per user = N+1!
    }
}

// With DataLoader: single batched query
@DgsDataLoader(name = "departments")
class DepartmentDataLoader implements BatchLoader<Long, Department> {
    @Override
    public CompletionStage<List<Department>> load(List<Long> deptIds) {
        // Called ONCE with ALL dept IDs from the current query
        return CompletableFuture.supplyAsync(
            () -> deptRepo.findAllById(deptIds) // 1 query total
        );
    }
}

@DgsData(parentType = "User", field = "department")
public CompletableFuture<Department> getDepartment(DgsDataFetchingEnvironment dfe) {
    DataLoader<Long, Department> loader = dfe.getDataLoader("departments");
    User user = dfe.getSource();
    return loader.load(user.getDeptId()); // batched — returns CompletableFuture
}
✅
DataLoader caching
DataLoader also caches within a request — if department 5 is requested by multiple users in the same query, it's only fetched once. The cache is per-request, not global, so it won't serve stale data.

gRPC in Java — protobuf definition, streaming types, when to prefer over REST
Hard ▼

gRPC uses HTTP/2 + Protocol Buffers (protobuf) — a binary serialisation format. Smaller payloads, cheaper (de)serialisation and multiplexed long-lived HTTP/2 connections usually give lower latency and higher throughput than REST+JSON for internal service-to-service calls — how much depends on payload and workload, so benchmark rather than quote a multiplier.

4 streaming types:

  • Unary — one request, one response (like REST)
  • Server streaming — one request, stream of responses (e.g. log tailing)
  • Client streaming — stream of requests, one response (e.g. file upload)
  • Bidirectional streaming — both sides stream (e.g. chat)
Protobuf + Java — gRPC service definition

service OrderService {

    rpc CreateOrders (stream CreateOrderRequest) returns (OrderSummary); // client stream
}

Choose gRPC for internal microservice communication where: (1) latency matters (trading systems, real-time analytics), (2) you need streaming (live data feeds), (3) strong typing and backward-compatible schema evolution via protobuf field numbers is valuable. JWT structure and validation in Spring Security — header.payload.signature, claims, exp
Medium ▼

A JWT (JSON Web Token) is a self-contained credential — the server doesn't need a session store because the token carries the claims itself.

Structure: three Base64URL-encoded parts separated by dots: header.payload.signature

  • Header — algorithm (alg: RS256) and type (typ: JWT)
  • Payload — claims: sub (subject/user ID), exp (expiry timestamp), iat (issued at), roles (custom)
  • Signature — HMAC or RSA signature over header+payload. Prevents tampering.
Java — Spring Security JWT validation
// Spring Security 6 — JWT resource server configuration
@Configuration
@EnableWebSecurity
class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .anyRequest().authenticated())
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtConverter())))
            .build();
    }

    @Bean
    public JwtDecoder jwtDecoder() {
        // Validates signature, expiry (exp), not-before (nbf) automatically
        return NimbusJwtDecoder
            .withPublicKey(rsaPublicKey()) // or .withJwkSetUri() for OIDC
            .build();
    }

    private JwtAuthenticationConverter jwtConverter() {
        var converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(jwt -> {
            // Extract custom "roles" claim → GrantedAuthority list
            List<String> roles = jwt.getClaimAsStringList("roles");
            return roles.stream()
                .map(r -> (GrantedAuthority) () -> "ROLE_" + r)
                .collect(toList());
        });
        return converter;
    }
}
⚠️
JWT security pitfalls
(1) Never use alg=none — reject tokens with no algorithm. (2) Short expiry (15min) + refresh token pattern reduces exposure window. (3) Sensitive data (passwords, PII) must NOT go in the payload — it's Base64-encoded, not encrypted. (4) JWTs cannot be invalidated before expiry — use a token blocklist or short expiry for logout.

OAuth2 flows — Authorization Code (PKCE), Client Credentials, when to use which
Hard ▼

OAuth2 is an authorization framework, not an authentication protocol. It defines several flows (grants) for different scenarios.

Authorization Code + PKCE — the secure flow for user-facing applications (web apps, SPAs, mobile). The user logs in at the identity provider; the app receives an authorization code and exchanges it for tokens. PKCE prevents authorization code interception attacks.

Client Credentials — machine-to-machine. No user involved. A service authenticates with its own client ID + secret to get an access token. Used for microservice-to-microservice calls.

API versioning strategies — URI path vs Accept header vs query param, pros/cons
Medium ▼

API versioning lets you evolve the API without breaking existing clients. Three main strategies:

StrategyExampleProsCons
URI Path/api/v2/usersSimple, cacheable, visible in logsNot pure REST (URI should identify resource, not version)
Accept HeaderAccept: application/vnd.api.v2+jsonPurest REST, same URIHard to test in browser, not cached by default
Query Param/users?version=2Easy to test, optionalBreaks caching, pollutes query string
Java — URI path versioning in Spring
// Most common in practice — URI path versioning
@RestController
@RequestMapping("/api/v1/users")
class UserControllerV1 { // legacy contract preserved
    @GetMapping("/{id}")
    public UserResponseV1 getUser(@PathVariable Long id) { ... }
}

@RestController
@RequestMapping("/api/v2/users")
class UserControllerV2 { // new contract
    @GetMapping("/{id}")
    public UserResponseV2 getUser(@PathVariable Long id) { ... }
}

// Sunset old versions gracefully — deprecation headers
// Deprecation (RFC 9745): structured-field date = @ + epoch seconds (here 2025-01-01T00:00:00Z)
response.addHeader("Deprecation", "@1735689600");
// Sunset (RFC 8594): HTTP-date, must not be earlier than Deprecation
response.addHeader("Sunset", "Tue, 01 Jul 2025 00:00:00 GMT");
response.addHeader("Link", "</api/v2/users>; rel=\"successor-version\"");
ℹ️
Industry preference
URI path versioning (/api/v2/) is the most common default because it is visible, cacheable and easy to route. Big public APIs often combine it with date-based versions: Stripe has /v1 in the path plus a dated Stripe-Version header pinned per account, and GitHub's REST API selects a dated version with the X-GitHub-Api-Version header. Twilio puts a date in the path (/2010-04-01/). Spring Framework 7 / Spring Boot 4 add first-class support: a version attribute on @GetMapping etc. plus a configured strategy (header, path segment, query parameter or media-type parameter).
